## Engines

One table in `lib.zsh` names every engine. Each is reached through its Docker Engine API socket with `docker -H <socket>`; no script changes the current docker context or `/var/run/docker.sock`.

| Engine       | Socket                                                               | Docker context  | Memory attribution (`engine-memory.ts`)                                                                                                                                     | Arms                          | Container IP from the Mac |
| ------------ | -------------------------------------------------------------------- | --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- | ------------------------- |
| `docker`     | `unix://$HOME/.docker/run/docker.sock`                               | `desktop-linux` | Docker.app and `com.docker.*` processes, plus the Virtualization VM process paired by start time with `com.docker.virtualization`                                           | `docker-cli`                  | no                        |
| `docker-vmm` | the same socket as `docker`                                          | `desktop-linux` | Docker.app and `com.docker.*` processes; the VM runs inside `com.docker.krun` (role `vm`), so no Virtualization VM process is expected                                      | `docker-cli`                  | no                        |
| `colima`     | `unix://$HOME/.colima/default/docker.sock`                           | `colima`        | the `limactl` processes and the ssh mux of `~/.colima/_lima`, plus the Virtualization VM process paired by start time with the `limactl hostagent` (its pid is in `vz.pid`) | `docker-cli`                  | no                        |
| `orbstack`   | `unix://$HOME/.orbstack/run/docker.sock`                             | `orbstack`      | to verify on install; `idle-memory.zsh` and `engine-memory.ts` refuse `orbstack` until it is filled in                                                                      | `docker-cli`                  | no (to verify on install) |

Override a socket with `BENCH_DOCKER_SOCKET`, `BENCH_COLIMA_SOCKET`, `BENCH_ORBSTACK_SOCKET` or `BENCH_APPLE_SOCKET`. An arm is a client of the engine: `docker-cli` is the docker CLI on the engine's socket (on `apple` that socket is socktainer), `container-cli` is Apple's own `container` CLI. The Apple arm is paused until socktainer ships a release built for container 1.7.1; it still works.

- **Colima here:** 0.10.3, Docker 29.5.2 (API 1.54), VZ with virtiofs and Rosetta, 8 CPUs, 8 GiB, a 30 GiB disk, `~` and `/var/folders` mounted writable, `--port-forwarder grpc`. Its VM is a `com.apple.Virtualization.VirtualMachine` process whose parent is launchd; Lima's hostagent (`limactl hostagent ... colima`) starts it and writes its own pid to `~/.colima/_lima/colima/vz.pid`. `limactl usernet` (the user-mode network) and the ssh control master (`ssh: ~/.colima/_lima/colima/ssh.sock [mux]`) run beside it.
- **`docker-vmm` is a label, not an engine.** The main session switches Docker Desktop to its Docker VMM hypervisor by hand; the scripts then run with `--engines docker-vmm,...`. `docker info` has no hypervisor field (on VZ it says `OperatingSystem` "Docker Desktop", `KernelVersion` `7.0.12-linuxkit`), so `bench_init` reads Docker Desktop's processes: `com.docker.virtualization` alone means VZ, `com.docker.krun` alone means Docker VMM. It refuses `docker-vmm` unless they show VMM and `docker` unless they show VZ, and says it cannot tell when both or neither run. `meta.json` records the verdict, the two process flags, and `OperatingSystem` and `KernelVersion`, under `docker_desktop_hypervisor`. `docker` and `docker-vmm` never run in one order.
- **OrbStack** is not installed yet. After install: read its host processes (`ps -axww -o pid,ppid,rss,lstart,args`), fill in its rule in `BENCH_MEMORY_RULE` and `engine-memory.ts`, and check whether the Mac reaches its container IPs (OrbStack documents that it does) before setting `BENCH_HOST_IP[orbstack]=1`.

## Running

```sh
docs/research/container-engines/scripts/startup-alpine-true.zsh               # docker,colima, A,B,A,B
docs/research/container-engines/scripts/startup-alpine-true.zsh --engines docker,colima,orbstack --interleave 3
docs/research/container-engines/scripts/startup-alpine-true.zsh --engine colima --out /some/folder
docs/research/container-engines/scripts/startup-alpine-true.zsh --dry-run     # prints every command, writes nothing
```

Every script takes the same common options (`--help` lists them and the script's own):

| Option              | Meaning                                                           |
| ------------------- | ----------------------------------------------------------------- |
| `--engines A,B[,C]` | The engines of the run, in their order. Default: `docker,colima`. |
| `--interleave N`    | Repeat the whole order N times: A,B,C,A,B,C. Default: 2.          |
| `--engine NAME`     | One engine, once; excludes `--engines` and `--interleave`.        |
| `--out DIR`         | Output folder. Default: `runs/<experiment-id>/<UTC timestamp>/`.  |
| `--dry-run`         | Print the commands only.                                          |

Each script:

- re-runs itself under `caffeinate -dimsu`;
- reaches each engine with `docker -H <socket>` from the engine table, and Apple's own `container` CLI as the `container-cli` arm of `apple`;
- wraps every docker and container CLI call in `gtimeout -s KILL` (`BENCH_CALL_TIMEOUT`, default 180 s; the long-running experiments raise it);
- labels every container and volume it makes `dev.zukhruf.bench=1` and, at exit, on a failed command and on Ctrl-C, removes those on the engines of the run (through the docker CLI and, when `apple` is in the run, through `container list`/`container delete`), and nothing else; a run without `apple` never touches socktainer or Apple's CLI;
- checks every result file after the measurement that writes it: it must be non-empty, and a `.json` file must parse (hyperfine files must hold `.results[i].summary.time_wall_clock.median`); otherwise the experiment fails with `FAILED: ...`, exit 1, and `meta.json` state `failed`. A run that measured nothing never exits 0;
- writes `meta.json` (experiment, state, order, limits, images; per engine of the run its socket, docker context and that context's endpoint, arms, memory rule, `docker version` and a slice of `docker info`; Docker Desktop's hypervisor when `docker` or `docker-vmm` runs; the versions of Colima, OrbStack, `container` and socktainer when they run, and of hyperfine; macOS version and host, load average at start and end, other running containers at start per engine, notes, and every command line as run) and `commands.log`.

Run nothing else on an engine of the run while a script runs: another test suite's containers are noise, and `idle-memory.zsh` refuses to start while other containers run.

## Limits

The measured containers get `--cpus 2 --memory 1g` on every engine, except where a script's option changes them (`sysbench-cpu.zsh --cpus`). socktainer floors CPUs to whole vCPUs, so CPU counts stay whole. Apple boots each container in its own VM with the asked vCPUs plus one vCPU of overhead (`configuration.resources.cpuOverhead`); Docker Desktop and Colima (and OrbStack) cap the container with a cgroup quota inside their one shared VM, 8 CPUs and 8 GiB each here.

### Traps

- **Two Apple arms, one engine.** socktainer and the `container` CLI reach the same container-apiserver. A container made through socktainer has a Docker-style id there and a UUID in `container list`, so each arm addresses its containers by the name it gave them.
- **VM processes.** Docker Desktop on VZ, Colima and Apple run VMs in `com.apple.Virtualization.VirtualMachine` processes whose parent is launchd. `engine-memory.ts` gives each VM process to the owner that started nearest it (`com.docker.virtualization`, Colima's `limactl hostagent`, or a `container-runtime-linux`), and lists any it cannot place. On 2026-11-16 the Colima VM (pid 78593) started one second after its hostagent (pid 78585, the pid in `vz.pid`) and 36 minutes after Docker Desktop's.
- **A shared VM's RSS moves** (Docker Desktop's, Colima's) with its memory balloon and page cache (1.5 to 4.4 GiB within minutes on 2026-11-15), so read the samples, not one value.
- **Host iperf3.** The host paths of `iperf3-network.zsh` need iperf3 on the macOS host (`brew install iperf3`; iperf 3.22 is installed). Without it the script skips those paths and records that in `meta.json`.
- **A failed iperf3 run** keeps iperf3's error JSON and the script goes on, but it fails unless at least one run on each route measured a throughput (`.end.sum_received.bits_per_second`).
- **Bind mounts from ~/Desktop.** This repo lives under ~/Desktop, which macOS guards with a Files & Folders grant. Docker Desktop has it; Apple's helper does not, and a run with such a bind mount hangs. So `fio-storage.zsh` keeps its bind folder under `/var/folders/...`, which Docker Desktop shares by default and Colima mounts (writable).
- **A bind mount can be fake.** A host path the engine does not share is no error: it becomes an empty folder on the VM's disk, and fio would measure that disk. So each fio slot first writes a marker on the host and reads it inside the container, then writes one inside and reads it on the host, and fails the experiment (`FAILED: the bind mount on <engine> is not <path>...`) on a mismatch. Proved on 2026-11-16: Colima, bound to `/private/tmp/...` (not in its mounts), failed with `cat: can't open '/mnt/bind/zukhruf-bench-host-marker'`.
- **Cleanup on a failed command.** zsh 5.9 runs neither the EXIT trap nor `zshexit` when errexit ends the shell inside a function (`setopt errexit; trap "print ran" EXIT; f() { false; }; f` prints nothing), nor when a trap calls `exit` inside one. `lib.zsh` therefore also cleans up from a ZERR trap, in the main shell only, with errexit off only inside the cleanup function (`setopt localoptions noerrexit`).
- **`| head -1` under pipefail.** `colima version | head -1` exits 141: head closes the pipe, the writer dies of SIGPIPE, and pipefail fails the line. Take the first line in zsh instead: `${${(f)"$(colima version)"}[1]}`.
- **zsh special names.** A local named `path` (or `status`, `options`, ...) replaces the special parameter: `local path=...` empties PATH and every later command fails with exit 127.
- **sysbench threads.** `experiments.yaml` says 4 threads and 4 CPUs; the script defaults to 2 and 2 to match the shared limits. Run `sysbench-cpu.zsh --threads 4 --cpus 4` for the yaml's shape.
- **fio is time-based.** `--size=256M` sets the file size; each job runs for `--runtime` seconds (default 20) after a 2 s ramp, so fast jobs are not over in milliseconds.

## Client-level experiments

Experiments 2 and 7 go through our own client, `@zukhruf/docker`, from `packages/docker` in this repo (with the socktainer fixes of c2adeef3 and d80eb532). Each wrapper takes the common options and runs one `node --conditions=@zukhruf/source <experiment>.ts` per slot; the repo's `node_modules/@zukhruf/docker` link resolves to the package's TypeScript source, which Node runs directly. The `.ts` script connects with `Docker.connect({ clock: globalThis, host })` to the slot's socket, writes `<slot>.json`, and the wrapper ends with `client-summary.ts`, which writes `summary.tsv`: engine, metric, sample (`first` or `warm`), n, failed runs, median, p95 (NumPy's linear quantile, from `@zukhruf/statistics`), min and max, in ms. In a dry run the wrapper runs each `.ts` with `--dry-run`, which prints the exact create body and the plan and touches no engine. Before the first slot, each wrapper pulls its image on an engine that lacks it, and records that in `meta.json`.

Each slot has one first run (it includes any image unpack), stored as `first` in the slot file and summarized apart, then the measured runs.

| Script                       | What runs                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Raw output                                                                  |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| `postgres-time-to-ready.zsh` | `--runs` (default 10) runs per slot of `postgres:18-alpine` with the Env and `MemorySwappiness: 0` of `packages/testing/src/databases/postgres.ts`, `NanoCpus` 2e9, `Memory` 1 GiB, and 5432 published on `127.0.0.1` with `HostPort: ""`. Each run: create, start, then three loops that poll every 50 ms (cap 60 s): the oracle, `exec pg_isready -h 127.0.0.1 -U postgres -t 1` as `packages/testing` checks; the published port, a TCP connect plus a Postgres SSLRequest that only the server answers (`S` or `N`); with `--ip-path`, which the wrapper passes where the Mac reaches container IPs (`apple`), the same probe on the container IP. `ready_published_ms` and `ready_ip_ms` are the later of the oracle and that path's answer. Then `remove({ force: true, v: true })`. | `<slot>.json` (every run's times, ports, IP, probe attempts), `summary.tsv` |
| `attach-round-trip.zsh`      | `--containers` (default 10) cat leases per slot: alpine, `Entrypoint: ['cat']`, `Cmd: ['-']`, `OpenStdin`, `StdinOnce`, `AttachStdin`, `AutoRemove`, the shared limits. Each: create, `attach({ stdin: true })`, start, `--writes` (default 20) round trips of a 32-byte line from the stdin write to its echo on stdout, close stdin until `exitCode` resolves, then exit until `containers.inspect()` gives 404 (polled every 10 ms) and until `wait({ condition: 'removed' })`, sent before the start, resolves.                                                                                                                                                                                                                                                                        | `<slot>.json` (every container's times and round trips), `summary.tsv`      |

Metrics in the slot files and `summary.tsv`, in ms:

- postgres-time-to-ready: `create_ms`, `oracle_ms`, `published_tcp_ms`, `published_answer_ms`, `ready_published_ms`, `ip_tcp_ms`, `ip_answer_ms`, `ready_ip_ms` and `total_ms` from t0 (just before the create); `start_ms` from created; `remove_ms` the removal alone.
- attach-round-trip: `create_ms`, `attach_ms`, `start_ms` (each call alone), `round_trip_ms` (all writes pooled), `close_to_exit_ms`, `exit_to_removed_ms` (inspect), `exit_to_removed_wait_ms` (wait).

### Traps

- **Tmpfs.** socktainer ignores `HostConfig.Tmpfs` (backlog #4434) but honours `HostConfig.Mounts` of type `tmpfs`, so `postgres-time-to-ready.ts` puts the data folder (`/var/lib/postgresql`, 512 MiB, mode 01777) on a tmpfs mount on every engine. `packages/testing` still uses `HostConfig.Tmpfs`, so on Apple its Postgres writes to the VM disk.
- **Limits.** `experiments.yaml` names 1 CPU for experiment 2; the script uses the shared `--cpus 2 --memory 1g`.
- **A connect is not readiness.** A port forwarder can accept a TCP connect before Postgres listens, so the `*_tcp_ms` times are recorded but readiness needs the SSLRequest answer. The probe never half-closes the socket: Apple's forwarder drops a half-closed connection.
- **The container IP** comes from the inspect's `NetworkSettings.Networks`. If socktainer gives none, the run records `the inspect gives no IPAddress` and fails, so the slot file shows it at once.
- **wait removed** may not be served by socktainer; `exit_to_removed_wait_ms` is then null and the slot file keeps the error in `waitRemovedError`. `exit_to_removed_ms` does not depend on it.

`/usr/bin/time -p npx nx run docker:test --skip-nx-cache` and `/usr/bin/time -p npx nx run mutex:test --skip-nx-cache` (then testing's database suites once #4205 lands), at least 3 runs per engine. A red suite is recorded with its exit code; it counts against criterion 2.
