# A step reads a tree, and runs its tools in a snapshot without the git variables of the repo

On 2026-11-16, three new pre-commit steps were planned for the repos of one developer. `LockfileSync` runs `npm ci --dry-run` on the staged tree, to find a lockfile that does not record the manifests. `NpmrcPolicy` reads `.npmrc` on each commit, also when the commit does not change it. `DockerfileInstallsFromLockfile` reads each staged Dockerfile. The first step stopped at a gap of this package: a step cannot run a tool on the staged tree with an environment that has no git variables of the repo. Ezz then asked for a redesign: "step back and do proper work. I don't care how long it takes and how many breaking changes", and "we need no backward compatibility, no legacy". A review of the package found these faults:

- `Commit.inSnapshot(work)` gives `work` a folder and no environment (`src/commit.ts:64`). The environment of `Commit` is private (`src/commit.ts:18`), and the island lint stops a package step that reads `process.env`. Thus a repo step that runs a tool starts it with `execFile` and no `env`, and the tool gets each variable of the hook, `GIT_INDEX_FILE` too. text2sql's `DesignCheck` runs a shell script that copies the index and runs node there (`.husky/pre-commit.ts:21-45`). zukhruf's `ReadmeTable` reads the index with its own git commands (`tools/readme-table/src/packages-table.ts:52-78`). A tool that runs git in a folder of its own then reaches the repo of the hook. This is the fault of zukhruf #3083.
- `staged()` lists the paths with `--diff-filter=ACMR` (`src/commit.ts:26-35`), so it leaves out deletions. `files()`, `touches()`, `affected()` and `DependencyChecks` read it. A commit that deletes `package-lock.json` or a `package.json` starts no step that watches these files.
- `Sync` and `Codegen` run nx in the working tree: `Commit.nx` runs with the root as its current folder (`src/commit.ts:89-104`). `Sync` stages each file whose working-tree copy changed during `nx sync` (`src/sync.ts:26-42`). `Codegen` builds from the working tree, which holds edits that are not staged, and then runs `git add` on whole folders (`src/codegen.ts:38-45`). ADR 0001 says that a step never reads the working tree to judge a commit.
- The pre-push install gives npm the environment of the hook, with the git variables of the repo (`src/push.ts:131-139`), although the hook made the environment without them at `src/push.ts:113`. `npm rebuild` runs the install scripts of the dependencies with these variables.
- The install copies a set of files that the code names: `package.json`, `package-lock.json`, `.npmrc` and the `package.json` of each workspace (`src/snapshot/installs.ts:68-77`), and the folders that `file:` dependencies name (`src/snapshot/installs.ts:78`). npm 12 also reads the `patches/` folder that `patchedDependencies` names (npm-patch(1)) and a `.npm-extension.mjs` or `.npm-extension.cjs` file (npm-extension(5)). The install has neither. The workspace folders come from a glob of the snapshot (`src/snapshot/installs.ts:104`). deepagents lists `.evals-sdk-it` in its workspaces and in its lockfile, but its `.gitignore` names the folder, so a clean checkout does not have it. The copy of that folder then fails with ENOENT, and each push with install drift stops (#4193). The name of an install is the hash of the lockfile only (`src/snapshot/installs.ts:39-42`), so a commit that changes only `.npmrc` uses an install made with the old `.npmrc`.
- `Commit` and `Push` have two snapshots (`checkout-index` at `src/commit.ts:64-71`, a shared clone at `src/push.ts:85-152`), two ways to run nx (`Commit.nx`, and `runNx` at `src/snapshot/nx.ts:12-35`, which alone knows the `nx.cmd` of Windows) and two environments. `Build` reads `NX_CACHE_DIRECTORY ?? ''` from the environment that it gets (`src/build.ts:83`).
- The index that the hook sees depends on how the commit started (`prepare_index` in git's `builtin/commit.c`). A plain `git commit` runs the hook on the real index, and does not lock it during the hook. A `git add` of a peer during the hook then goes into the commit, and no step judged it. `git commit -a` runs the hook on the locked index, `index.lock`. `git commit --only` and `git commit <paths>` run the hook on a temporary index, `next-index-<pid>.lock`, and then commit the real index with only those paths. Git reads the index again after the hook. Thus a file that a step stages in the temporary index goes into the commit, but not into the real index.

The leading tools judge staged content too, but they change the working tree to do it:

- pre-commit saves the edits that are not staged as a patch, checks out the index, runs the hooks, and applies the patch again (`_unstaged_changes_cleared` in `pre_commit/staged_files_only.py`, https://pre-commit.com). lint-staged makes a backup stash and hides the unstaged edits of the files that are partly staged (lint-staged README, `--no-stash` and `--no-hide-partially-staged`). lefthook saves the unstaged edits of those files as a patch, discards them, and applies the patch after the hook (`withHiddenUnstagedChanges` in `internal/run/controller/guard.go`). ADR 0001 rules this out: many sessions edit one working tree.
- No tool gives a deleted path to a content tool. pre-commit lists the paths with `--diff-filter=ACMRTUXB`, "Everything except for D" (`get_staged_files` in `pre_commit/git.py`). lint-staged and lefthook use `ACMR` (`lib/getDiffCommand.js`, `internal/git/wrapper/staged_files.go`). lefthook decides whether to skip a command with `ACMRD` (`internal/git/wrapper/staged_files_with_deleted.go`, used in `internal/run/controller/command/build_command.go`), so a commit that only deletes a file still runs the command. text2sql's design script does the same (`tools/design-md/bin/pre-commit-check.sh:4`).
- When a hook changes a file, pre-commit fails the commit ("files were modified by this hook", `pre_commit/commands/run.py`). lint-staged and lefthook (`stage_fixed`) stage the change. ADR 0001 already chose to stage only the files that a step wrote.
- githooks(5) (https://git-scm.com/docs/githooks): git exports `GIT_DIR`, `GIT_WORK_TREE` and the other variables so that the git commands of the hook find the repo. A hook that runs git in another repo or in another working tree must clear them, for example with `unset $(git rev-parse --local-env-vars)`. pre-commit removes the `GIT_` variables before it runs git elsewhere (`no_git_env` in `pre_commit/git.py`), because `GIT_DIR` made `git clone` clone the wrong repo.

## Decision

1. **The host.** `src/scripts/host.ts` is the one module that reads the process: the current folder, the arguments, the standard input and the environment of the hook. It prints the outcomes and sets the exit code. `preCommit`, `prePush` and `commitMsg` call it. The host builds the subject of the steps, and keeps each environment private to the package. A step never gets an environment.
2. **Two environments.** Git commands on the repo get the hook environment, which is the environment that git gave the hook. Thus they read and write the index of the commit. Each tool gets the tool environment: the hook environment without each variable that `git rev-parse --local-env-vars` lists. A tool is nx, npm (the installs too), ESLint, Prettier, a command of the repo, and git inside a snapshot. In a snapshot, the tool environment also has `NX_DAEMON=false`, and the nx cache and the workspace data of the state folder. The host computes the tool environment one time for each run of a hook.
3. **A tree.** A step reads a `Tree`: git's tree object. The staged tree is the tree that `git write-tree` writes from the index of the hook, as pre-commit does (`pre_commit/staged_files_only.py`). The hook runs it on a private copy of that index: `git write-tree` takes the lock of the index (`index.lock`) to keep the trees that it wrote, and fails with "File exists" while another process holds the lock. A plain `git commit` does not lock the index while the hook runs, so a peer's `git add`, or the `git status` of an editor, can hold it (seen on git 2.54, 2026-11-16). The tree of a pushed commit is `<sha>^{tree}`. `entries(globs?)` lists its tree entries (libgit2's term, `git_tree_entry`), each with its path and its kind: file, link or submodule. `read(path)` gives the content of an entry, or `undefined` when the tree has no file or link there. A tree does not change, so a step reads one state of the commit, also when the index changes during the hook.
4. **Diff entries.** `changes()` lists the diff entries (JGit's term, `DiffEntry`) from the tree of `HEAD` to the staged tree, with `git diff-tree -r --no-renames`. Each entry is added, modified, deleted or type-changed, the words of git's `--diff-filter`. A rename is a deleted entry and an added entry. A first commit diffs from the empty tree. `Push.changes(update)` diffs from the tree of the base to the tree of the head, or from the empty tree when there is no base. A step that reads content skips the deleted entries. `touches(globs)` counts them, as lefthook does for its skip.
5. **One snapshot.** Both hooks use the snapshot of ADR 0002 point 1: `git clone --shared --no-checkout`, then `git checkout --detach <commit>` in the clone, both with the tool environment. For the staged tree, the hook first writes a commit of it with `git commit-tree <tree> -p HEAD`, on the repo, with a fixed author, committer and date (`GIT_AUTHOR_*`, `GIT_COMMITTER_*`) and `--no-gpg-sign`. Thus one tree and one parent give one commit id. No ref holds that commit, and `git gc` prunes it. The clone finds it through the shared object store. A snapshot is shared by the steps that ask for the same tree. A later ask for packages links a `node_modules` into the same clone. A step does not change the files of the commit in it. The runner disposes each snapshot after the last step, with an `AsyncDisposableStack`.
6. **A tool in a snapshot.** `snapshot.run(command, args)` runs a command from the `PATH`, and `snapshot.bin(name, args)` runs `node_modules/.bin/<name>` (`<name>.cmd` through a shell on Windows). Each runs with the snapshot as its current folder and with the tool environment. Neither uses a shell, except for a `.cmd` file on Windows. An option `env` adds variables, as the `env` of `Build` does for nx. Each gives a `ProcessResult` with the field names of Node's `spawnSync`: `status`, `stdout` and `stderr`. An exit code other than 0 is a result, not an error. A command that cannot start throws the error of Node. `snapshot.nxCacheDirectory` names the nx cache of the state folder, where `Build` reads the summary of its run.
7. **Packages on request.** A snapshot has a `node_modules` only when a step asks for it with `{ packages: true }`. Only then the tree must have a `package-lock.json`. On 2026-11-16, Ezz chose "Exact: commit's own packages" for the steps of the pre-commit hook. Thus a pre-commit snapshot with packages uses the install of the staged lockfile, as a pre-push snapshot does: the installed packages when they match the lockfile, and else an install in the state folder (ADR 0002 point 3).
8. **Generated files.** A step that writes files, such as `Sync` and `Codegen`, calls `commit.generate(globs, work)`. `work` runs in a private snapshot of the staged tree, with packages. Then the hook lists the paths that the work changed in the clone, with `git status`: changed, new and deleted files, but not ignored files. It stages each path that matches a glob into the index of the hook. It writes a file into the object store of the repo with `git hash-object -w --path=<path>`, and sets its entry with `git update-index`. It removes the entry of a deleted path. Then it writes the working-tree copy, or deletes it, only when the working-tree copy still equals the old staged copy (`git hash-object` of the working-tree file against the old entry; no file equals no entry). Else it leaves that copy, and prints a line that names it. When the work throws, `generate` stages nothing, and throws the same error. The steps after `generate` read the new staged tree. In a partial commit (`git commit --only`, `git commit <paths>`), `generate` writes the working-tree copies by the same rule, stages nothing, and throws an error that names the paths and the command that adds them to the commit. The host knows a partial commit by the name of its index, `next-index-<pid>.lock`. No git command says that a commit is partial, so this check by name stays.
9. **The index guard.** After the last step, the runner writes the tree of the index again. When that tree differs from the last staged tree that the steps judged, the commit stops: the index changed while the hook ran.
10. **The install.** An install starts from a copy of the full tree of the commit, without `.git` and `node_modules`. Thus the patch files, the `.npm-extension.*` file, the folders of `file:` dependencies and the workspace manifests are there, as in a clean checkout. The name of an install is the hash (sha256) of the lockfile and the `.npmrc` together. When the hook uses an install again, it copies again only the link targets that the commit has, and skips each target that the commit does not have (#4193). npm gets the tool environment. The install runs `npm ci --ignore-scripts` and then `npm rebuild <names>`, as ADR 0002 point 3 says.
11. **Locks.** The pre-push hook holds `build.lock` in the state folder from its first snapshot to its end, so one pre-push build runs at a time in a repo. Each hook holds `installs.lock` only while it installs or prunes. The pre-commit hook does not wait for a pre-push build.
12. **The API.** `Commit` has `tree()`, `changes()`, `touches(globs)`, `snapshot(options?)` and `generate(globs, work)`. `Push` has `remote`, `updates`, `tree(sha)`, `changes(update)` and `snapshot(sha, options?)`. `CommitMessage` does not change. The three are type-only exports: the runners build them. One loop replaces the three loops of `preCommit`, `prePush` and `commitMsg`. A new entry point, `@zukhruf/git-hooks/testing`, runs steps as each hook does, with a folder and an environment that the test gives, and gives the outcomes. These members are removed: `staged`, `files`, `blob`, `inSnapshot`, `modified`, `stage`, `nx`, `affected`, `root`, `push.inSnapshot` and `push.nx`. One lockfile parser, `src/npm/lockfile.ts`, replaces the private one of `src/snapshot/drift.ts:69-78`, and `LockfileSync` uses it too.

## Considered Options

- **Give a step the environment.** Each step must then remove the git variables itself, and one step that forgets reaches the repo (#3083).
- **Keep a snapshot of only the files for the pre-commit hook.** A tool that needs packages or git, such as nx and `npm ci`, cannot run there, and the two hooks keep two snapshots.
- **Stash the unstaged edits, as pre-commit and lint-staged do.** A stash changes the working tree of every session (ADR 0001).
- **Keep the install of the files that the code names.** Each new file that npm reads, such as the patch files of npm 12, needs a change of this package, and #4193 stays.
- **Judge with the packages of the working tree.** This is faster, because a commit that changes the lockfile does not wait for an install. Ezz chose the exact option: an install of the commit's own lockfile.
- **One snapshot for both hooks, a tree for each read, and the tool environment for each tool.** This option was selected.

## Consequences

- A pre-commit step that needs packages, such as `Format`, `DependencyChecks` and `LockfileSync`, waits for a snapshot. The steps that read the same tree share it. The time is not measured yet. The estimate is 0.6 to 2 s, from the probe of ADR 0002 (about 1 s for the files and the links of deepagents). The proof before the release measures it on zukhruf and text2sql.
- A commit that changes the lockfile or `.npmrc` waits for one full install. The pre-push hook then uses the same install, because its name is the same.
- `Sync` and `Codegen` judge the commit, not the working tree. An edit that is not staged no longer changes what they write. Each of them opens a private snapshot.
- A partial commit cannot take a generated file. The step fails, and names the files and the command.
- Each pre-commit snapshot writes one commit object that no ref holds. `git gc` prunes it after `gc.pruneExpire`, two weeks by default.
- A `git add` of a peer during a plain `git commit` stops the commit. Before, it went into the commit without a check.
- A tool in a pre-commit snapshot cannot read a file that is only in the working tree, such as `.env`. A pre-push build already had this limit.
- `Commit`, `Push` and `CommitMessage` are type-only exports. A repo tests its own steps with `@zukhruf/git-hooks/testing`. The callers change: the step and the test of `tools/readme-table` in zukhruf, the `DesignCheck` and the `Codegen` options of text2sql (`stage` takes globs, so `packages/client/src` becomes `packages/client/src/**`), and the `.husky/pre-push.ts` of sdk-it.
- This ADR supersedes the staging mechanism of ADR 0001, and its rule that `preCommit` reads the environment. It supersedes ADR 0002 point 3 for the files and the name of an install, the environment of npm, the `push.nx` and `Commit.nx` of point 4, and the one lock of point 5.
