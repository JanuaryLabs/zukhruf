# @zukhruf/eslint

ESLint rules and configs that several repos share. Each check is a named rule, such as `zukhruf/no-enum`. A repo's own config cannot silently erase it, and a repo can turn off one check by name.

The words in this document have one meaning each. See the glossary in [CONTEXT.md](./CONTEXT.md).

## The problem

The same rules were copied from repo to repo, and the copies broke in three ways:

1. **One key, many checks.** The hand-written bans (no enums, no test hooks, …) were entries of one rule, `no-restricted-syntax`. Flat config keeps one options list for each rule. A framework preset set `no-restricted-syntax` again, and every ban was gone.
2. **Globs that depend on the folder.** `nx lint` runs ESLint from the project folder. When a project's config re-exports the root config, a glob such as `apps/**` matches nothing.
3. **Partial options.** A project set `@nx/dependency-checks` with only its own `ignoredFiles`. The rule's defaults filled in the rest, and the shared policy was lost.

This package gives each check its own key, writes every glob as `**/…`, scopes by the linted file's path, and builds options with factories that add a repo's entries to the shared ones.

## Use it

You need ESLint 9.30 or later.

```sh
npm install --save-dev @zukhruf/eslint
```

Its peers are `eslint`, `@eslint/js`, `typescript-eslint`, `typescript`, `eslint-plugin-import-x`, `eslint-plugin-functional`, `jsonc-eslint-parser` and `yaml-eslint-parser`. `@zukhruf/eslint/nx` also needs `@nx/eslint-plugin`, `@zukhruf/eslint/react` needs `react` and the 3 plugins in [React](#react), `@zukhruf/eslint/react-native` needs `eslint-plugin-es-x`, and `@zukhruf/eslint/shadcn-strict` needs `@shadcn/lint`. npm installs the required peers for you; the ones a subpath needs are optional peers, which npm does not install, so add those to your devDependencies. With `legacy-peer-deps=true` in `.npmrc`, npm installs no peer, so add them all.

```js
// eslint.config.mjs
import { defineConfig } from 'eslint/config';

import zukhruf from '@zukhruf/eslint';

export default defineConfig({
  plugins: { zukhruf },
  extends: ['zukhruf/base', 'zukhruf/tests'],
});
```

Put framework configs (for example [`@zukhruf/eslint/react`](#react)) **before** the zukhruf configs. The package's own checks survive any order. But `base` also changes some third-party rules, for example it turns `@typescript-eslint/no-unused-vars` off, and a preset that comes later sets them again.

`base` turns on typed lint (`parserOptions.projectService`). Each linted TypeScript file must be in a tsconfig.

`@typescript-eslint/no-deprecated` reports a use of an API that its package marks `@deprecated`. The note names the replacement, so move to it while the change is small. A repo that must keep a deprecated API for a time sets the rule's `allow` option in its own config, in a block for the files that need it, with the reason. Give a name for a value of a plain type, such as a boolean option. Give `{ from: 'package', package, name }` for a type that the package declares.

`zukhruf/no-promise-field` reads each class field's type, so it also sees a promise behind an alias, in a type argument (`Map<string, Promise<X>>`, `Record<string, Promise<X>>`), in a union or an intersection, in a `PromiseWithResolvers`, or inferred from the initializer. It also looks inside a record that the project declares, such as `Map<string, { key: string; answer: Promise<boolean> }>`, up to four properties deep. It stops at a class, because the rule checks the fields of that class on their own, and at a library's type, because its promises belong to the library. A field that holds a function returning a promise is fine: that is a memoized function. A record of functions that settle a promise, `{ resolve, reject }`, is fine too: the caller keeps the promise. To wait until something has happened, use a state object or a one-shot latch. See [ADR 0006](./docs/adr/0006-no-promise-field-stops-at-the-class-boundary.md).

`zukhruf/no-phase-flag` reads each class field's type too. It reports a field that is a boolean, or that can be `undefined` or `null`, when code outside the constructor sets it. A callback that the constructor creates runs later, so its assignment counts as outside. Such a field records a phase, and every reader must know which phase holds. Push the fact as an event, wait on a one-shot latch, keep the phases in state objects, or ask the platform for the fact.

The rule also reports a `let` with the same types when a function that its function returns sets it. Such a function runs after the return, as a method runs after the constructor: a method of the returned object or class, a returned function, or the cleanup that a React effect returns. Thus `let closed = false; return { close() { closed = true; } }` is reported. A callback that the function calls before it returns, such as the callback of `map`, is not reported. A `let` that only its own function body sets is not reported.

A lazy memo is not a phase, so the rule does not report it. In a lazy memo, each write is `x ??= …` (for a field, the private `this.#x ??= …`), so the value never becomes empty again. Each read is the value of that `??=`, or comes after an `x ??= …;` statement at the top level of the same function body, as in `this.#x ??= build(); return this.#x;` or `return () => (value ??= read());`. A field or `let` that has `??=` writes but no read is a flag, and the rule reports it.

`zukhruf/no-captured-assignment` reports a nested function that assigns a `let`, a `var` or a parameter of an enclosing function. Such a variable is state that the closures share. Its value depends on the order in which they run (temporal coupling), and a reader of one function cannot see who changes it. The rule reports `=`, a compound assignment, `++`, `--`, a destructuring target and the target of a `for…of` or `for…in` loop. A nested function is an arrow function, a function expression, a function declaration, or a method or an accessor of an object or a class that the outer function defines. An immediately invoked function (IIFE) is reported too: return the value from it. A `new Promise((r) => { resolve = r; })` is reported: use `Promise.withResolvers()`. A counter in a callback, such as `items.forEach((item) => { total += item; })`, is reported: use `reduce()` or a `for…of` loop. A function that assigns its own variables is not reported, also a generator between its `yield`s. A module-scope `let` is not reported, because `functional/no-let` bans it. A lazy memo, `x ??= …`, is not reported, because it sets the value one time and never clears it. `||=` and `&&=` are reported, because they can set the value again. The rule reads the scope, not the types. Thus it does not report a member assignment (`this.#x = …`, `state.n += 1`) or a call that changes a captured object (`map.set()`, `list.push()`). A check of those needs the type of the object, to know if the call changes it. To share state, give it to an object that owns it, or return the value. The rule is off in `base` until the repos fix their findings ([ADR 0007](./docs/adr/0007-no-captured-assignment-is-off-until-the-repos-are-clean.md)).

`zukhruf/no-test-lifecycle-hooks` keeps the arrange and the teardown of a test in that test. A hook moves them out, so the reader does not see the full test, and the state that one test leaves can reach the next test. A per-test `t.after()` of node:test also moves the teardown out of the flow of the test. The rule reads the names of the scope, not only the text. It reports a hook from the Vitest, Jest or Mocha globals, and from an import, also under a different name (`import { after as cleanup }`). It reports a hook on `test` or `it` of node:test, or on its namespace (`test.after()`). It reports a hook on a test context: the first parameter of a test callback or a subtest callback of node:test, or a parameter of the type `TestContext`. A function of the file that has the name `after` is not a hook. Put the teardown in `try`/`finally`, or use `await using` with a disposable.

`zukhruf/no-own-module-mock` reports a module mock of code that the workspace owns: `vi.mock`, `vi.doMock`, `jest.mock`, `jest.doMock`, `jest.unstable_mockModule`, and `mock.module` or `t.mock.module` of node:test, given a relative path or a package of the same workspace, a subpath of it too, and Vitest's `vi.mock(import('./x.ts'))`. The packages of the workspace are the ones that the `workspaces` globs of the root `package.json` match. A mock of a path binds the test to where the code lives today. When the code moves, the mock stops applying, and the test still passes on the real code while it asserts nothing. Run the real module, and replace only what lies outside the workspace: HTTP with msw, a database with a real one, the data the module reads through its inputs. A mock of a package from outside the workspace, such as a native addon or `electron`, passes (#3619).

`zukhruf/one-test-runner` reports a test file that imports a test runner its project does not run. A project is a Vitest project when it has a `vitest.config.*`, or a `vite.config.*` that sets `test`: the rule of `@nx/vitest`, which `@zukhruf/nx/test` follows. There an import of `node:test` is reported. Every other project runs `node --test`, and there an import of `vitest` is reported. A node:test file that a Vitest `include` leaves out runs under no target, and a second runner in one project needs a second collection, reporter and target. Import from the runner of the project. An `import type` passes. The rule reads the vite config with the TypeScript parser and does not run it: a `test` whose value is a regex (the filter of a plugin) does not count, and a `test` that the config takes from another file is not seen (#3619).

`zukhruf/no-vitest-globals` reports `globals: true` in the `test` options of a config file (`*.config.*`: `vite.config.ts`, `vitest.config.mts`, `vitest.browser.config.ts`), also in an entry of `test.projects`. Vitest's globals put `describe`, `it`, `expect` and `vi` in scope with no import, so a test file reads names that nothing in it declares. Delete the option (`false` is Vitest's default), import the test APIs from `vitest` in each test file, and remove `vitest/globals` from the tsconfig types (`zukhruf/no-vitest-globals-types`, in the `tsconfig` config), so the type check rejects a test that uses one without an import. `@nx/vitest` writes `globals: true`; the `react-app` generator of `@zukhruf/nx` writes `globals: false`.

`zukhruf/no-raw-database-sync` reports `new DatabaseSync` of `node:sqlite`. Each such open sets up its connection in its own way: its busy timeout, its journal, and which errors mean that the file is missing or denied. `open(path, options)` of `@zukhruf/sqlite-open` takes the same options and does that setup in one place; a reader is `open(path, { readOnly: true })`. The rule follows the bindings of the file: a named import under any local name, a namespace or default import, and `require` or `import()` of `node:sqlite`. A type-only import constructs nothing, so the rule does not report it. Turn it off only where a package cannot depend on `@zukhruf/sqlite-open`, and write the reason beside the override.

`zukhruf/no-node-env` reports a read of `NODE_ENV`: `process.env.NODE_ENV`, with a computed key too, `import.meta.env.NODE_ENV`, a destructured `NODE_ENV`, and a read through a variable bound to the environment object (`const env = process.env`, `const { env } = process`, or `env` imported from `node:process`). `NODE_ENV` is `production` on a laptop, in CI and in production, so code that branches on it takes the same path everywhere. A behaviour that differs between setups reads its own setting, such as `ALLOWED_ORIGINS` or `LOG_LEVEL` ([NODE_ENV does not mean what you think it means](https://ezz.sh/posts/nodeenv-does-not-mean-what-you-think-it-means)). Tools still read `NODE_ENV`, and targets set it for them, so a write (`process.env.NODE_ENV = …`), a `delete`, a key of an env object for a child process, and `NODE_ENV` in a string, in the text of a template or in a comment pass.

`zukhruf/no-zod-to-json-schema` reports an import of `zod-to-json-schema`. The package reads the internals of Zod 3, so given a Zod 4 schema it returns `{}` and throws nothing: every tool schema built with it reaches the model empty. Zod 4 converts a schema itself with `z.toJSONSchema(schema)`.

`zukhruf/no-nock` reports an import of `nock`. msw is the one HTTP stub tool, and the checks of `zukhruf/tests` on stubs (`no-direct-msw-server`, `no-catch-all-msw-handler`) see only msw, so a nock stub escapes them. In a test, stub with `new Msw().intercept(...handlers)` from `@zukhruf/testing/msw`.

`zukhruf/no-ts-beside-dts` reports a `.ts` or `.tsx` file beside a `.d.ts` of the same base name, and a `.mts` beside a `.d.mts`. TypeScript then reads the declaration file as the declarations of the source file and stops loading it, so its globals and module augmentations disappear, and the type error lands in a file that uses them. A `.cts` keeps its `.d.cts`, so the rule skips it. Rename the declaration file, for example `env.d.ts` to `vite-env.d.ts`.

`zukhruf/no-reflect-get-chain` reports a `Reflect.get` on the result of another `Reflect.get`: nested, or through a variable set from one, also behind `Object(…)`, `as`, `satisfies` or `!`. Such a chain guesses the shape of a payload one field at a time. Type the payload from the real data and read its fields directly, with optional chaining; at a boundary that nothing else validates, parse it once with a schema. One `Reflect.get` with a dynamic key on a record passes.

`zukhruf/no-process-global-write` reports a write to `console`, in shipped code and in tests: an assignment to `console` or to one of its methods, also through `globalThis`, `window`, `global` or `self`, and `Object.assign`, `Object.defineProperty` or `Object.defineProperties` on it. One process shares one `console`. A patch changes what every module logs, and no call site shows that it is installed. In shipped code, pass a logger or an `enrich` option to the code that logs. In a test, use `t.mock.method(console, 'error')`: node:test restores it when the test ends. A read and a call pass. The rule does not yet report the other globals of a process, such as an assignment to `globalThis.fetch` or `process.stdout.write`, or `process.chdir` (#3753).

`zukhruf/no-silent-catch` reports a catch that drops the error, in shipped code and in tests: an empty `catch` block, also one that holds only a comment, and a rejection callback written in place in `.catch(…)`, or as the second argument of `.then(…)`, on a promise made in the same expression, whose body is empty or only gives back a literal fallback: `undefined`, `null`, `void 0`, a string, a number, `true` or `false`, or an array or object of these, such as `[]` and `{}`. `readdir(dir).catch(() => [])` reads EACCES as an empty folder. A callback that reads the error, such as `(error) => process.emitWarning(error)` or one that checks its code and rethrows the rest, a callback that calls a function or assigns, such as `() => this.#lose()`, a named handler such as `.catch(missing)`, and a callback that throws pass. A dropped error hides the failure from everyone: the test that should fail passes, and the log that should explain an outage is empty. Test cleanup that may fail runs in `await using` with `AsyncDisposableStack.defer(cleanup)`. When the test and the cleanup both fail, Node throws a `SuppressedError` that reports both, where a plain `finally` loses the test's own failure. Other code catches only the error it expects, by its code, and rethrows the rest. A promise kept in a variable and marked handled, `running.catch(() => undefined)`, passes: the code that awaits it still sees the rejection.

`zukhruf/no-unhandled-readline-error` reports `createInterface` of `node:readline` or `node:readline/promises` over a socket or another Duplex when nothing listens for `'error'` on the interface, in shipped code and in tests. readline emits the errors of its input again on the interface, so with no listener there a reset of the socket is an uncaught exception, even when the socket has its own listener. Linux resets a socket when its peer closes with data it did not read, and macOS does not, so the gap passes locally and fails CI: it turned CI red in #2573 and in #5265. The rule reads the type of the input: a `net.Socket`, a TLS socket, a `PassThrough` or another `Duplex` counts. A stream that the code only reads gets no such reset, so a child's `stdout` or `stderr`, a plain `Readable` and `process.stdin` are not reported, and neither is an input typed `any`. These pass: `.on('error', …)`, `.once`, `.addListener`, `.prependListener` or `.prependOnceListener` with `'error'` on the interface, chained (`createInterface(…).on('line', …).on('error', …)`) or on a variable or a class field that holds it; a function whose body does one of these with the parameter it is given, such as `leaveErrorsToClose(lines)` of `@zukhruf/mutex`, up to four functions deep; and `for await (… of lines)` or `lines[Symbol.asyncIterator]()`, because node:events turns the error into a rejection of the iterator. `once(lines, 'line')` of `node:events` does not pass: it removes its listener when the line comes. A function that only a `.d.ts` declares does not pass either, because the rule cannot read its body. See [ADR 0012](./docs/adr/0012-no-unhandled-readline-error-counts-an-input-the-code-can-write-to.md).

`zukhruf/require-warning-code` reports a call of Node's `process.emitWarning`, through `process`, `globalThis.process` or `node:process`, whose warning has no code, in shipped code and in tests: a string with no `code` in its options and no third argument, or an `Error` whose type has no `code` property, such as a raw failure. Without a code, a `'warning'` listener and `--disable-warning` cannot tell the warning from one of Node or of another package. It also reports an `Error` passed with a second argument, because Node ignores the type, the code and the options of an `Error` warning. It also reports an `Object.assign(…)` as the warning, such as `Object.assign(new Error(message, { cause: failure }), { name, code, detail })`, also when it sets a code, because a host cannot test that warning with `instanceof`. Declare a class for each type of warning that `extends Error` and sets its `name`, `code` and `detail`, and emit its instance: `process.emitWarning(new LeaderSelectorWarning(failure, { key }))`. undici does the same: `process.emitWarning(new RequestContentLengthMismatchError())` (`lib/dispatcher/client-h1.js:1220`), whose class sets its `name` and `code` (`lib/core/errors.js:183-189`). Write a string with `{ type, code, detail }` for a warning with no failure, such as a deprecation. A `process.emit('warning', …)` is not reported, and an `Object.assign(…)` kept in a variable before the call is not reported. See [root ADR 0010](../../docs/adr/0010-a-package-warning-names-its-type-code-and-subject-and-keeps-the-failure-as-its-cause.md) and [root ADR 0011](../../docs/adr/0011-a-package-warning-is-an-instance-of-its-own-class-which-the-package-exports.md).

`zukhruf/no-add-issue-string` reports `ctx.addIssue(…)` given a string: a literal, a template, or any value whose type is a string. In zod 4 the string form makes an issue without `continue: true`, so the `refine` and `superRefine` checks of every parent schema stop running, which zod 3 did not do. Pass an object: `ctx.addIssue({ code: 'custom', message })`.

`zukhruf/no-http-exception-factory` reports a function that only returns `new HTTPException(…)`. The function hides the status and the cause code behind a name, so the reader of the throw site cannot see what the client gets. Write `throw new HTTPException(status, { message, cause: { code, detail } })` in full at each throw site, also when many sites use the same code. A function with more statements than the `return`, such as a branch, stays. A lookup in the arguments of the exception does not change the result: put the lookup in a function of its own, and keep the exception at the throw site. A class method that returns the exception, such as `toHTTPException()`, also stays: each class translates its own error.

`zukhruf/no-catch-around-next` reports the `catch` of a `try` block that only calls `await next()` or `return next()`. Hono's `compose()` catches the error of each handler and gives it to the app's error handler. An app always has an error handler, because Hono adds a default one. Thus `next()` does not reject with an `Error`, and the `catch` never runs. Translate the error at the throw site, or read `c.error` after `next()`. The rule applies only to a file that imports `hono` or `hono/*`. In Koa, the same `catch` is the error handler that the Koa documentation shows.

`zukhruf/no-api-error-instanceof` reports `instanceof APIError` when `APIError` comes from `better-auth`, `better-auth/api`, `@better-auth/core/error`, `better-call` or `better-call/error`. The `APIError` of better-auth extends the `APIError` of better-call. Thus an `APIError` that better-call throws is not an instance of the better-auth class, and the error goes to the 500 path. Use `isAPIError(error)` from `better-auth/api`. It checks the two classes and the name of the error. An `APIError` from a different module, such as a generated client, is not reported.

`zukhruf/no-on-api-error-throw` reports `onAPIError: { throw: true }`. With this option, better-auth throws the error again before `onAPIError.onError` and before its own log. The router of better-call catches that error and makes a response from it, so the error handler of the app does not run, and no log shows a 4xx error. Log the error in `onAPIError.onError`.

`zukhruf/no-missing-dependency-build` reports a target of a `project.json` that runs a file with `node` or `tsx` when that file imports a workspace package that Node loads from the outputs of the package's `build`, and the target does not run after that build. Locally an old `dist` hides the gap; a clean checkout fails with `ERR_MODULE_NOT_FOUND`. The rule reads the commands of `nx:run-commands` and the package.json script of `nx:run-script`, and the test files of `node --test`, globs included. It follows relative imports from file to file, and the source of a workspace package whose entry is source, as with `--conditions=development`. It resolves each package's `exports` with the command's `--conditions` and Node's own. `import type` loads nothing, so it does not count. A target runs after the build when its `dependsOn`, as Nx resolves it from the cached project graph, reaches that build: `^build`, a target default in `nx.json`, or a target of the same project that depends on `^build`. Without a cached graph, as on a fresh clone, the rule checks nothing. The suggestion adds `"^build"` to `dependsOn`.

`zukhruf/no-missing-command-executor` reports a target of a `project.json`, or of the `nx` key of a `package.json`, that sets `options.command` or `options.commands` but neither `executor` nor a top-level `command`. Nx turns a top-level `command` into `nx:run-commands`, but it never reads `options` to pick an executor. A target with no executor becomes `nx:noop` when it has a `dependsOn`, and Nx drops it when it has none. Either way the target passes, and the command never runs. Set `"executor": "nx:run-commands"`, or move the command to the top-level `command`. A target default in `nx.json` or a target that an Nx plugin infers can give the executor, but the file does not show it, so the rule asks for the executor in the target itself. `nx:run-commands` merges with such a target.

`zukhruf/no-depends-on-project` reports a `dependsOn` entry that names projects: an object with `projects`, whether it gives names, globs or tags. Build order comes from the import graph: `^build` builds each project that this project imports, first. A named project is a build order written by hand, and it stays after the import is gone. Write `^<target>`, or import the project. `projects: "self"` and `projects: "dependencies"`, the old spellings of the same project and of `^`, pass. The string form `"<project>:<target>"` is not reported: a target name can have a colon, such as `format:check`, and only the project graph tells the two apart.

`zukhruf/no-timer-race` reports `Promise.race` between a promise and a timer in a test or a `src/testing` file. The timers are `delay`, `sleep` and `setTimeout` of `node:timers/promises` (also with `.then(…)` or `.catch(…)` after them) `new Promise` with a callback timer, and the `promise` of `Promise.withResolvers()` whose `resolve` a callback timer calls. A timer that rejects or throws (`.then(() => { throw … })`, `.then(() => assert.fail(…))`) fails the test with an error of its own and leaves the promise running (`matched`). A timer that resolves a marker, such as `delay(500, 'pending')`, ends the wait at a limit of its own, so the race is allowed only when each read of its result asserts that the result is the marker: `assert.equal(result, 'pending')`, `assert.deepEqual`, `assert.ok(result)` with a marker of `true`, `if (result !== marker) assert.fail(…)`, or a member of the result against the same member of an object marker. An assertion that the result is not the marker is a deadline in disguise (`deadline`). Any other read, and no read, is reported (`ownLimit`): await the promise through `untilAborted(promise, t.signal)` from `@zukhruf/async`, which ends at the test's limit. A function that returns such a race is checked at each call, in the linted file and, with type information, in another file, up to four functions deep. The message of an assertion and an argument of `assert.fail` do not count as reads. See [ADR 0013](./docs/adr/0013-no-timer-race-allows-a-race-against-a-timer-only-when-it-asserts-that-the-timer-won.md).

`zukhruf/no-missing-test-timeout` reports a command of a target, in a `project.json` or in the `nx` key of a `package.json`, that runs `node --test` or `tsx --test` without `--test-timeout`. A wait in a test ends on `t.signal` (`zukhruf/no-own-wait-limit`), and `t.signal` aborts only at the runner's `--test-timeout`. Node sets no limit, so a hung wait runs until the CI job limit. Add `--test-timeout=300000`, the limit that the test target of `@zukhruf/nx` sets. The rule reads the top-level `command` and the `command` and `commands` options of `nx:run-commands`; the test target that `@zukhruf/nx` infers is not in the file, and sets the flag.

`zukhruf/no-duplicate-nx-key` reports a top-level key of a `project.json` that the `nx` key of the `package.json` in the same folder also sets, such as `tags` or `targets`. Nx reads both files and merges them, so a reader of one file does not see the whole project. Keep each key in one file. The rule reads the `package.json` from disk and reports in the `project.json`.

`zukhruf/no-cross-project-paths` reports an entry of `compilerOptions.paths` whose target is in a different project from the tsconfig. Projects import each other by package name, and `nx sync` writes the project references. An alias reads the other project's source past its `exports` and its manifest, so the import works in the workspace and breaks where the package is installed. The project of a path is the nearest folder with a `project.json` or a `package.json`, as for islands; the project of the workspace root's `tsconfig.base.json` is the root. A target resolves from `baseUrl` when the file sets it, and from the tsconfig's folder otherwise; a `baseUrl` that comes through `extends` is not read. A target under `node_modules` is not a project. An alias inside one project, such as `#components/*` to `./src/components/*`, passes.

`zukhruf/no-vitest-globals-types` reports `vitest/globals` in `compilerOptions.types`. It declares `describe`, `it`, `expect` and `vi` as globals, so the type check accepts a test file that uses them with no import. Without it, the type check rejects a `describe` that the file does not import. Remove it, and delete `globals: true` from the Vitest config (`zukhruf/no-vitest-globals`). The `tsconfig.spec.json` that `@nx/vitest` writes lists it; the `react-app` generator of `@zukhruf/nx` removes it.

`zukhruf/no-generate-package-json` reports `generatePackageJson` in a target of `@nx/esbuild:esbuild`, in its `options` or in a `configurations` entry, when the workspace is a TS solution one. There the executor throws: "Setting 'generatePackageJson: true' is not supported with the current TypeScript setup". The project's own `package.json` is its deploy manifest, and the `prune-lockfile` target writes it with the lockfile into the output. The rule decides a TS solution workspace from the root files, as `isUsingTsSolutionSetup()` of `@nx/js` does: `workspaces` in the root `package.json` or `packages` in `pnpm-workspace.yaml`, a `tsconfig.json` that extends `./tsconfig.base.json` with `files` or `include` set only as an empty list, and a `tsconfig.base.json` with `composite`. A target with no `executor` and a target default in `nx.json` are not checked: only the project graph shows their executor.

`zukhruf/no-manual-workspace-install` reports a `steps` list, of a job or of a composite action, that uses `actions/setup-node` and runs `npm ci` itself. Such a job installs with the npm that Node bundles, which is older than npm 12: it ignores the `allowScripts` of `package.json` and runs every install script. Install the workspace with `JanuaryLabs/zukhruf/.github/actions/setup-workspace@main`, which installs the latest npm before `npm ci`. A job that uses `actions/setup-node` and does not run `npm ci`, such as one that installs a CLI with `npm install --global`, passes. No Nx project holds `.github`, so a repo lints these files in a step of its own: `npx eslint .github` in CI, and the `WorkflowChecks` step of `@zukhruf/git-hooks` before a commit.

[ADR 0009](./docs/adr/0009-project-config-rules-read-the-file-not-the-graph.md) says why these rules read the file and its folder, and which rules of the monorepo standard stay prose. [ADR 0010](./docs/adr/0010-workspace-rules-read-the-root-files-as-the-tool-does.md) says why `no-generate-package-json` and `manifest/no-globstar-workspace` read the root files as Nx and npm do.

`zukhruf/no-data-slot-restyle` reports a class that restyles a part of `@zukhruf/shadcn` from a parent through its `data-slot`, such as `[&_[data-slot=input]]:h-12`, `*:data-[slot=select-value]:text-primary` or `has-[[data-slot=checkbox]]:pl-2`. A host uses the kit as installed, and a look the kit lacks becomes a variant or a size of the kit. shadcn's own `no-restyle` reads the `className` of the component only, so a variant on a parent slips past it. The rule reads the strings of a `className` (or `…ClassName`) prop and of a `cn()`, `clsx()` or `cva()` call, and reports a slot only when the variant ends in a `:` of the same class and the kit renders that slot (`src/react/kit-slots.ts`, which a test checks against `packages/shadcn/src/components`). A slot of the host's own component, such as `**:data-[slot=content]:max-w-3xl`, and a CSS selector string, such as `querySelector('[data-slot=field-error]')`, are not reported. On 2026-11-20 it reported 14 slots in 11 class strings over every `.ts` and `.tsx` of meddit, factory, deepagents, text2sql, sdk-it and theagentlab, each a kit part. The `shadcn` config leaves it off, and [`@zukhruf/eslint/shadcn-strict`](#strict-rules-shadcn-strict) turns it on for a host that opts in (#5017).

### Options for a repo

Give repo-specific values as rule options. For example:

```js
{
  rules: {
    'zukhruf/no-bare-spawn': ['error', { roots: ['apps/desktop/src'] }],
  },
}
```

`roots` are folders relative to the workspace root. A rule finds the workspace root from the linted file: the nearest folder with `nx.json`, `pnpm-workspace.yaml`, or a `package.json` that declares `workspaces`.

A fact about the repo goes in `settings`, not in rule options. If you set a rule again, you replace its config's `files` and `ignores`. A setting changes no scope. For example, `env` reads the startup env schema from `src/startup.ts` in each project. If the schema is in a different file, give that file:

```js
{
  settings: { env: { startupFile: 'src/env.ts' } },
}
```

A relative `startupFile` is relative to the project of the linted file. `env` does not check test files or tool configs, such as `vite.config.ts`. A tool config runs at build time and has no startup env schema.

Each config registers its plugins for all files. Each rule keeps its own `files` and `ignores`. So you can set a rule in a folder that its config skips, such as `functional/no-let` in `src/testing`. You do not copy the config's globs.

To extend a `base` rule, use its factory. Do not declare the key again with only your entries: that replaces the base options.

```js
import { noFloatingPromises, noLet, noUnassignedImport } from '@zukhruf/eslint';

{
  rules: {
    'functional/no-let': ['error', noLet({ ignoreIdentifierPattern: ['^cached'] })],
    '@typescript-eslint/no-floating-promises': ['error', noFloatingPromises({ allowForKnownSafeCalls: [/* … */] })],
    'import-x/no-unassigned-import': ['error', noUnassignedImport({ allow: ['**/exceptions.ts'] })],
  },
}
```

React Router's loaders and actions throw `redirect()`, `replace()` (a `Response`) or `data()` (a `DataWithResponseInit`). React Router catches the value and renders it. So `react-router` sets `only-throw-error` again with these two types in its allow list. The allow list applies in every TypeScript file of the config, not only in a routes folder, because a loader helper, such as an auth gate, can live in a different folder. Use `react-router` together with `base`, because `base` gives the typed lint that the rule needs. To add more types, use the factory:

```js
import { reactRouterOnlyThrowError } from '@zukhruf/eslint';

'@typescript-eslint/only-throw-error': ['error', reactRouterOnlyThrowError({ allow: [/* … */] })]
```

## Nx: islands and module boundaries

`@zukhruf/eslint/nx` needs `@nx/eslint-plugin`.

```js
import nx from '@nx/eslint-plugin';
import { defineConfig } from 'eslint/config';

import zukhruf from '@zukhruf/eslint';
import island, { islandConstraint, moduleBoundaries } from '@zukhruf/eslint/nx';

export default defineConfig(
  nx.configs['flat/base'],
  {
    plugins: { zukhruf, island },
    extends: ['zukhruf/base', 'zukhruf/tests', 'island/recommended'],
    settings: { island: { libraries: ['packages/**/*.ts'] } },
  },
  {
    files: ['**/*.ts'],
    rules: {
      '@nx/enforce-module-boundaries': [
        'error',
        moduleBoundaries({
          depConstraints: [islandConstraint(['hono', 'hono/*'])],
        }),
      ],
    },
  },
);
```

An island is an Nx project tagged `layer:island`. Its tags come from its `project.json` or its `package.json` `nx.tags`. `island/recommended` has these rules:

- `island/no-generic-port` and `island/no-explicit-any` in islands.
- `island/no-process-env`, `island/no-console` and `island/jsdom-virtual-console` in islands and in the files that `settings.island.libraries` names. jsdom's default virtual console writes a page's errors to the host's `console.error`, so each `new JSDOM(…)` from `jsdom` sets `virtualConsole` in its options literal.
- `island/no-ambient-time` in islands and in the files that `settings.island.libraries` names. A library that waits on a timer or reads the time takes the clock from its caller, so that a test can give it a fake clock and move the time ([zukhruf root ADR 0004](../../docs/adr/0004-a-library-that-waits-takes-the-clock-as-an-input.md)). The rule reports `Date.now`, `performance.now`, `process.hrtime`, `AbortSignal.timeout` and `Temporal.Now`, called or as values (`now = Date.now`), `new Date()` and `Date()` with no argument, `setTimeout` and `setInterval` as calls or values (`promisify(setTimeout)`), the same through `globalThis` or `global`, an import of `setTimeout`, `setInterval` or `scheduler` from `node:timers` or `node:timers/promises`, and an import of `performance` from `node:perf_hooks`. A dynamic `import()` or `require()` of these modules, and a global that a destructure renames (`const { Date } = globalThis`), are not reported. It does not report a call on a clock (`clock.setTimeout(…)`), `globalThis` given as a clock (`delay(ms, { clock: globalThis })`, as an app or a real deadline does), `setImmediate` (a turn of the event loop, not a time), or `new Date(value)`. A name that a local binding shadows passes.
- `island/dependency-checks` on each island's `package.json`, with `dependencyPolicy()`.

`moduleBoundaries()` and `dependencyPolicy()` add your entries to the shared options:

```js
'island/dependency-checks': ['error', dependencyPolicy({ ignoredDependencies: ['electron'] })]
```

### Every other manifest

`manifest/recommended` checks the `package.json` of every project that is not an island. What a manifest must declare depends on the project's shape:

- A **bundled** project is an application whose build inlines the workspace packages it imports. Their manifests are not there when it is deployed, so its own manifest declares every npm package that the modules its bundle loads import. Workspace packages themselves are not demanded.
- Every other project is **unbundled**. It declares what its own code imports.

The rule reads the build target as Nx resolves it: `project.json`, the target defaults in `nx.json`, and the targets that Nx plugins infer. An application bundles unless its build compiles with tsc, is `nx:noop`, or is esbuild with `bundle: false`. tsc emits one file for each source file and keeps each import. The rule counts `@nx/js:tsc` and the `tsc --build` target that the `@nx/js/typescript` plugin infers.

The rule follows the bundle's imports, not the project edges ([ADR 0014](./docs/adr/0014-a-bundled-apps-manifest-follows-its-import-graph-not-the-project-edge.md)). It starts at the app's files that Nx's check reads and follows each import: a relative path to its file, a workspace package through the subpath of its `exports` (or `main` and `module`), and a `#x` through the importing package's `imports`. A static import, a type-only import, `export … from`, a literal `import()` and `require()` all count. Nx's check then skips the files that the bundle never loads. So an app that imports `@acme/evidence` and `@acme/evidence/pubmed` does not declare `yauzl`, which only `@acme/evidence/dailymed` imports. When the rule cannot follow an import, the whole project counts, as Nx counts it: a subpath with no source file, a `#x` or a relative path that leads to no file, a bare name that is no npm package, builtin or workspace package (such as a tsconfig `paths` alias), `import.meta.glob`, `new URL('…', import.meta.url)`, an `import()` of anything but one string literal, and a workspace project that Nx sees in a file and that no followed import accounts for. The rule reads Nx's file map through `@nx/devkit/internal`, which has the functions it needs from Nx 23.2. On an older Nx, every file of an inlined package counts.

An esbuild app can name workspace packages in `external`. Its build does not inline those packages, so they come from `node_modules` when the app runs. When the app imports one of them, it is unbundled, and its manifest declares them. Its manifest does not declare the workspace packages that its build still inlines. The rule reads the list that Nx gives esbuild: `external` and `esbuildOptions.external`, less the entries in `excludeFromExternal`. A `*` in an entry is esbuild's wildcard, as in `@acme/*`.

An app, or a workspace package that it imports, can name a project in `implicitDependencies` so that Nx builds that project first. The code does not import it, so the bundle holds none of its code. Nx's check follows such an edge as it follows an import. So the rule does not demand an npm package that only such a project imports. For example, a web imports the sdk-it client of `@zukhruf/nx`, and the client names its backend: the web does not declare `hono`. A package that the app's imports also pull in stays demanded. The rule passes these packages to Nx's check as `ignoredDependencies`, so the check also does not report one as obsolete when the app's manifest declares it.

A `testing/` folder holds test support, so the rule does not check its imports. A package can also ship a testing subpath to its consumers. So the rule checks a `testing/` folder when the manifest publishes it: an `exports` target or a `files` entry has a `testing` segment, an `exports` target has a `*`, or a `files` entry names the folder or a folder that holds it, such as `src`. For a bundled project, the rule applies the same decision to each workspace package that it inlines, and a `testing/` folder inside a nested project follows the manifest of that project.

Nx's check follows the imports of all workspace packages, or of none. So when an app inlines some workspace packages and names others in `external`, the rule does not check the npm imports of the inlined packages.

```js
import island, { manifest } from '@zukhruf/eslint/nx';

export default defineConfig({
  plugins: { island, manifest },
  extends: ['island/recommended', 'manifest/recommended'],
  rules: {
    'manifest/dependency-checks': [
      'error',
      {
        ignoredDependencies: ['electron'],
        projects: {
          'apps/website': { ignoredDependencies: ['@radix-ui/react-slot'] },
        },
      },
    ],
  },
});
```

The rule decides each manifest's options itself, so your options add to the shared policy and never replace it. `projects` keys are folders relative to the workspace root. Like Nx's own rule, it needs the project graph that `nx` caches; without it, the rule checks nothing. It needs `@nx/devkit`, which `@nx/eslint-plugin` installs.

`manifest/recommended` also has `manifest/no-truncated-description`. The npm registry keeps only the first 255 characters of a package's `description`. `npm view` and the npm search do not show the rest. The rule reports a `description` that is longer than 255 characters. It does not check a manifest with `"private": true`, because npm does not publish it. Put the key fact in the description, and put the details in the README.

`manifest/recommended` also has `manifest/provenance-repository`. With npm provenance (`--provenance`, or `NPM_CONFIG_PROVENANCE=true` in CI), the npm registry refuses a publish whose `repository.url` does not match the GitHub repository of the workflow, and a manifest without `repository` fails with `"repository.url" is ""`. The rule reports a `package.json` that npm can publish and that has no `repository`, or a `repository` with no non-empty `url`. A string `repository` passes, because `npm publish` turns it into `{ "type": "git", "url": ... }`. A `package.json` below the workspace root also names its folder, relative to the workspace root, in `repository.directory`, so the npm page links to the package. The rule does not read the Git remote, so it does not check which repository the URL names. It does not check a manifest with `"private": true`, or one without a string `name` and `version`, because npm publishes neither.

`manifest/recommended` also has `manifest/no-other-test-runner`. It reports a test runner other than node:test and Vitest in the `dependencies`, `devDependencies`, `optionalDependencies` or `peerDependencies` of a `package.json`: each runner that `zukhruf/no-other-test-runner` bans as an import (`jest`, `@jest/globals`, `mocha`, `jasmine`, `ava`, `tap`, `tape`, `uvu`), the `@types/*` package of each unscoped one, and `jest-expo`. A Jest or Mocha test calls `describe`, `it` and `expect` as globals, with no import, so the import ban does not see it; the manifest that installs the runner, or the types of its globals, does. Use node:test, or Vitest in a Vite app.

`manifest/recommended` also has `manifest/no-root-script`. It reports each script of the workspace root `package.json` other than `prepare`. Each command of the workspace runs as an Nx target, so Nx knows its inputs, caches it and orders it. `prepare` stays: npm runs it after `npm install`, and it installs the Git hooks. The rule checks only a `package.json` whose folder is a workspace root; a `package.json` outside any workspace has no Nx targets to move to.

`manifest/recommended` also has `manifest/no-globstar-workspace`. It reports each `workspaces` glob with a `**` segment. npm matches workspaces without `dot`, and a `**` makes a workspace of each folder below it that holds a `package.json`: an untracked folder, or the `dist/package.json` that a build writes. List each project folder with a single `*` (`apps/*`, `packages/*`, `packages/sqlite/*`), and name a dot folder by its path, such as `.github/actions/*`. A negated glob such as `!packages/**/dist` takes folders out, so it passes. The rule does not check that the globs cover every project: a walk of the tree also sees the folders that Git does not track.

`manifest/recommended` also has `manifest/nx-family-pinned`. `nx` ships a native addon, and each `@nx/*` package depends on `nx` at its own version. When two versions are asked for, npm nests a second `nx`, with its own addon, under the package that asked. So the rule allows one version of the nx family:

- In the workspace root `package.json`, every `nx` and `@nx/*` entry in `dependencies`, `devDependencies` and `optionalDependencies` has an exact version, with no range operator, and that version is the version of the root's `nx`.
- Every other `package.json` names `nx` and `@nx/*` packages only in `peerDependencies`, with any range.

The workspace root is the nearest folder with an `nx.json`, a `pnpm-workspace.yaml`, or a `package.json` that declares `workspaces`. A `package.json` outside any workspace is a root itself. The rule runs on each `package.json` that ESLint lints, so the root's clause runs only where the root `package.json` is linted.

## React

`@zukhruf/eslint/react` gives the configs that the React community maintains. The package adds no rule of its own to them and changes no severity; it sets the options of one rule, below. Use it in the `eslint.config.mjs` of a React project. Put it first, and then the root config, as before:

```js
import react from '@zukhruf/eslint/react';

import baseConfig from '../../eslint.config.mjs';

export default [...react, ...baseConfig];
```

The configs apply only to TypeScript files, the files to which `zukhruf/base` gives type information. Thus they do not lint the `package.json` or the other files of a project.

It gives these configs, in this order:

1. `recommended` of `eslint-plugin-jsx-a11y-x`: the accessibility rules. This plugin is the maintained fork of `eslint-plugin-jsx-a11y`, and its peer range includes ESLint 10.
   `label-has-associated-control` keeps its severity and `assert`, and gets two options: `controlComponents` names the controls of `@zukhruf/shadcn` that a wrapping `<label>` labels (`Checkbox`, `Switch`, `RadioGroupItem`, `Slider`, `Input`, `Textarea`, `SelectTrigger` and the other inputs), and `depth` 4 reaches the text of shadcn's choice card, a `<label>` around a `Field` with a `Checkbox`.
2. `flat.recommended` of `eslint-plugin-react-hooks`: the rules of the React team.
3. `recommended-type-checked` of `@eslint-react/eslint-plugin`: the React rules, for example `@eslint-react/no-missing-key`. The rules use type information. `zukhruf/base` gives it, because it sets `projectService`.
4. `disable-conflict-eslint-plugin-react-hooks` of `@eslint-react/eslint-plugin`: it turns off the 12 rules of `eslint-plugin-react-hooks` that `@eslint-react/eslint-plugin` also has.
5. `strict` of `eslint-plugin-react-you-might-not-need-an-effect`: its 10 rules report an effect that React does not need, for example state derived from props or an event handler run from an effect. `strict` makes each rule an error.

Thus `@eslint-react/eslint-plugin` owns the hook rules, for example `@eslint-react/rules-of-hooks` and `@eslint-react/exhaustive-deps`, and ESLint reports each problem one time. This is the path of the eslint-react guide "Migrating from eslint-plugin-react-hooks". `eslint-plugin-react-hooks` adds only its 4 React Compiler rules: `preserve-manual-memoization`, `incompatible-library`, `config` and `gating`. Each rule of the first 4 configs has the severity that its plugin ships.

The rules of zukhruf for the components of `@zukhruf/shadcn` are not in this export. They are in the config [`zukhruf/shadcn`](#shadcn).

Install the 4 plugins in the React workspace:

```sh
npm install --save-dev @eslint-react/eslint-plugin eslint-plugin-jsx-a11y-x eslint-plugin-react-hooks eslint-plugin-react-you-might-not-need-an-effect
```

They are optional peers of this package. With the peers, npm writes the lockfile edges from `@zukhruf/eslint` to the 3 plugins, so a lint input on `@zukhruf/eslint` also hashes the plugins.

`react` is also an optional peer, because the React version changes the lint result. `@eslint-react/eslint-plugin` reads the version of the `react` package that resolves from the folder where ESLint runs. `nx lint` runs ESLint in the project folder, and a hoisted `react` resolves from there. With the peer, a lint input on `@zukhruf/eslint` also hashes the React version.

## shadcn

The config `zukhruf/shadcn` checks the use of `@zukhruf/shadcn`, the kit of shadcn/ui components on Base UI. A project that imports the kit uses it with the React configs:

```js
import zukhruf from '@zukhruf/eslint';
import react from '@zukhruf/eslint/react';

import baseConfig from '../../eslint.config.mjs';

export default [...react, ...baseConfig, ...zukhruf.configs['shadcn']];
```

`extends: ['zukhruf/shadcn']` gives the same config. The rule ids keep the `zukhruf/` prefix, for example `zukhruf/no-as-child`.

`zukhruf/no-native-control` reports a control whose widget the browser draws where the kit has its own: `<select>` and `NativeSelect`, and an `<input>` or an input of the kit (`Input`, `InputGroupInput`, `SidebarInput`) whose `type` is `date`, `datetime-local`, `checkbox`, `radio` or `range`. It reads a `type` that is a string literal, or each literal branch of a conditional. Its message names the component of the kit to use, for example `Popover` with `Calendar` for a date. The browser's widget does not follow the theme, the direction or the language of the app.

The config also sets `settings.zukhruf.shadcn`, in a block with no `files`, so it is set in every file that the config covers. `zukhruf/require-shadcn-config` of `base` reports an import of `@zukhruf/shadcn` in a file without the setting, and the message names the config to add. Thus a project that spreads only `@zukhruf/eslint/react` cannot miss the kit rules. A repo does not set `settings.zukhruf.shadcn` itself: that silences the guard and turns on no kit rule.

`react` is the old name of this config. `zukhruf.configs['react']` and `extends: ['zukhruf/react']` still give it, and each read prints a `DeprecationWarning` (`ZUKHRUF_ESLINT_REACT_CONFIG`). The name goes away in the next release. See [ADR 0011](./docs/adr/0011-the-kit-rules-are-the-shadcn-config-and-base-guards-them.md).

### Strict rules: shadcn-strict

`@zukhruf/eslint/shadcn-strict` holds the strict rules for a host of the kit: the kit is used as installed, and a look the kit lacks goes into the host's theme or stylesheet, keyed on the `data-slot` the component writes, not into `className`. A host spreads it after the `shadcn` config once it has fixed its hits, so an update of this package fails no host that has not opted in:

```sh
npm install --save-dev @shadcn/lint
```

```js
import zukhruf from '@zukhruf/eslint';
import react from '@zukhruf/eslint/react';
import shadcnStrict from '@zukhruf/eslint/shadcn-strict';

import baseConfig from '../../eslint.config.mjs';

export default [
  ...react,
  ...baseConfig,
  ...zukhruf.configs['shadcn'],
  ...shadcnStrict,
];
```

`@shadcn/lint` is an optional peer: only this export loads it, so a host that does not opt in does not install it.

It turns on, at `error`, on `.tsx` and `.jsx`, `zukhruf/no-data-slot-restyle` and the six rules of shadcn's own linter, [`@shadcn/lint`](https://github.com/shadcn-ui/lint), under its `shadcn/` prefix:

- `no-restyle` allows `layout` (margin, width, position) on every component, and `layout` and `spacing` on the kit's layout containers, where a host spaces its own content: `Field`, `FieldGroup`, `CardContent`, `CardHeader`, `CollapsibleContent`, `SidebarHeader`, `SidebarContent`, `SidebarGroup`, `SidebarMenu`, `TabsContent`, `DropdownMenuLabel` and `InputOTPGroup`.
- `no-arbitrary-values` has no allow-list. An off-scale size rounds to Tailwind's scale; a CSS-variable setter such as `[--header-height:61px]` moves into the host's stylesheet, and a grid template becomes a named `@theme` value.
- `no-raw-colors`, `no-unknown-classes`, `no-inline-styles` and `require-static-classes` keep their defaults.

The rules are strict. Fix each flagged line in code: do not disable the rule on the line, also with a reason, and add no exception in the config. A value known only at runtime goes in a `--*` custom property in `style`, and a class reads it: ``style={{ '--drag-width': `${width}px` }}`` with `w-(--drag-width)`.

It sets `settings.shadcn`, which names the kit for the linter: `componentImports: ['^@zukhruf/shadcn$']`, so the components of the package are the design system, and `themeImports: ['^@zukhruf/shadcn/']`, so the tokens of the kit's stylesheets that the host's theme imports count as the host's own. The linter reads each component's variants and sizes from the kit's built `dist`.

The kit's own source styles its parts, so a repo that lints the kit and opts in turns these rules off for the kit's source. See [ADR 0011](./docs/adr/0011-the-kit-rules-are-the-shadcn-config-and-base-guards-them.md#the-strict-rules-are-opt-in).

## React Native: Hermes

`@zukhruf/eslint/react-native` needs `eslint-plugin-es-x`. es-x 10 needs ESLint 10.6 or later; on ESLint 9, install `eslint-plugin-es-x@9`. `hermes/recommended` checks the code that ships in the app, and leaves tests, config files and scripts alone, because those run in Node:

- the `Intl` APIs Hermes does not have: es-x's `no-intl-displaynames`, `no-intl-durationformat`, `no-intl-listformat`, `no-intl-locale`, `no-intl-pluralrules`, `no-intl-relativetimeformat` and `no-intl-segmenter`;
- Node's built-in modules: `import-x/no-nodejs-modules`;
- `hermes/no-missing-console`: `console.clear`, `dir`, `dirxml`, `profile`, `profileEnd` and `timeLog`, which React Native release builds do not have, and `console[name]` with a computed name.
- `hermes/no-compact-notation`: `notation: 'compact'` and `compactDisplay` in the options of `Intl.NumberFormat`, which Hermes on iOS ignores: `format(44000)` gives `44,000`, not `44K`. Build the short form yourself.

```js
import hermes from '@zukhruf/eslint/react-native';

export default defineConfig({
  plugins: { zukhruf, hermes },
  extends: ['zukhruf/base', 'hermes/recommended'],
});
```

If the app installs an npm polyfill that has a Node module's name, allow it: `'import-x/no-nodejs-modules': ['error', { allow: ['buffer'] }]`.

## Modern Node

Node and JavaScript add APIs that replace older code. `modern-node/recommended` reports the older code on each lint run, so a repo learns about a replacement and no person has to look for it.

The config is for code that runs on Node. Keep a browser bundle out of it. When a project has its own `eslint.config` that spreads the root config, ESLint resolves each glob from the folder of the project, so `ignores` in the root does not apply there. In that repo, add this config to the config of each Node project. Check the result with `eslint --print-config` in a browser project. `Error.isError` and `Uint8Array.prototype.toHex` do not work in all the browsers that people use, so the fix can throw in a browser.

`@zukhruf/eslint/modern-node` needs `@e18e/eslint-plugin` and `eslint-plugin-unicorn`. `eslint-plugin-unicorn` 80 needs ESLint 10.4 or later.

```js
import modernNode from '@zukhruf/eslint/modern-node';

export default defineConfig({
  plugins: { zukhruf, 'modern-node': modernNode },
  extends: ['zukhruf/base', 'modern-node/recommended'],
});
```

The config turns on:

- `modern-node/crypto-hash`: `createHash(algorithm).update(data).digest(encoding)` becomes `hash(algorithm, data, encoding)` of `node:crypto`. `createHash` stays for several updates and for a stream. When the file already has a different `hash`, the rule reports and does not fix. Rename that `hash`, and the fix applies.
- `modern-node/timers-promises-set-immediate`: `new Promise((resolve) => setImmediate(resolve))` becomes `setImmediate()` of `node:timers/promises`. The fix uses the import of `node:timers/promises` that the file has, or adds `setImmediate` to it. When the file also calls the global `setImmediate`, the rule reports and does not fix, because the import would capture those calls. Import `setImmediate` of `node:timers/promises` under another name, such as `nextTurn`, and the fix applies. A value, as in `setImmediate(resolve, 'pending')`, is left alone.
- e18e's `modernization` config, without `prefer-array-fill`, `prefer-array-to-spliced` and `prefer-spread-syntax`;
- `e18e/prefer-exponentiation-operator` and `e18e/prefer-flatmap-over-map-flat`;
- `unicorn/no-new-buffer`, `prefer-abort-signal-any`, `prefer-array-from-async`, `prefer-error-is-error`, `prefer-group-by`, `prefer-import-meta-properties`, `prefer-iterator-helpers`, `prefer-promise-with-resolvers`, `prefer-set-methods`, `prefer-uint8array-hex` and `prefer-url-search-parameters`;
- `unicorn/prefer-dispose`, for TypeScript files only. It needs type information, which `zukhruf/base` gives. A repo that lints TypeScript with no type information must turn it off.

`unicorn/prefer-uint8array-hex` needs Node 26. Code that runs on Node 24 turns it off: `'unicorn/prefer-uint8array-hex': 'off'`.

Run `eslint --fix` first. The e18e fixers do not read types, so `[...set].sort()` becomes `set.toSorted()`. Run the type check after the fix, and read each change to a `.mjs` file. [ADR 0008](docs/adr/0008-modern-node-is-a-namespace-and-a-config.md) gives the measurement, and it tells why each other rule is off.

## Development

The workspace lints itself with this package's source: the root `eslint.config.mjs` imports `packages/eslint/src/index.ts`. Nx loads that config while it builds the project graph, before anything is built. A rule edit applies on the next lint.

```sh
npx nx run eslint:test        # builds, then runs the rule and composition tests
```

The composition tests run the real ESLint CLI on temporary workspaces. They load the built package, which is what consumers install.

### Add a check

A check is a rule under its own key ([ADR 0001](./docs/adr/0001-one-key-per-check.md)). Before you write a visitor by hand, use the builders in `src/authoring/`:

- `importBanRule()` bans packages and their subpaths. It reports static imports, re-exports and literal dynamic imports, type-only ones included.
- `selectorRule()` reports each node that one of its esquery selectors matches. Its `message` is plain text: a `{{ … }}` in it, such as a JSX object literal, is not an ESLint placeholder. The substring operator `*=` never matches a Literal's `value`, so write a regex selector (`[value=/…/]`). A `:has(> A > B)` with more than one level never matches, so nest it: `:has(> A:has(> B))`.
- `scopedRule()` turns a rule on only for the files that its function accepts. Build that function from `isTestFile()`, `inRoots()` and `matchesAnyGlob()` in `path-scope.ts`. A rule finds its scope from the linted file, not from a config glob ([ADR 0002](./docs/adr/0002-scope-from-the-linted-file.md)).
- `ast.ts` has the type guards for a visitor: `isAstNode()`, `isType()` and `identifierName()`.

Folders that differ from repo to repo are `roots` options. A fact about the repo is a repo setting. A rule whose options a repo extends gets an option factory ([ADR 0004](./docs/adr/0004-option-factories.md)).

1. Put the rule in the folder of the subject that it checks, such as `src/async-values/` or `src/imports/`. The file exports the rule as its default.
2. Put `<rule>.test.ts` next to it. Use `typescriptRuleTester()` from `src/testing/rule-tester.ts`, or `typedRuleTester(root)` when the rule reads types. Call `run()` inside a node:test `test()`.
3. Add the rule to the `rules` map in the `config.ts` of its concept, and turn on `zukhruf/<rule>` in that concept's config. A new concept also goes into the `concepts` list in `src/plugin.ts`. The composition tests fail when not exactly one config turns on a rule, when a config sets a repo-owned rule, or when a shipped glob does not start with `**`.
4. Add the rule to its concept's row in the Configs table. Below the table, write a paragraph that tells why the check exists.
5. Fix the findings that the new rule reports in the other packages of this workspace, in the same commit (for example 20b34e0). The workspace lints itself with this source. When a package must keep its code, turn the rule off for those files in the root `eslint.config.mjs`, with a comment that tells why (for example 495f19d).
6. Run `npx nx run eslint:test` and `npx nx run eslint:typecheck`.
