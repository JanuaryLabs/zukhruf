# An image build sends a tar context to BuildKit through the Engine API, and the caller pulls each base image first

Status: accepted by Ezz on 2026-11-23 ("Accept") for the API and the builder. After a measurement of the npm packages, Ezz ruled on 2026-11-23 for the three parts: "modern-tar; write the other two (Recommended)". Thus `modern-tar` writes the tar, and the package writes the `.dockerignore` matcher and the BuildKit trace reader. The owner ruled on 2026-11-23 that the build goes into this package first: "Fix in docker first". The code is not written, and no probe of an engine ran for it.

[ADR 0001](./0001-the-client-speaks-the-engine-api-not-the-docker-cli.md) and [ADR 0003](./0003-the-package-leads-and-the-repositories-change.md) left image builds with the Docker CLI, because "a build with BuildKit needs its session protocol". `@zukhruf/testing` [ADR 0027](../../../testing/docs/adr/0027-a-sql-server-with-full-text-search-runs-an-image-that-the-fixture-builds-on-the-engine-from-the-plain-image.md) (accepted) needs a build with no CLI: its SQL Server fixture builds a Full-Text Search image on the engine, from a Dockerfile of one file, with three build arguments and `linux/amd64`, also on an arm64 Docker Desktop and on an SSH engine. Today the fixture can only pull (`#creating` in `testbed.ts`).

The facts:

- **The request.** [ImageBuild](https://docs.docker.com/reference/api/engine/version/v1.47/#tag/Image/operation/ImageBuild), `POST /build`, takes the build context as its body: "A tar archive compressed with one of the following algorithms: identity (no compression), gzip, bzip2, xz". Its query has `dockerfile` (default `Dockerfile`), `t` (one or more `name:tag`), `buildargs` and `labels` (JSON maps of strings), `platform` (`os[/arch[/variant]]`), `target`, `nocache`, `pull`, `rm` and `forcerm` (intermediate containers of the classic builder), and `version`: "`1` is the first generation classic (deprecated) builder … (default)", "`2` is BuildKit" ([`api/swagger.yaml` of Moby at 8b0c45e42959](https://github.com/moby/moby/blob/8b0c45e42959/api/swagger.yaml)). "The build is canceled if the client drops the connection." The engine reads the body and writes the progress at the same time (`EnableFullDuplex` in [`build_routes.go`](https://github.com/moby/moby/blob/8b0c45e42959/daemon/server/router/build/build_routes.go)).
- **The progress.** The answer is newline-delimited JSON of `BuildInfo`: `stream`, `status`, `errorDetail` and `aux`. BuildKit gives the image as `{"id":"moby.image.id","aux":{"ID":"sha256:…"}}` (`daemon/internal/builder-next/builder.go`); the classic builder gives the same `aux` with no `id` (`emitImageID` in `daemon/builder/dockerfile/builder.go`). The classic builder writes the output of its steps as `stream` text. BuildKit writes it only as `{"id":"moby.buildkit.trace","aux":"<base64>"}`: a protobuf `StatusResponse` with `vertexes` (field 1: `digest` 1, `name` 3, `error` 7) and `logs` (field 3: `vertex` 1, `msg` 4) ([`control.proto` of BuildKit at f272b8657b45](https://github.com/moby/buildkit/blob/f272b8657b45/api/services/control/control.proto)).
- **BuildKit with no session.** With `version=2` and a tar body, Moby serves the body to BuildKit as an HTTP context (`reqBodyHandler` in `builder-next/builder.go`), so the context needs no session. A pull from a registry does: the resolver asks the session for credentials, also for an anonymous pull, and fails with `no active sessions`. A base image that is already on the engine builds ([testcontainers-node#571](https://github.com/testcontainers/testcontainers-node/issues/571), comment of 2024-06-12; [dockerode#601](https://github.com/apocas/dockerode/issues/601)). Secrets, `--mount=type=ssh` and credentials need the session.
- **The classic builder.** Docker deprecated it in v23.0 for Linux images, with no removal release ([Deprecated features](https://docs.docker.com/engine/deprecated/)). On the containerd image store, the default of Docker Desktop since 4.34, a classic build with a platform that is not native fails or uses the wrong platform ([moby#47823](https://github.com/moby/moby/issues/47823), open). That is the case of the fixture: `linux/amd64` on an arm64 Docker Desktop.
- **Node.js.** Node 26 has no tar, protobuf or `.dockerignore` module ([ADR 0006](./0006-files-move-through-the-archive-requests-not-through-exec.md)). Today this package writes ustar with PAX itself (`src/tar-writer.ts`), for directories and regular files only, as one `Uint8Array`, and reads tar with `src/tar-reader.ts`. `node:zlib` gives gzip, which the engine accepts. `fs.promises.readdir({ recursive: true, withFileTypes: true })`, `lstat` and `readlink` walk a folder. `path.matchesGlob` exists, but its rules are not the rules of `.dockerignore` (`moby/patternmatcher`: Go `filepath.Match`, `**`, `!` exceptions, the last match wins).
- **The layer permits npm packages.** This package is a base package, and root [ADR 0001](../../../../docs/adr/0001-zukhruf-is-a-layered-standard-library.md) says: "A base package imports Node.js, other base packages and npm packages". The layer rule of the root `eslint.config.mjs` constrains only workspace projects. Today the package depends only on `@zukhruf/async` and `@zukhruf/ssh`; that is a choice, not a rule.
- **The tar of the CLI.** The Docker CLI tars a context with `moby/go-archive`: PAX format, owner 0:0, the mtime cut to seconds, a symbolic link as a link, and no entry for the root `.` ([`archive.go` at ca576ae5ca67](https://github.com/moby/go-archive/blob/ca576ae5ca672ebaaefb0dac19edca693ed3e66b/archive.go), lines 261-273, 371-385, 405-408, 887). A probe wrote a folder of 10 entries in that way with Go `archive/tar` (a file name of 124 bytes, a link target of 110 bytes, a symbolic link with no target, modes 0644 and 0755, a non-ASCII name) and compared each candidate field for field.

## Decision

`docker.images.build(context, options)` builds an image on the engine with BuildKit through `POST /build`, and reads the progress to its end, as `pull()` does. Its name follows `images.pull()`, `push()` and `load()` of this package, `images.build()` of docker-py and `buildImage` of dockerode.

```ts
type BuildFile =
  | { path: string; data: string | Uint8Array; mode?: number }
  | { path: string; directory: true; mode?: number };

type BuildContext =
  | { directory: string } // a folder on this machine, filtered by its .dockerignore
  | { files: BuildFile[] } // files in memory
  | { archive: ReadableStream<Uint8Array> | Uint8Array }; // a tar that the caller made

build(
  context: BuildContext,
  options?: CancelOptions & {
    dockerfile?: string; // the path in the context; default 'Dockerfile'
    t?: string | string[];
    buildargs?: Record<string, string>;
    labels?: Record<string, string>;
    platform?: string; // 'linux/amd64', as pull() takes it
    target?: string;
    nocache?: boolean;
  },
): Promise<EngineApi.ImageID>; // { ID: 'sha256:…' }
```

1. **The builder is BuildKit, with no session.** The call sends `version=2`. It sends no `pull` and takes no `auth`: a pull inside the build needs the session. The caller pulls each `FROM` image with `images.pull()` first, with `auth` when it needs one, as the fixture of ADR 0027 already pulls `BASE` to read its label.
2. **The options have the names of the query.** `t`, `buildargs`, `dockerfile`, as ADR 0001 decides: no second name for a field. The package encodes the JSON maps. `rm` and `forcerm` are out, because BuildKit makes no intermediate containers. More fields come one by one from the reference, as `HostConfig` does ([ADR 0008](./0008-hostconfig-grows-field-by-field-from-the-engine-api-reference.md)).
3. **The result is the `ImageID` of the Engine API** (`{ ID }`, a new type in `engine-api.ts`), from the `moby.image.id` message. The tags are the `t` that the caller gave, so the result does not repeat them.
4. **The context.**
   - The tar is written by [`modern-tar`](https://www.npmjs.com/package/modern-tar/v/0.8.6) (`^0.8.6`; MIT, ESM, with types, no dependencies). It replaces `src/tar-writer.ts` and `src/tar-reader.ts`, so `writeFiles()`, `readFile()` and the build use one tar implementation. Its archives were identical to the archive of go-archive's way on each field (type, name, mode, uid, gid, mtime, link target, size, content), with PAX headers for the long path and the long link target.
   - `files` goes through `modern-tar` with owner 0:0, as the Docker CLI tars a context. The fixture gives `[{ path: 'Dockerfile', data }]`.
   - `directory` is streamed: `modern-tar` reads one file at a time, so the memory is one file, not the folder. The package applies `.dockerignore` with its own matcher, a port of [`moby/patternmatcher` v0.6.1](https://github.com/moby/patternmatcher/blob/5a6d8429a19bb6948a372ff19e86fe83599a04b7/patternmatcher.go) and of `ignorefile.ReadAll` (a BOM, `#` comments, trimmed lines, cleaned paths). It always sends the Dockerfile and `.dockerignore`, as the CLI does (`TrimBuildFilesFromExcludes` in [`dockerignore.go` at 62881a9b826b](https://github.com/docker/cli/blob/62881a9b826b0ad813e493be15d603ce3a01b319/cli/command/image/build/dockerignore.go)). It keeps the mode and the mtime of each entry, and a symbolic link stays a link.
   - The `filter` of `modern-tar` drops an excluded directory with all its contents, but a `!` pattern can include a file again inside an excluded directory (`docs`, `!docs/README.md`). Thus the package walks the folder itself, applies the matcher to each path, and gives `modern-tar` the list of sources to write.
   - `archive` goes as it is, as in `load()` and `ContextArchive` of Testcontainers Go.
   - No compression: the transport is a local socket or one SSH channel.
5. **Progress and errors.** The call reads the progress to its end and gives no progress to the caller, as `pull()` does. It decodes only the protobuf fields above, with a reader of the protobuf wire format written here: varints as `BigInt`, the wire types 0, 1, 2 and 5, and a table of fields for each message; it skips each other field. It keeps the log of each vertex, up to its last 64 KiB (a bound of this package, not of a leader).
   - An `errorDetail` in the progress rejects with `BuildFailedError`, a `DockerEngineError` with `status` `undefined`. It has `vertex`, the name of the vertex with an `error` (`[2/2] RUN set -eux; …`), and `output`, that vertex's log. Its handling differs ([ADR 0007](./0007-an-error-has-its-own-class-when-the-caller-handles-it-differently.md)): the Dockerfile or its network failed, not the engine, so the caller shows the step and its output and does not try again. docker-py's `BuildError` carries its `build_log` for the same reason. A missing base image is a `BuildFailedError` with `no active sessions` in its message: the package does not read the text, and the README tells the caller to pull first.
   - An answer before the progress, such as 400 for a bad Dockerfile or a bad parameter, is a `DockerEngineError` with its status.
6. **Abort and the clock.** The signal ends the request. The engine then cancels the build, because the client dropped the connection. The call has no wait of its own, so it uses no clock and has no timeout ([ADR 0001](./0001-the-client-speaks-the-engine-api-not-the-docker-cli.md)).
7. **SSH engines.** The context is the body of the request, so it streams through the SSH channel of that request ([ADR 0015](./0015-an-ssh-engine-is-reached-through-zukhruf-ssh-in-the-node-process.md)), as `load()` streams its archive. The build runs on the engine host. A lost connection after the answer started rejects with the error of Node ([ADR 0011](./0011-only-a-failure-before-the-answer-is-a-connection-failure.md)).

## Considered Options

- **Spawn `docker build` or `docker buildx build`.** It needs a Docker CLI on the `PATH` and reads errors from text. ADR 0001 refused this for each call.
- **The classic builder (`version=1`).** It is the API's default. Its output is plain `stream` text, so it needs no protobuf. It lost: Docker deprecated it, and moby#47823 breaks the fixture's own case, a non-native platform on the containerd image store.
- **BuildKit with its session**, as dockerode does since [dockerode#766](https://github.com/apocas/dockerode/pull/766). The client serves gRPC over HTTP/2 on `POST /session` (deprecated in the swagger) for files, credentials and secrets. It needs `@grpc/grpc-js`, or a gRPC server and HTTP/2 written here. It gives pulls with credentials and secrets inside the build, which no caller needs now. It stays the next step when one does.
- **BuildKit's own API**: `buildctl` against a `buildkitd`, or the `/grpc` endpoint of the engine that buildx's `docker` driver uses. The same gRPC cost, and a `buildkitd` is not on each engine.
- **The tar writer of this package, with a link entry and a streaming form added.** This was the first plan, because "the package is in the base layer, with no third-party dependency". That reason was wrong: root ADR 0001 permits npm packages in a base package. The writer has 166 lines and the reader 188; the writer needs a symbolic link type, a PAX `linkpath` record and a streaming form (about 40 more lines). `modern-tar` was exact with no dependencies, so the package stops owning those lines.
- **Another tar package.** Each was compared with the archive of go-archive's way:
  - [`tar-stream`](https://www.npmjs.com/package/tar-stream/v/3.3.0) 3.3.0 was exact, but it is CommonJS and has 13 packages in its closure.
  - [`tar-fs`](https://www.npmjs.com/package/tar-fs/v/3.1.4) 3.1.4, which dockerode and Testcontainers Node use, has 18 packages in its closure and no types, and it writes an extra `./` entry that go-archive does not write.
  - [`tar`](https://www.npmjs.com/package/tar/v/7.5.23) (node-tar) 7.5.23 writes the uid and the user name of the host and the PAX records `SCHILY.dev`, `ino` and `nlink` by default, and has no option for owner 0:0. Its `portable` option sets the mtime of each directory to 0 and changes the modes to `(mode | 0o600) & ~0o22`.
  - [`nanotar`](https://www.npmjs.com/package/nanotar/v/0.3.0) 0.3.0 cuts each name at 100 bytes, with no PAX header and no prefix, has no symbolic link type, and gives one `Uint8Array` of the whole archive.
- **A protobuf dependency** for the trace. A probe decoded one sample with each candidate: an int64 above 2^53, bytes that are not UTF-8, a log of 70 KB, and four fields that BuildKit does not define. The reader written here has about 41 lines and was exact. `@bufbuild/protobuf` 2.17.0 was exact too, but its `BinaryReader` still needs the loop over the fields, so it saves only about 25 lines, for 2.8 MB. `protobufjs`, which dockerode uses with a `.proto` file cut by hand ([`lib/buildkit.js` at c3ab2f99e7fa](https://github.com/apocas/dockerode/blob/c3ab2f99e7fa65e5ff4da5929bd9e44c1975b4f5/lib/buildkit.js)), was exact, with 17 GitHub advisories. [`pbf`](https://www.npmjs.com/package/pbf/v/5.2.0) 5.2.0 read 9007199254740993 as 9007199254740992: it gives an int64 as a JavaScript number. Not decoding the trace at all loses the output of the failed step, which is what a person reads to fix it.
- **A `.dockerignore` package.** The table of the test is each case of [`patternmatcher_test.go` at v0.6.1](https://github.com/moby/patternmatcher/blob/5a6d8429a19bb6948a372ff19e86fe83599a04b7/patternmatcher_test.go): 137 cases, of which 17 patterns must give an error. Go agrees on 137.
  - [`@balena/dockerignore`](https://www.npmjs.com/package/@balena/dockerignore/v/1.0.2) 1.0.2, which dockerode and Testcontainers Node use, agrees on 120. It escapes only `.` and `$` before it makes a `RegExp` (`_compile` in [`index.js` at 41f80f9469b3](https://github.com/balena-io-modules/dockerignore/blob/41f80f9469b37f1886e49ea65676ca6077a3f407/index.js)), so it does not match `file (1).txt` or `a+b.txt`, and it throws `Invalid regular expression` on the legal pattern `C++`. Its last release is of 2020.
  - [`ignore`](https://www.npmjs.com/package/ignore/v/7.0.16) 7.0.16 agrees on 108. It has the rules of `.gitignore`, which cannot include a file again inside an excluded directory, and it does not clean paths.
  - `path.matchesGlob` agrees on 105, also with the `!`, last-match, parent and clean rules of patternmatcher written around it. It misses `**file`, `a**/*.txt` and the backslash escapes, and it reports none of the 16 malformed globs.

## Consequences

- When the owner accepts this ADR, ADRs 0001 and 0003 get a status line "Superseded in part … for image builds", and the README, its error table, its API block and `## What the package does not do` change. CONTEXT.md gets **Build context**. `docker.cliEnvironment` stays for Compose and for builds that need the session.
- `@zukhruf/testing` ADR 0027 step 3 calls `images.pull(BASE, { platform: 'linux/amd64' })` when needed, then `images.build({ files: [{ path: 'Dockerfile', data }] }, { t, buildargs: { BASE, SERVER_VERSION, REPOSITORY }, platform: 'linux/amd64' })`.
- The package gets its first npm dependency, `modern-tar` `^0.8.6`. The README sentence about the dependencies changes, and [ADR 0006](./0006-files-move-through-the-archive-requests-not-through-exec.md) ("The package writes and reads tar itself") gets a status line "Superseded in part" for the tar code.
- The swap of `tar-writer.ts` and `tar-reader.ts` for `modern-tar` needs the archive tests of the package (`tar.test.ts`, `images.test.ts` and the archive cases of the container tests) green before and after, as black-box regression tests. The reader must also read the PAX headers that the engine writes.
- The cost of the tar: `files` holds the size of the files, about 1 KB for the fixture. `directory` holds one file at a time. The new code is the `.dockerignore` matcher (`patternmatcher.go` has 312 lines of code and `ignorefile.go` 51, and the port needs the check of `filepath.Match` for the malformed patterns), with the 137 cases of `patternmatcher_test.go` as its test table, and the reader of the trace, about 41 lines.
- Before the code, probes on `desktop-linux` (the mac-mini engine is unreachable today) must show: a `version=2` build from a tar body with no session, of a local `FROM` image with `platform=linux/amd64` on the containerd image store; the `no active sessions` failure for a missing base; the cancel of the build on abort; and the trace of a failed `RUN`. A build over SSH waits for an SSH engine.
- Windows images stay out: BuildKit does not build them ([Deprecated features](https://docs.docker.com/engine/deprecated/)).
