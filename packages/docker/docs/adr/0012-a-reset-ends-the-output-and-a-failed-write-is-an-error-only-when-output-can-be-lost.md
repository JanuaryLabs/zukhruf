# A reset ends the output, and a failed write is an error only when output can be lost

A command can end before it reads all of its input, such as `true` or `head -c1`. The README says: "The result of the command then stands: the input that the command did not read is not an error." On a Unix socket, the package did not always keep this promise.

Backlog #3660 records the failure. On 2026-11-02, CI run 41459914754 failed one time in the test "a command that does not read all of its input still gives its result: true and head -c1 with 10 MB of stdin" (`exec.test.ts`). The exec of `true` with 10 MB of standard input rejected with `read ECONNRESET`. The test expected `{ exitCode: 0, stdout: '', stderr: '', output: '' }`. The failure blocked the release 0.6.15.

The maintainer gave the rule on 2026-11-13: follow what the leading tools do, and do not add an opinion of our own.

## What a reproduction showed

A probe on 2026-11-13 ran the package from source with Node 26.13.1 in `node:lts-alpine` on the virtual machine of Docker Desktop (kernel 7.0.12-linuxkit, arm64, Docker Engine 29.8.0). The scripts and the raw results are in the notes of backlog #3660.

- The failure comes only on the engine's own socket, `/var/run/docker.sock.raw`. A Linux CI runner has this socket. Through the proxy socket of Docker Desktop, `/var/run/docker.sock`, 0 of 5,200 execs failed.
- It needs a starved client and a busy engine. With 1 CPU, 4 busy loops, 2 processes that keep the engine busy and 10 MB of standard input, 163 of 1,000 execs rejected. With no load on the engine, 0.2% rejected. With 4 CPUs and no busy loops, none rejected. With 64 KB of standard input, none rejected.
- Two errors reject the call, about half each: `read ECONNRESET` and `write EPIPE`.
- `exec()` never gave a result with wrong output. After the error, the exit code was readable and 0 in 9,000 of 9,000 execs.

## What the kernel and Node do

- **Linux.** On a Unix stream socket, the kernel gives the data in the queue first. It gives the error only when the queue is empty ([`af_unix.c`, `unix_stream_read_generic`](https://github.com/torvalds/linux/blob/7e1392a42ea288d70a266f6553fe06f57f8647ea/net/unix/af_unix.c#L2977-L3000)). Thus a reset loses no output in the kernel: the reader gets all the output, and then `ECONNRESET` in place of the end.
- **macOS.** A Unix stream socket gets no error on the read, only the end. The writer gets `EPIPE` ([`uipc_usrreq.c`, `unp_disconnect`](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/uipc_usrreq.c#L1699-L1737)).
- **Node, read error.** A read error destroys the socket ([`stream_base_commons.js`](https://github.com/nodejs/node/blob/925faf48f950d9d2209b544194568cbea3d6d7fd/lib/internal/stream_base_commons.js#L218-L221)).
- **Node, the iterator.** The async iterator of a destroyed stream does not give the chunks that are still in the buffer of the stream ([`readable.js`](https://github.com/nodejs/node/blob/925faf48f950d9d2209b544194568cbea3d6d7fd/lib/internal/streams/readable.js#L1673)). The probe measured it: `for await (const chunk of socket)` lost output that Node had read when the reader was slower than the socket (136 bytes of a 64 KB output; 49 KB and more of a 1 MB output). `'data'` events gave each byte that Node read. With `'data'`, nothing of a 1 MB output was lost in 900 real execs.
- **Node, write error.** A failed write always destroys the socket, the read side too ([`writable.js`](https://github.com/nodejs/node/blob/925faf48f950d9d2209b544194568cbea3d6d7fd/lib/internal/streams/writable.js#L641-L652)). `net.Socket` sets `autoDestroy` to true whatever the caller gives. `allowHalfOpen`, an error listener and the write callback change nothing, and no public API keeps the socket open for the read. Thus output that is still in the kernel when the write fails is lost. In the probe, `head -c1` lost its one byte in about 1% of the starved execs (8 of 600, 8 of 900, 5 of 900) with each read method, `'data'` included. In each counted case, Node had read 0 output bytes after the upgrade. `echo hi` lost its output in 2 of 900.

A second probe on the same day used the same starved setup on the engine's own socket: 2,500 execs for each arm and command, with `'data'` reads, each socket error counted as the end, and the exit code from the inspect of the exec. The exit code was 0 in all 60,000 execs. Output lost by `head -c1` and `echo hi`, of 5,000 execs:

| Arm                                                                                    | Output lost |
| -------------------------------------------------------------------------------------- | ----------- |
| A: one write of 10 MB at once                                                          | 13          |
| B: the same write after a poll phase                                                   | 10          |
| C: pieces of 1 MB after a poll phase                                                   | 10          |
| C: pieces of 64 KB after a poll phase                                                  | 19          |
| E: pieces of 64 KB, chained, with no poll phase                                        | 46          |
| D: two `net.Socket` objects on one connection, through a helper process, write at once | 0           |

- `true` and a command with 1 MB of output lost nothing in any arm.
- Each loss with a single write was a write that Node had accepted and that failed later with `EPIPE` (13 of 13, 10 of 10). A write that is already in flight when the engine closes cannot be deferred.
- All 98 lost execs had one signature: the write failed with `EPIPE` before the output ended, and Node had read 0 output bytes since the upgrade. For a command with output, the signature was exact: each exec with the signature lost its output, and no exec without it did. The signature cannot tell a loss from a command that prints nothing: `true` had the signature in 13 of 2,500 execs of arm A, and it lost nothing. Thus the package can know "the output can be incomplete", not "the output is incomplete".
- With no starvation, 200 execs of `wc -c`, which reads all 10 MB, took about 40 ms each in every arm. No arm had a cost that the probe could measure.

Podman had the same race. In [podman#11446](https://github.com/podman-container-tools/podman/issues/11446), `echo | podman run --rm -i fedora /bin/true` failed about 4 times in 1,000 with `read: connection reset by peer`. [PR #14109](https://github.com/podman-container-tools/podman/pull/14109) fixed it with commit [`9974c90ccc`](https://github.com/podman-container-tools/podman/commit/9974c90ccc), "libpod: treat ECONNRESET as EOF". The Docker CLI has the same failure open with no fix: in [docker/cli#1456](https://github.com/docker/cli/issues/1456), a `head -n 1` with a large standard input prints its line and then fails with `connection reset by peer`.

No client stops its stdin copy when the output ends. Each one ignores the stdin write error or only logs it. No leading tool has an error for an output that can be incomplete. The loss exists only in Node, where a failed write destroys the socket. Go keeps reading.

What closes the engine's end of the connection is not known. The handlers of Moby only half-close the hijacked connection when the output ends, and they do not read the rest of the stdin ([`httputils.go`](https://github.com/moby/moby/blob/8fa9f49a2be4ad50dcbc88c1b7bb30370c5d16c1/daemon/server/httputils/httputils.go#L24-L45)). A full close by the finalizer of Go at a later garbage collection fits "rare, on a starved client". That is an inference only.

## Considered Options

- **Reject on a reset, as the Docker CLI does.** The result of a command that ended and has a known exit code is then lost. The Docker CLI has this as an open bug since 2018 (docker/cli#1456). The one leader that fixed the same race, the Podman runtime, treats the reset as the end.
- **Count a failed write as the end in each case.** In rare cases the call then gives exit code 0 with missing output, and the caller cannot know it.
- **A "still running" check with a time limit after a reset.** The engine reports an exec as running for a moment after its output ends, so one inspect after a reset would reject a command that had ended. A wait for the end needs a time limit, and that would be the first time limit of the package ([ADR 0001](./0001-the-client-speaks-the-engine-api-not-the-docker-cli.md): "The package has no timeout of its own"). No leading tool has the check.
- **Writes after a poll phase, or in pieces.** Measured: 10, 10 and 19 lost of 5,000, against 13 for one write at once. No gain.
- **Two sockets on one connection, through a helper process.** 0 lost of 5,000. But it needs a helper process and its own hand-written upgrade request, it cannot use the hijack of the package, and it has no form for a Windows named pipe or for SSH. It proves that zero is possible. It is not a design.
- **A retry in the package.** The command did run: its exit code is known. A second run is not safe for a command with side effects, and the package cannot know whether it is safe. The engine keeps no output of an exec. No leading client runs an exec again.
- **Read with no limit while the input is open.** Then the package never stops reading, and a failed write can lose only the bytes in flight. But a caller that keeps `stdin` open and reads slowly makes the package hold all the output in memory, and [ADR 0005](./0005-output-is-one-stream-of-chunks-and-only-a-close-ends-the-input.md) says that the package reads as fast as the caller iterates.
- **A reset is the end of the output, as the Podman runtime does, and one error class for the cases that can lose output.** This option was selected.

## Consequences

- For an exec and an attach on a Unix socket or a Windows named pipe, a reset on the read side of the hijacked connection (`ECONNRESET`) is the end of the output. The package first gives the output that came before the reset.
- The package reads the hijacked connection with `'data'` events into a queue of its own. The async iterator of a destroyed stream drops the chunks that Node already read.
- The queue keeps the rule of [ADR 0005](./0005-output-is-one-stream-of-chunks-and-only-a-close-ends-the-input.md): the package reads as fast as the caller iterates. When the queue holds the default high-water mark of Node (`getDefaultHighWaterMark()` of `node:stream`) of output that the caller did not take, the package pauses the connection. It resumes it when the caller takes the output.
- A stdin write that fails is not, by itself, an error of the call. This agrees with the README: the input that the command did not read is not an error.
- Two cases are an error, because output can be in the kernel when Node destroys the socket after a failed write. The stdin write failed before the output ended, and:
  - no output byte came since the upgrade, or
  - the connection was paused, because the caller did not take the output in the queue.

  In the first case the package cannot know whether there was output. In the second case the stand-in server of the probe showed the loss: a reader that stopped the reads lost 48 KB and more of a 1 MB output when the write failed. The call then rejects with `IncompleteOutputError`. The error has the exit code of the command, and its `cause` is the write error. The caller decides: it goes on, or it runs the command again. A caller that takes each chunk at once, such as `collect()` and `exec()`, gets only the first case. No leading tool decides this, because the loss exists only in Node: the maintainers of the package chose this rule.

- `IncompleteOutputError` is a new exported class. [ADR 0007](./0007-an-error-has-its-own-class-when-the-caller-handles-it-differently.md) gives the rule: a class of its own when the next step of the caller is different. The name says what the caller must deal with. A command that prints nothing lost nothing, so a name with "lost" would be wrong. It is not an answer of the engine, so it extends `DockerError` and not `DockerEngineError`.
- The exit code comes from the requests that the package already sends. For an exec, it is the inspect of the exec, every 10 ms while the engine reports the exec as running. For an attach, it is the open `POST /containers/{id}/wait`. The package sends no extra "still running" check, and it has no time limit. When the engine is gone, that request fails, and the call rejects.
- The package does not run the command again.
- An accepted limit: when a connection drops in the middle of a run and the engine stays up, the call gives the real exit code with only the output that came before the drop. The call waits until the command ends, as the Podman runtime waits for the exit file of conmon. Without a signal, a command that never ends makes the call wait without end. Before this decision the call rejected at once with the reset. The signal of the caller limits the wait, as [ADR 0001](./0001-the-client-speaks-the-engine-api-not-the-docker-cli.md) gives each limit to the caller.
- These parts are not covered:
  - The SSH transport. There the failure is a non-zero exit of `ssh`, not `ECONNRESET` or `EPIPE`. It needs its own measurement on a real sshd (backlog #4346).
  - A Windows named pipe was not run (backlog #2753).
  - A native Linux host and the rate on the CI runner were not measured. The probe ran on the virtual machine of Docker Desktop.
  - An output that Node reads in part before a write fails. It was not seen in 15,000 execs with 1 MB of output, but it is not excluded.
  - What closes the engine's end of the connection. That is an inference only.
- The code is in place: `src/container-process.ts` reads the hijacked connection, and `IncompleteOutputError` is in `src/errors.ts`.
