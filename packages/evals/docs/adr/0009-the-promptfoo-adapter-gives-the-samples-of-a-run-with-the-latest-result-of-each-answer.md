# The promptfoo adapter gives the samples of a run, with the latest result of each answer

Status: accepted and built (2026-11-27, #6110): `src/promptfoo/promptfoo-samples.ts`. Ezz ruled the shape ("Adapter + Iterator"). The build adds three rules that the real rows asked for: the rows are of one prompt (a run of two providers is two logs), a row that is still a promptfoo error after the newest-row rule was never retried and refuses the run (ADR 0005 keeps such failures for `--retry-errors`), and a failed call is the graded row of `FailedCall` with its `failed` reason. The tests run the real promptfoo CLI, a retry with `--retry-errors` included. Two facts of the real rows shaped the code: promptfoo 0.126 gives each execution of a test, each repeat too, its own `testIdx`, in the order of the tests and then of their repeats, so `testIdx` alone is the key and the order of an answer (a key with the epoch added nothing that a mutation could show), and it writes the weight of every named score, 1 when its assertion sets none, so a score with no weight refuses the run instead of reading as weight 1. A row with no tokens and no cost has no usage, a new call too, since promptfoo fills the tokens with 0 when a provider measured none.

Status update (2026-11-28, #6325, #6326): an error row that carries named scores is a failed sample, the answer null with the error of the row, as point 5 says of a failed call. It is the second form of ADR 0005, an `afterEach` hook that grades the error row on `FailedCall.answer` (Inspect AI's `score_on_error`, offers-evals `apps/sob/src/failed-answer.ts`). A hook cannot write `namedScoreWeights`, so each score of such a row that has no weight weighs 1, as promptfoo counts it: with no weight and no component results, `getNamedMetricContribution` gives a score the weight 1 (`dist/src/evaluator-5tUcjTs8.js:6622-6632` of promptfoo 0.126.0), and promptfoo runs `afterEach` before it adds the row to the metrics of its prompt (lines 9379-9400). A score with no weight on a graded row still refuses the run. An error row with no named scores was neither retried nor graded, and still refuses the run; after `--retry-errors` the newest-row rule still keeps the retried row. A graded error row with no error is refused, since promptfoo writes the error of each error row. `PromptfooResult` takes promptfoo's own `EvaluateResult` under `exactOptionalPropertyTypes`: an optional field that promptfoo's type gives `| undefined` (its zod-inferred `testCase.metadata` and `tokenUsage`) or `| null` (`gradingResult.namedScoreWeights`) takes it too, and `error` takes `undefined`, which the rows of `afterAll` hold on every answered row. The tests run the real CLI for both: a graded error row before and after `--retry-errors`, and an `afterAll` extension that passes `context.results` to `PromptfooSamples` as they are; a type test passes `EvaluateResult[]` and `AfterAllExtensionHookContext['results']` with no cast.

Status update (2026-11-28, #6341): a row whose assertion threw refuses the run with `ThrownAssertionError` of `./promptfoo`. A thrown assertion is a defect of the scorer, not a failed call (ADR 0005), so the score of its test is unknown, not the score of the answer null. promptfoo 0.125.1 made such a row an error row, which refused the run as an ungraded error; promptfoo 0.126.0 (#11939) grades it as a failed component with no named scores (`scriptFailure`, `dist/src/evaluator-5tUcjTs8.js:5593-5598, 5613-5616`), so the row fails with `ASSERT`, its `error` is the reason (`applyGradingResult`, 7292-7300), and its `gradingResult` has no `namedScoreWeights`, which promptfoo writes only when an assertion scored a name (1558-1565). Read as an answered sample, its empty scorecard left its test out of every whole, the failure ADR 0005 exists to prevent. The reader tells it apart by what promptfoo writes: `failureReason` `ASSERT` and a `gradingResult` with no `namedScoreWeights`; an assertion that fails on its scores writes them with their weights and is still an answered sample. The error is a class, not a `RangeError`, because a host must catch it by its type and still finish its own work (offers-evals' climb writes a failed line and counts the calls of the run, #4593); it holds each test and epoch with promptfoo's reason (`gradingResult.reason`) as data. Not covered: an assertion that throws beside another assertion that scores a name, or one with a `metric` (promptfoo then scores the metric 0 with its weight), since the row then has `namedScoreWeights`. The tests run the real CLI: an assertion that throws on one test over two epochs, one that fails on its scores, and one that passes with no score. As a follow-through of #6326, `PromptfooResult`'s `testCase` takes promptfoo's optional `description` (`string | undefined`, as its zod-inferred `AtomicTestCase` has it), so a reader reads the test id from it with no cast (offers-evals #6347), and the type test reads it.

Status update (2026-11-28, #6359): the weight of a case belongs to the case, and `Run` applies it, once: the unit of a test is the mean of its epochs times the weight of its case (`src/scoring/run.ts`). A writer of the rows stores each ratio as the scorer gave it, the scorer's whole as `namedScoreWeights[name]`, and the reader reads the rows as stored. `PromptfooAssertion` multiplied each ratio by the weight of its case (`ratio.times(testCase.weight)`), so a case of weight w counted w² in `Run#total`, `Bootstrap` and `PairedBootstrap`: a probe on the real promptfoo 0.126.0 CLI of two tests of weight 1 and 3 gave the recall 10/19 (Σ part·w² / Σ whole·w²) in place of 4/7 (Σ s·w / Σ w). `ScorerAssertion` stores its assertion's weight with no case weight, so its rows were already right (1/4 for the exact match), and a row does not say which writer wrote it, so the reader cannot undo one writer: the writer changed. `PromptfooAssertion` now stores the scorer's whole; promptfoo's own metric for its rows is no longer weighted by the case, as it never was for `ScorerAssertion` rows, and point 3 holds for cases of weight 1. A host that writes rows itself must store the scorer's whole too: offers-evals' `Score` (`packages/score/src/score.ts:86-87`, used by SOB and offers) multiplies by the case weight today (offers-evals #6347). The test runs the real CLI: two tests of weight 1 and 3, scored by `PromptfooAssertion` and by `ScorerAssertion`, read through `PromptfooSamples` into a `Run`.

## Context

`./promptfoo` turns scorers into promptfoo assertions. Nothing reads a promptfoo run back. Three evals read the rows by hand (read 2026-11-27):

| Place                                                      | What it reads                                                                                         |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| offers-evals `apps/offers/src/climb.ts`, `Answers.from`    | `Ratio(namedScores[n] × namedScoreWeights[n], namedScoreWeights[n])` for each name of the goal        |
| offers-evals `apps/offers/src/held-out-compare.ts`, `rows` | the same, from an export file (offers-evals #4593, strike 2, ledger `docs/copied-from-climb-host.md`) |
| offers-evals `apps/sob/src/summary/scored-row.ts`, `rowOf` | `namedScores` as values, and the modality and difficulty of the metadata                              |

`latestResults`, which keeps one row for each test after `--retry-errors`, is copied from offers-evals' SOB summary into context-compiler (#3996). promptfoo hands the rows to an `afterAll` extension as `context.results`, and `promptfoo export eval <id>` writes the same `EvaluateResult` rows under `results.results`.

The paper first had a static `PromptfooLog.read(results, options)`. A static method on a class with no state is a namespace; the job is to adapt one interface (promptfoo's rows) to another (the samples of the core), which is the Adapter pattern, and the samples are a sequence, which is the Iterator pattern.

## Decision

1. **`new PromptfooSamples(results, readers)` is an iterable of `Sample`s**, and `new RunLog(info, samples)` takes any iterable of samples (core ADR 0007). The results are `EvaluateResult` rows, from `afterAll` or from an export.
2. **The caller gives the test id, the case reader and the answer reader** (Strategy). promptfoo has no stable test id (ADR 0004, point 1). The case comes from the vars through the `CaseReader` that the assertions already use. The answer reader turns the stored output into the value that the comparer reads.
3. **The ratio of a name is the named score times its weight, over its weight.** So `Totals` of the log gives the ratio of sums that promptfoo's column header shows (`PromptfooAssertion`), when every case weighs 1 (status update of #6359).
4. **The newest result of each test and epoch wins.** After `--retry-errors`, a test has a stale error row and its retried row. The adapter keeps the one that promptfoo wrote last, as `latestResults` does.
5. **A failed call is a failed sample.** A result with an error and no output gives the answer null and its error (ADR 0005).
6. **The usage comes from `tokenUsage` and `cost`, and `response.cached` marks a replay.** `prompt` and `completion` are the input and output tokens, `completionDetails.cacheReadInputTokens` the input that the provider read from its prompt cache, and `cost` the cost of the answer. A row whose `response.cached` is true is a replayed sample (core ADR 0007, point 5), and its usage is the usage that the harness reports for the answer: promptfoo keeps a cached answer's tokens and counts what this run incurred apart, in `incurredTokenUsage` and `incurredCost`. A harness that reports a replay with no tokens and no cost gives it no usage: eval-ove of offers-evals has 711 such rows of 921 (offers-evals #6114).

## Consequences

- The three readers of offers-evals move onto it, and the copies go: #4593 (`climb.ts`, `held-out-compare.ts`), #6115 (`rowOf`).
- A reader of another runner, such as Inspect AI's logs, is one more iterable of samples; `RunLog` does not change.
- context-compiler's copy of `latestResults` stays: startup-credits is not changed.
