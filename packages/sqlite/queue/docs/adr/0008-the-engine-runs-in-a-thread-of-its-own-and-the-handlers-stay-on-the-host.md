# The engine runs in a thread of its own, and the handlers stay on the host

Status: Accepted 2026-11-28 (backlog #4984).

Decision-makers: Ezz, on the placement ("sqlite-queue + notify": each engine package owns its off-thread form) and on the name ("...Thread"); the zukhruf session mutex-91 from the evidence for the rest (paper v2, `~/.claude/plans/4984/paper-v2.md`).

`node:sqlite` is synchronous. A `SqliteJobQueue` runs each statement on the thread that calls it. A commit with `synchronous` FULL waits for the disk, which ADR 0005 keeps, and a write waits up to the busy timeout of 5000 ms for the lock of another connection (`@zukhruf/sqlite-open`, `open.ts`). On a loaded Mac, a pool host on the main thread stalled up to 4.5 s, and each stall matched a slow `COMMIT` (#4984: runs2.log, runs3.log). pg-boss never blocks its host, because Postgres writes in its own process. PGlite ships the same answer for its engine: `PGliteWorker` runs it in a worker.

## Decision

- `SqliteJobQueueThread`, at the subpath `@zukhruf/sqlite-queue/thread`, runs a `SqliteJobQueue` in a worker thread. It is a `JobQueue` and `AsyncDisposable`, and it emits `error`, `warning`, `wip` and `stopped`.
- It takes the options of `SqliteJobQueue` without `database`, which cannot go to another thread, with `path` necessary, and with `resourceLimits` for the thread. The engine in the thread opens the file with `synchronous` FULL, as `SqliteJobQueue` does.
- The calls cross through `@zukhruf/rpc`. Each thread has one link: in the thread, a `ConnectionSupervisor` over a `ParentPortConnection`, with a `Server` of the engine and a `Client` of the host; on the host, the same over a `WorkerConnection`. A link carries one thread only, so the answer of a handler of a lost thread never reaches the thread that replaces it, and a call in flight on a lost thread can never go out again.
- The `work()` handlers run on the host. The thread calls the host's `handle(work, batch, jobs)` for each batch, and each job's signal follows as `abort(batch, job, reason)`, also after the handler returns, when the batch settles (`manager.js:606`).
- With `systemClock`, or no clock, the engine uses the timers of its thread. Any other clock is the host's: the thread notifies `arm(timer, ms, repeat)` and `disarm(timer)`, the host arms each timer on its clock and notifies `fire(timer)`, and before each message the host sends `time(now)`, which the thread's clock gives as `now()`. The thread's `Date.now` reads that clock too, because pg-boss times a worker's round on `Date.now` (`worker.js:64-67`). A `TestClock` is attached on the host: its `idle()` calls the thread, which takes a turn of its event loop, as the clock gives one before it asks (`clock.js:193-200`), and answers when the engine's activity is idle. The host's `idle()` also says that it waited when a handler settled since the last call, because the handler's answer, on its way to the thread, starts the engine's next statements there. So `tick()` waits for the statements in the thread.
- The errors cross through an `ErrorCodec` that lists `AssertionError`, `DatabaseError`, `UnsupportedStartAfterError`, the errors of `@zukhruf/sqlite-open` and the two warning classes. The built-ins cross without a list, and an error of `node:sqlite` keeps `code`, `errcode` and `errstr`.
- A function, a symbol and a `toJSON` method in an argument or in a handler's output cross as records that the other end makes again, because the engine reads them: it refuses a function as data, and it stores data as `JSON.stringify` makes it.
- The engine reacts to an `error` that nobody hears (`ERR_UNHANDLED_ERROR`, `index.ts` `#failWip`). So the host sends its count of `error` listeners at each change, and the thread listens to the engine's `error` only while the count is not 0. The thread removes Node's printer of its process warnings, and the host emits each one again under its own flags.
- The thread comes with `start()`, or with a `work()` before it, as pg-boss takes a `work()` before its first start (`manager.js:1178-1180`). The engine is made as at the time of the queue's constructor on the host clock, so its `wip` window counts from then (`manager.js:248`). A start that fails rejects and ends the thread. `stop({ close: true })` ends the thread, and the dispose waits for its exit. A `work()` of an engine that never started stays for the next start, as on the main thread.
- A thread that ends outside a stop is started again after 1 s, doubling up to 30 s, on the queue's clock, as pg-boss reconnects (`db.js:129-178`). Each failed attempt emits `error`. A call in flight rejects with `ConnectionLostError` and is not sent again. A call made during the restart waits for the attempt and gets its error when it fails. The new thread opens the engine, starts it with the last options of `start()`, and registers each `work()` again, under the ids that `work()` gave. The workers fetch at once, as pg-boss fetches when its listener comes back (`notifier.js:58`).

## Considered Options

- **Run each statement in a thread, and keep the engine on the host.** Each statement is a round trip, and a transaction holds the thread across them. Paper v1 Decision 1 rejected it.
- **One package that runs both engines in one thread.** Ezz placed each off-thread form in its engine's package ("sqlite-queue + notify"); pool composes the two.
- **comlink 4.4.2, birpc 4.2.0 or vscode-jsonrpc 10.0.2 for the calls.** Each leaves a call pending after its thread exits, and each loses the `code` of an error (paper v2, probes on Node 26.13.1). `@zukhruf/rpc` does both.
- **Synchronous NORMAL in place of a thread.** It removes the fsync of each commit but not the checkpoint or the busy wait, and a commit can roll back after a power loss (#4984 A/B: 7 slow commits of up to 1.7 s remained). ADR 0005 keeps FULL.
- **Keep the thread's real time under a host clock.** A worker's poll then comes early by the real time of its round, so the thread form diverges from pg-boss on a `TestClock`: 45 of 262 parity checks failed until the thread's `Date.now` followed the clock.

## Consequences

- A host that stays responsive picks `SqliteJobQueueThread`. `SqliteJobQueue` stays for a CLI or a test.
- A thread costs 10 to 23 ms to start and 13 MB of memory, and a call costs a round trip of 37 to 98 µs median (paper v2, `cost.mjs`).
- `--max-old-space-size`, also in `NODE_OPTIONS`, is a flag of the process, and it overrides `resourceLimits.maxOldGenerationSizeMb` of each thread (probe on Node 26.13.1: a thread with a limit of 32 MB had a heap limit of 4192 MB under `--max-old-space-size=4096`).
- A host that `node --eval` started cannot start the thread: the thread takes the host's `--input-type`, and Node allows it only for `--eval` (`ERR_INPUT_TYPE_NOT_ALLOWED`).
- An `error` listener of the host that throws gives a `ServerWarning` of `@zukhruf/rpc` (`ZUKHRUF_RPC_NOTIFICATION_FAILED`), not the `SqliteJobQueueWarning` `ZUKHRUF_SQLITE_QUEUE_ERROR_LISTENER_THREW` of the main thread: the engine does not hear the throw.
- One parity scenario runs on the main thread only (`Parity.assertSameOnTheMainThread`, `src/parity/groups.test.ts`): a `stop()` right after `work()` reaches the thread after the first fetch landed, because `work()` answers after a round trip. On the main thread the stop starts in the turn of the fetch's I/O.
- A value that the structured clone refuses, such as a `WeakMap`, in an argument ends the link: `@zukhruf/rpc` reports the failed `postMessage` as a loss. The call rejects with `ConnectionLostError`, not with the `DataCloneError`, and the thread is ended and started again like a lost one (`goes on after a call with a value that the port cannot clone`). On the main thread the engine stores such a value as `JSON.stringify` makes it. A fix in `@zukhruf/rpc` would reject the one call with its `DataCloneError` and keep the link.
- A `DOMException` crosses through the codec as a `ServerError` named `DOMException`, so the reason of an aborted job's signal keeps its message but not its name `AbortError` (a `todo` test, #4984).
- The remote clock is strike 1: `@zukhruf/sqlite-notify`'s thread form copies it, with a ledger.

## Confirmation

- `src/thread/sqlite-job-queue-thread.test.ts`: a send that waits 2 s for another connection's write lock leaves a 50 ms host timer under 100 ms late. On `SqliteJobQueue` the same test fails: the main thread cannot commit the other connection, and the send fails with `database is locked` after 5.2 s.
- The same file: a call in flight when the thread runs out of memory rejects with `ConnectionLostError` and is not sent again; the restart takes the next call and runs each `work()` of the lost thread, by fetch and by notification; the restart waits 1, 2, 4, 8, 16, 30 and 30 s on a `TestClock`, and a failed attempt reaches `error` and the calls that waited; each error class arrives as `SqliteJobQueue` throws it; the clock kinds; the `error` listeners; the lifecycle in a host process.
- The parity suite runs each scenario on a third backend, `SqliteThreadBackend`, on a file in a `TemporaryFiles` folder, and requires its observation to equal pg-boss's (`src/parity/parity.ts`). The first run of the suite on the thread form failed 45 of 262 checks; each failure named a gap that this record now decides: the round timer under a host clock, a `work()` and a `stop()` before `start()`, a function or `toJSON` in the data, a job's signal after its handler, the `wip` window from the constructor, and `idle()` while a handler's answer crosses. The last run: 261 of 262 pass, and 1 is the recorded divergence. A later run under the suite's own load failed a check of `wip` events after a graceful stop, about 1 run in 12 alone: the thread emitted a `wip` event at 6000 ms that `stop()` clears on the main thread. The cause was in the engine, not in the thread: `stop()` awaits the close of its listener before it clears its intervals (`manager.js:1126-1129`), and its `Activity` did not count that close, so a `TestClock` fired the interval during it. Only the thread backend runs on a file, whose listener closes with I/O of `@zukhruf/sqlite-notify`; the main-thread backend runs in memory, whose listener closes in one turn. `Activity.track` now counts the close: with a close made 30 ms slower, the test of a graceful stop on a file in `src/index.test.ts` passes, and without the count it fails with the emit at 6000; the thread form's check then passed 12 of 12.
