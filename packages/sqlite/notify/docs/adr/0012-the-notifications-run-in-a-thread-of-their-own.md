# The notifications run in a thread of their own

Status: Accepted 2026-11-28 (backlog #4984, step 3).

Decision-makers: Ezz, on the placement ("sqlite-queue + notify": each engine package owns its off-thread form) and on the name ("...Thread"); the zukhruf session mutex-91 from the evidence for the rest (paper v2, `~/.claude/plans/4984/paper-v2.md`, which still says `NotificationsWorker` at `/worker`).

`node:sqlite` is synchronous. A `notify` and a `listen` run their transactions on the thread that calls them. A commit with `synchronous` FULL waits for the disk, and a `BEGIN IMMEDIATE` waits up to the busy timeout of 5000 ms for the lock of another connection (`@zukhruf/sqlite-open`, `open.ts`). On the main thread each such wait stops every timer of the host: with the test's own connection holding the lock for 2 s, a 50 ms timer of the host ran 5127 ms late, and the `notify` failed with `database is locked`, because the host could not commit the other connection while it waited. Postgres never blocks the program that sends `NOTIFY`, because it writes in its own process. `@zukhruf/sqlite-queue` made the same move for its engine (its [ADR 0008](../../../queue/docs/adr/0008-the-engine-runs-in-a-thread-of-its-own-and-the-handlers-stay-on-the-host.md)), and `@zukhruf/pool` composes the two.

## Decision

- `NotificationsThread`, at the subpath `@zukhruf/sqlite-notify/thread`, runs a `Notifications` in a worker thread. It emits `notification` and `error`, and it is `AsyncDisposable`. `NotificationsThread.create(options)` makes it and resolves once the thread has opened the file, as `PGliteWorker.create` does; a failure rejects and leaves no thread.
- It takes the options of `new Notifications({ path })`: `path`, `clock` and `maxQueuedNotifications`. A `DatabaseSync` cannot go to another thread, so there is no `database` option. The thread opens the file with `synchronous` FULL, as `new Notifications({ path })` does.
- `notify` returns a promise that resolves when its own `BEGIN IMMEDIATE` transaction in the thread has committed. It cannot join a transaction of the caller. This is the one difference from `Notifications`: the contract claims of a caller's transaction (C2, C4, C7 and a transaction held across an await) run on `Notifications` only (`src/contract.test.ts`).
- The calls cross through `@zukhruf/rpc`, one link for each thread: in the thread a `ConnectionSupervisor` over a `ParentPortConnection`, with a `Server` of the notifications and a `Client` of the host; on the host the same over a `WorkerConnection`. A call is sent in the caller's turn, so calls reach the thread in the order they were made.
- The host checks a channel and a payload, and refuses a call after the dispose, before anything crosses, so the errors come in the order of `Notifications`. The host keeps the wanted channels as `Notifications` keeps them: `unlisten` removes its channel at once, and the host drops a notification of a channel it no longer wants, also one that the thread sent before it heard the `unlisten`.
- With `globalThis` as the clock, the thread uses its own timers. Any other clock is the host's: the thread notifies `arm(timer, ms)` and `disarm(timer)`, the host arms each timer on its clock and notifies `fire(timer)`, and before each message the host sends `time(now)`, which the thread's clock gives as `performance.now()`. `@zukhruf/async`'s `Clock` has no interval and no attach, so the thread's clock has neither.
- The errors cross through an `ErrorCodec` that lists `DisposedError`, `QueueFullError`, the errors of `@zukhruf/sqlite-open` and `NoServerError` and `UnsafeFolderError` of `@zukhruf/pipes`. The built-ins cross without a list, and an error of `node:sqlite` keeps `code`, `errcode` and `errstr`.
- The thread always listens to the `error` of its notifications and sends each error to the host. The host emits it. An `error` that nobody hears on the host, or that a listener throws, is thrown again on the next tick, so it ends the host as it ends a program with `Notifications`. A throw inside the `Server`'s handler would become a `ServerWarning` of `@zukhruf/rpc` instead.
- A thread that ends outside a dispose is started again after 1 s, doubling up to 30 s, on the clock, as pg-boss reconnects its `LISTEN` (`db.js:159-178`). Each attempt that fails emits `error`; an attempt that opens the file resets the wait to 1 s. A call in flight rejects with `ConnectionLostError` and is not sent again. A call made during the restart waits for the attempt and gets its error when it fails, or `DisposedError` when a dispose overtakes it. The new thread listens again on each wanted channel. A notification that commits in the gap does not come, as with a lost `LISTEN` of Postgres. A thread that throws an uncaught error during an attempt fails the attempt with that error, not with `ConnectionLostError`.
- The thread keeps the host alive from `create` to the dispose. The dispose disposes the notifications in the thread, as `Notifications` disposes, waits for the thread's exit and clears the timers that the thread armed on the host's clock.

## Considered Options

- **One package that runs both engines in one thread.** Ezz placed each off-thread form in its engine's package ("sqlite-queue + notify"); pool composes the two.
- **comlink 4.4.2, birpc 4.2.0 or vscode-jsonrpc 10.0.2 for the calls.** Each leaves a call pending after its thread exits, and each loses the `code` of an error (paper v2, probes on Node 26.13.1). `@zukhruf/rpc` does both.
- **A `notify` that joins the caller's transaction.** The caller's connection is on the host, and the thread has its own. Only `Notifications` on the caller's connection can write the row in the caller's transaction.
- **Send the host's count of `error` listeners, as `SqliteJobQueueThread` does.** The queue's engine changes what it does when nobody hears its `error`. `Notifications` does not: an `error` that nobody hears is thrown where it is emitted. The thread form throws it on the host instead.
- **Forward each process warning of the thread, as `SqliteJobQueueThread` does.** `Notifications` and the code it calls emit no process warning, so nothing would cross.
- **A TestClock attached across the thread, as `SqliteJobQueueThread` does.** `@zukhruf/async`'s `Clock` has no `attach`. A fake clock's tick does not wait for the thread: a timer that the thread arms after a fired one is armed when its message reaches the host, as a late timer would be.

## Consequences

- A host that must stay responsive, such as pool, picks `NotificationsThread`. A sender that writes a row and its notification in one transaction keeps `Notifications` on its own connection.
- A thread costs 10 to 23 ms to start and 13 MB of memory, and a call costs a round trip of 37 to 98 µs median (paper v2, `cost.mjs`).
- A host that `node --eval` started cannot start the thread: the thread takes the host's `--input-type`, and Node allows it only for `--eval` (`ERR_INPUT_TYPE_NOT_ALLOWED`). `create` rejects with that error. The thread form of the test program (`src/testing/program.ts`) runs from a file for that reason.
- A value that the structured clone refuses cannot reach `notify`, since a channel and a payload are strings. A failed `postMessage` would end the link (#6336), and the thread would be started again like a lost one.
- A crashed thread leaves its listener row, as a crashed program does: a sender removes it once it finds the listener dead (ADR 0010, ADR 0011). The new thread registers a new listener.
- The remote clock is strike 2: `src/thread/host-clock.ts` and the host side of `src/thread/engine-thread.ts` copy `@zukhruf/sqlite-queue`'s, with a ledger ([copied-from-sqlite-queue.md](../copied-from-sqlite-queue.md)) and a backlog item that waits for a third consumer.

## Confirmation

- `src/thread/notifications-thread.test.ts`: a `notify` that waits 2 s for another connection's write lock leaves a 50 ms host timer under 100 ms late (the same body on `Notifications`: 5127 ms late, then `database is locked`). A call in flight when the thread ends rejects with `ConnectionLostError` and is not sent again. The restart waits 1 s on the clock, listens again on each channel, keeps a channel that was unlistened off, misses the gap, waits 1, 2, 4, 8, 16, 30 and 30 s while attempts fail, gives each failure to `error` and to the call that waited, waits 1 s again after an attempt that opened the file, gives `DisposedError` to a call when the dispose overtakes it, and does not listen again on a channel whose `listen` failed. Each error class arrives as `Notifications` throws or emits it. Calls of one turn arrive in order. `unlisten` drops a notification that waited in the host's port. The clock kinds. A host process exits by itself after the dispose and after a failed `create`; an `error` that nobody hears ends it on both forms.
- `src/contract.test.ts`: each contract claim that needs no caller's transaction runs on both forms.
