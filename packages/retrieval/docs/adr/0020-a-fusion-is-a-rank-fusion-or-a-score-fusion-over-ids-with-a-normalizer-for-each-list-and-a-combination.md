# A fusion is a rank fusion or a score fusion over ids, with a normalizer for each list and a combination

Status: Accepted 2026-11-26 (backlog #5400, #5585).

Decision-makers: Ezz, who set the direction on 2026-11-25 ("All of it, port split included") and approved the paper of #5400 on 2026-11-26. On its splits he chose `retrievers` over `sources` for the record of `FusionRetriever` and kept the four names that no leader has (`RankedDoc`, `RankedPassage`, `RankNormalizer`, `ListScores`), and he accepted that `@zukhruf/mteb` takes the checks of the core. The leader tables of the paper (`~/.claude/plans/retrieval-fusion-families-5400.md`) decided the rest.

`Fusion<P>.fuse(lists, weights)` took lists of passages. `@zukhruf/mteb`'s hybrid search holds only ids and scores, so it could not call the package, and it kept three loops of its own (#5400, strike 3). The weights went in an array beside the lists, so a count that differed was a `RangeError` at run time, and a message could name a list only by its index. Meddit's federation needs the greatest score of an id (#5585), which would have been a fourth copy of the sum loop.

The leaders agree on the shape:

- The engines fuse ids and attach the documents after: Elasticsearch `RRFRetrieverBuilder.java:198-212`, OpenSearch `ScoreCombiner.java`, Qdrant `local_shard/query.rs`.
- A score fusion is a normalizer for each list, then a combination with weights: OpenSearch's normalization processor (`normalization` and `combination`), Qdrant `score_fusion.rs:10-31`, ranx `fuse.py:8-37`, Elasticsearch's `linear` retriever, MongoDB `$scoreFusion`.
- Reciprocal rank fusion is a rank normalizer and a sum: OpenSearch `RRFNormalizationTechnique`, Vespa `reciprocal_rank(x, k)`.
- MongoDB splits the two families by what the inputs carry. `$rankFusion` requires a "Ranked Pipeline". `$scoreFusion` says: "You must specify `$score` to the input pipeline if the input pipeline doesn't return a score." Both take `weights` by pipeline name, "a non-negative number", 1 by default ([$rankFusion](https://www.mongodb.com/docs/manual/reference/operator/aggregation/rankFusion/), [$scoreFusion](https://www.mongodb.com/docs/manual/reference/operator/aggregation/scoreFusion/)).
- OpenSearch's `arithmetic_mean` is `Σ wᵢsᵢ / Σ wᵢ` over the sub-queries that hold the document, and gives 0 when the sum of the weights is 0 (`ArithmeticMeanScoreCombinationTechnique.java:43-59`). Milvus merges by `max`, `sum` or `avg` (`mv_merge.go:46-48, 771-800`). Elasticsearch names its identity normalizer `none` (`IdentityScoreNormalizer.java:16`) and divides by `sqrt(Σ s²)` in `l2_norm` (`L2ScoreNormalizer.java`).

Supersedes in part:

- [ADR 0007](./0007-reciprocal-rank-fusion-is-the-default-fusion-with-k-60-and-ranks-from-1.md), for the three fusion factories, the `weights` option of `FusionRetriever`, the `RangeError` for weights that are not one for each list, and `checkWeights` of `src/sum-on-id.ts`. RRF with k 60 and ranks from 1 stays the default, and so do the rules of its amendments: weights as given, the edges of min-max and of mean ± 3σ, the first passage and the first vector, the order of ties, and the weight rule of #5720.
- [ADR 0008](./0008-a-search-is-composed-of-retrievers-that-wrap-retrievers-and-a-list-of-postprocessors.md), for the default `fusion` of `MultiQueryRetriever`: `new RankFusion()`.
- [ADR 0014](./0014-a-retrieve-call-answers-with-the-retrievers-that-answered-and-names-those-that-were-unavailable.md), for `weights: { [name]: number }` and its considered option "a list of children with a weight beside each". The weight is on each entry of the record of retrievers.
- [ADR 0015](./0015-a-passage-is-typed-by-its-metadata-and-only-a-stored-passage-has-source-seq-start-and-end.md), for `Fusion<in out P>` and its `NoInfer` slot. The port has no passage type.

## Decision

- **A fusion fuses ids.** `RankedDoc = { id }` is an item of a list of order only, whose place is its rank. `ScoreDoc = RankedDoc & { score }` is an item of a scored list (Lucene `ScoreDoc`). `ScoreDoc` is an intersection, not a flat type, so that TypeScript infers the fields of a fusion besides the id from it.
- **A list travels with its name and its weight.** `FusionInput<D> = { name, docs, weight }`. `interface Fusion<in D extends RankedDoc> { fuse(inputs): ScoreDoc[] }`. A count of weights that differs from the count of lists cannot be written. `in D`: a fusion of ranked docs fuses scored docs too. `fuse` is not generic, so `island/no-generic-port` passes, and a host writes its own fusion over ids with no assertion.
- **The strategies.** `ScoreNormalizer.normalize(score, list: ListScores)`, where `ListScores` gives `min`, `max`, `mean`, `std` (population, ddof 0) and `l2`, each computed on its first read in the order of the list. `RankNormalizer.normalize(rank, length)`, with ranks from 1. `Combination.combine(contributions)`, the `{ score, weight }` of each input that holds the id, in input order, a weight of 0 among them. The package ships `minMax()` (1 when all scores are equal), `distributionBased()` (population σ, not clipped, 0.5 when σ is 0), `none()`, `reciprocalRank({ k = 60 })` (k an integer of 1 or more), `sum()` (`Σ w·s` from 0), `max()` (the greatest `w·s`, #5585) and `arithmeticMean()` (`Σ w·s / Σ w`, 0 when `Σ w` is 0).
- **Two families, after MongoDB.** `RankFusion { normalizer?, combination? }` reads the order only, and with no options it is reciprocal rank fusion, `reciprocalRank({ k: 60 })` and `sum()`, as `$rankFusion` is. `ScoreFusion { normalizer, combination }` reads the scores, and takes both with no default, because the leaders split on both: MongoDB `avg`, Elasticsearch and Qdrant `sum`, OpenSearch `arithmetic_mean`. The three old fusions are compositions with the same numbers: `new RankFusion({ normalizer: reciprocalRank({ k }) })`, `new ScoreFusion({ normalizer: minMax(), combination: sum() })` and `new ScoreFusion({ normalizer: distributionBased(), combination: sum() })`. #5585's fusion is `new ScoreFusion({ normalizer: none(), combination: max() })`.
- **One private core** (`src/fuse.ts`) does the shared steps in this order: the weight rule of #5720, with a `RangeError` "The weight of <name> is a finite number of 0 or more, not <w>" and `fuse([])` giving `[]`; for `ScoreFusion` only, a `TypeError` for an input score that is not finite (#5700), which names the id and the input; the normalizer of each input, whose result must be finite, else a `TypeError` that names the id and the input; the grouping by id in the order of first appearance, with one `combine` call for each id, whose result must be finite, else a `TypeError` that names the id and the inputs; a stable sort, best first.
- **`FusionRetriever` takes `retrievers: { [name]: { retriever, weight? } }`**, with a weight of 1 when absent, as the `weight` of Elasticsearch's rrf retriever and MongoDB's `weights`, and `fusion?: Fusion<RankedDoc & F>`, `new RankFusion()` when absent. `F` is inferred from the fusion: `{ score: number }` under a `ScoreFusion`, so each retriever must give scored passages, and `unknown` under a `RankFusion`, so any retriever compiles. Each list becomes docs as `{ ...item, id: item.passage.id }`. The fused ids get the passage of the first input that holds them and the first vector that an input gives. It checks the weights when it is made, with the names of the retrievers, and gives the fusion one input for each retriever, an empty one for a retriever that did not answer. A host fusion that gives an id of no input is a `TypeError`.
- **`MultiQueryRetriever<P, F>`** takes `fusion?: Fusion<RankedDoc & F>` by the same rule. Its inputs are `query`, `version 1` … `version n`, each with the weight 1.
- **Deleted, with no alias:** `reciprocalRankFusion`, `relativeScoreFusion`, `distributionBasedScoreFusion`, `sumOnId`, `scoresOf`, `Fusion<P>`, the `weights` option, the `RangeError` "one weight for each list" and the `TypeError` for a passage without a score. The types now prevent both errors.

## Considered Options

- **Keep `Fusion<P>` over passages, and add a fusion over ids beside it.** It lost: two ports for one job, and every engine leader fuses ids.
- **Defaults for `ScoreFusion`, such as `minMax()` and `sum()`.** It lost: the leaders split on both the normalizer and the combination, so a default would be one leader's choice presented as the standard.
- **The whole list for a normalizer, as Elasticsearch's `ScoreNormalizer.normalizeScores` and OpenSearch take it.** It lost: a host normalizer over the whole list must also keep the order and the ids. `ListScores` gives each score its statistics and keeps the loop in the core. The name is coined; no leader passes statistics.
- **`sources` for the record of `FusionRetriever`**, as the first text of the direction said. It lost on Ezz's choice: Elasticsearch's rrf and linear retrievers say `retrievers: [{ retriever, weight }]`, the option was already `retrievers`, and "source" is a glossary word for the row key of a passage.
- **A flat `ScoreDoc = { id, score }`.** It lost in the type probe: TypeScript then infers `F` as the whole doc, and six cases that should compile fail (`flat.out` of the paper's probes).

## Consequences

- A host fusion is written over ids: `const first: Fusion<RankedDoc> = { fuse: (inputs) => … }`.
- `@zukhruf/mteb` moves onto `RankFusion`, `ScoreFusion` and `sum()` with its own host normalizers for MTEB's edge values (0.5 for equal scores, a clip to [0, 1], `rrfK` from 0). It takes the checks of the core: a weight that is negative, not finite, or all 0 is a `RangeError`, and a NaN score a `TypeError`. MTEB accepts both silently; Ezz accepted the deviation.
- `max()` multiplies the score by the weight, so a weight of 0 gives 0, and 0 ranks above a negative raw score (#5585's rule, "score = weight × score, max per id").
- `sum()` starts from 0, so a first contribution of `-0` becomes `0`. Only `distributionBased` under a weight of 0 can give `-0`; the two are equal under `===`.
- The consumers (elt's vectorizer tests, text2sql's two playground searches, April's bridge) write `{ retriever }` entries when they take this release.

## Confirmation

- `src/fusion.test.ts`: the old fusions' scores and orders "to the last bit" through the compositions (golden tables, `RankFusion` and `ScoreFusion` with `minMax` and `distributionBased`); a `test.each` table for each strategy; `ListScores` read by a host normalizer; the weight rule of #5720 for each family; a host normalizer and a host combination that give NaN or ±Infinity, each a `TypeError` that names the id and the input or inputs; `ScoreFusion` refusing a score that is not finite before it normalizes any list; `max()` keeping the greatest score of a shared id, a weight of 2 on 0.3 above 0.5, and a weight of 0 giving 0 (#5585); `arithmeticMean()` giving 0 when every weight is 0.
- `src/fusion-retriever.test.ts` and `src/multi-query-retriever.test.ts`: weights on each entry give the same four scores as the old `weights` record; a host `Fusion<RankedDoc>` with no assertion; the failure and abort tests unchanged.
- `type-tests/published-types.ts`, compiled against `dist` with TypeScript 7 by `src/published-types.test.ts`: a `ScoreFusion` over a retriever of order only (TS2322), and a score fusion of a fusion compiles.
- Mutation proof of the core and the strategies: about 75 mutants, each caught but one equivalent (the build of part (b)). The gate of the release: `retrieval:test` 393 tests, 336 pass, 0 fail, 57 skipped (the SQL Server suites on arm64, #5469).
