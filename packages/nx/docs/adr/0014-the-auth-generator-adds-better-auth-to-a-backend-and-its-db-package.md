# The auth generator adds better-auth to a backend and its db package

Status: Proposed 2026-11-19 (backlog #4719, parts A and B). The Dokploy environment (backlog #4733) and the use of `@zukhruf/authentication` (part C) are not in it.

meddit needs sign-in on its node-app and db package (plan step 4). text2sql, thing and blackboard each set up better-auth by hand. Spike #4716 (2026-11-19) proved how the better-auth CLI works on the layout that the node-app and prisma generators write.

Facts read on 2026-11-19 (spike #4716 and the smoke test below):

- `better-auth` 1.7.26 and the CLI `auth` 1.7.26 release together; the CLI depends on `better-auth` 1.7.26 (`npm view auth@1.7.26 dependencies`). Neither adds an install script: `npm install` passed under `strict-allow-scripts` with no new `allowScripts` key.
- `auth generate --adapter prisma --output <db>/models/auth.prisma` writes the models of the plugins and leaves `schema.prisma` alone. When the output file is missing, it writes its own `generator` and `datasource` blocks first, and `prisma generate` then fails with P1012. One comment line in the file is enough to prevent it.
- The CLI imports the config with c12 and jiti, together with every module the config imports. The config must export `auth` or a default. If the config imports the app's `env.ts` and `startup.ts`, the CLI exits on a missing variable or fails on a database it cannot reach. jiti resolves a workspace package to `dist` unless `NODE_OPTIONS=--conditions=development` is set. With `NODE_ENV=production` the CLI refuses the default secret.
- `auth check schema` reads the generated Prisma client. It exits 0 on a match and 1 on a mismatch (it names the missing column), and 2 when it cannot load the config.
- better-auth 1.7.26 trusts the origin of `baseURL` (`BETTER_AUTH_URL`), the `trustedOrigins` option and `BETTER_AUTH_TRUSTED_ORIGINS` (`context/helpers.mjs`, `getTrustedOrigins`). Sign-up and sign-in check the `Origin` of each request that sends one (`api/middlewares/origin-check.mjs`, `validateFormCsrf`), cookies or not, and answer 403 `INVALID_ORIGIN` for any other origin.
- `createAuthClient()` of `better-auth/react` with no `baseURL` calls `window.location.origin` plus `/api/auth` (`client/config.mjs`, `utils/url.mjs` `withPath`). It ignores Vite's `import.meta.env.BASE_URL` of `/`.
- The Vite proxy of a react-app has `changeOrigin: false`, so the backend gets the `Origin` of the page: `http://localhost:5173` under `nx run <web>:dev`, and `https://web.<scope>.localhost` under the `portless` target (portless 0.18 serves `--name` on 443 with TLS, and keeps the `Origin`). Neither is `BETTER_AUTH_URL` (`http://localhost:<PORT>`), so the part A values refuse sign-up from the web app. A portless proxy with another TLD (`--tld`) or a prefix sends another origin.
- `zukhruf/no-depends-on-project` of `@zukhruf/eslint` rejects `dependsOn` entries that name projects. It asks for `^<target>`.

## Decision

The package gets the generator `auth` in `generators.json`. The README section `## auth generator` lists the files it writes.

1. **The options are two project roots, `backend` and `db`, and both are required.** The prisma and pair generators also take project roots. Three guards stop the generator with exact messages: the backend has no `sdk-it.config.ts` (it is not a node-app); the db has no `prisma.config.ts` and no `createPrisma` in `src/index.ts` (it is not a db package of the prisma generator); `startup.ts` does not import the db package (the prisma generator has not wired the db into this backend). The generator runs `init` first (ADR 0010 decision 4).
2. **The auth is a factory, `createAuth({ prisma, secret, baseURL, trustedOrigins })` in `src/auth.ts`.** It reads no environment and imports neither `env.ts` nor `startup.ts`. It turns on `prismaAdapter(prisma, { provider: 'postgresql' })` and `emailAndPassword`. `startup.ts` calls it with the client that the prisma generator wired and with the validated environment. `trustedOrigins` comes from `ALLOWED_ORIGINS`, the list that CORS reads.
3. **The CLI loads `src/auth.cli.ts`, a module with no side effects.** It exports `auth = createAuth(...)` on `createPrisma({ connectionString: process.env.CONNECTION_STRING ?? '' })`, which opens no connection until a query. The secret and the URL are placeholders. The runtime and the CLI call the same factory, so both always have the same plugins. The module is in `src/`, so `typecheck` checks it against the factory, and the bundle leaves it out because `server.ts` does not import it.
4. **The routes are mounted from `src/routes/auth.route.ts`, and the handler loads `startup.ts` on the first request, not when `app.ts` is imported.** The route is `app.on(['POST', 'GET'], '/api/auth/*', ...)`, from better-auth's Hono guide. `app.ts` mounts it with one line, the way pair mounts the UI, and the line goes before the pair UI mount and before `notFound`. `app.test.ts` imports `app.ts`. If `app.ts` imported `startup.ts`, every test would need a database and the auth variables. `server.ts` loads `startup.ts` first, so the import inside the handler only reads a module that is already loaded. esbuild bundles that import as the `init_startup()` promise, which resolves once. The smoke test signed up through the bundle.
5. **`env.ts` declares `BETTER_AUTH_SECRET: z.string().min(32)` and `BETTER_AUTH_URL: z.url()`.** The generator inserts them at the same marker the prisma generator uses. `.env.example` gets an empty secret and `http://localhost:<PORT>`. `.env` is the developer's copy and is not committed. It gets a random secret of its own (`randomBytes(32)` in base64url, 43 characters) and the same URL. A key that is already there keeps its value, so a second run does not rotate the secret.
6. **The models come from the CLI, not from the generator.** The generator writes a placeholder `models/auth.prisma` with one comment line (see the facts above). After the install, a task runs `nx run <backend>:auth:generate`. The generator writes no migration: the first migration belongs to the consumer (ADR 0012).
7. **The backend gets two `nx:run-commands` targets in its `package.json`, where node-app writes its own targets.** `auth:generate` runs `npx auth generate --adapter prisma --config src/auth.cli.ts --output <db>/models/auth.prisma --yes` and then `nx run <db>:generate`. `auth:check` runs `npx auth check schema --config src/auth.cli.ts`. A check never writes (ADR 0002). Both depend on `^generate`, because the CLI imports the db package's development export, and that export imports the generated client. Both set `NODE_OPTIONS=--conditions=development` and `NODE_ENV=development`, and run in the project root. The spike asked for `NODE_ENV` unset, because the CLI refuses the placeholder secret only in production. The target sets `development` instead, so it also works in a shell that sets `production`, and the generator never has to read `process.env` (`island/no-process-env`).
8. **`better-auth` is a dependency of the backend, and the CLI `auth` is a root devDependency.** Both are pinned exactly at 1.7.26 in `appPackageVersions`, and a test checks that the two pins are equal. The CLI goes in the root because it is a workspace tool, like `@sdk-it/cli` of node-app (ADR 0010 decision 8). The app manifest is the deploy manifest, and it declares only what the bundle leaves external.
9. **A second run keeps the files it wrote and adds nothing twice.** It writes `auth.ts`, `auth.cli.ts`, `auth.route.ts` and the placeholder only when they are missing, because the consumer adds plugins there. Each insert first checks for its own line. The targets are rewritten on each run, as node-app rewrites its own targets.
10. **An optional `--web` takes the project root of a react-app, and stops with an exact message when it has no `vite.config.ts`**, the guard and message of pair. It writes `src/auth-client.ts`, `export const authClient = createAuthClient()` from `better-auth/react`, only when missing, and adds `better-auth` at the same exact pin to the web's `dependencies`. The client has no `baseURL`: in development the Vite proxy sends `/api` to the backend, and in production the backend of pair serves the web from its own origin, so the page origin plus `/api/auth` is the backend's auth in both. The route guard comes with `@zukhruf/authentication` (part C).
11. **`--web` adds the development origins of the web app to `ALLOWED_ORIGINS`, and leaves `BETTER_AUTH_URL` alone.** Both env files get `http://localhost:5173` (the port of the react-app's `vite.config.ts`) and `https://<name>.localhost`, where `<name>` is the `--name` of the web's `portless` target. Origins already in the list stay, in their order, and a comment above the line says that better-auth trusts them. `BETTER_AUTH_URL` stays the URL of the backend: the backend runs at one URL in both modes, while the web origin depends on the mode. better-auth sets host-only cookies, and a host-only cookie of `localhost` is sent to each port, so a link to the backend's URL signs the browser in for the web on `localhost:5173` too. CORS of the node-app already returns each origin in development, so the list changes nothing there.
12. **`insert` and the env-file helper are copies (strike 2).** `insert` is the prisma generator's, with "auth" in its message in place of "the database". `addEnvEntry` is prisma's `addEnvKey`, plus a value. Interim rule: mirror every fix in both copies, and name both files in the commit. Backlog item #4732 waits for a third consumer.

## Considered Options

- **The handler imports `auth` from `startup.ts` when `app.ts` is imported.** REJECTED. `app.test.ts` would need a database and the auth variables (decision 4).
- **Mount the routes in `server.ts`, after `app` is imported.** Not selected. The mount would come after the pair UI mount and `notFound`, and the one file that shows how the app's routes are assembled would no longer show this one.
- **A CLI config that imports `startup.ts`, or one `auth` instance shared by the app and the CLI.** REJECTED by the spike. The import connects to the database, and `env.ts` exits when a variable is missing.
- **The generator writes the models itself.** REJECTED. The CLI knows the models of each plugin and version. A copy in this package would drift with every release of better-auth.
- **`dependsOn: [{ projects: [<db>], target: 'generate' }]`.** REJECTED by `zukhruf/no-depends-on-project`. The import graph already orders the db package before the backend.
- **The CLI `auth` in the backend's devDependencies, as the brief worded it.** Not selected (decision 8).
- **`BETTER_AUTH_URL` is the web origin in development (`http://localhost:5173`), as it is the public origin in production.** Not selected. It holds one origin, and the portless origin is another; a backend generated without `--web` would also need a different value, and a second run with `--web` would have to change a key that the developer may have set.
- **Trust every origin in development**, as CORS of the node-app does (`trustedOrigins` as a function that returns the request's origin when `NODE_ENV` is development). Not selected. It would also trust a cross-site form post in development, and the brief asked for values in the env files. It remains the answer if custom portless TLDs become common.
- **A wildcard origin such as `https://*.localhost`.** Not selected: better-auth matches it, but it trusts each app on the machine's portless proxy, and still misses a custom TLD.
- **A guard that the web is paired with the backend.** Not selected. The Vite proxy is in every react-app, and pair is what gives production one origin; the README says to pair first.
- **Using `@zukhruf/authentication` for a middleware that refuses requests.** Deferred to part C: the API of that library is still under review.

## Consequences

- meddit adds sign-in with one command after prisma: `nx g @zukhruf/nx:auth --backend apps/backend --db packages/db`. It then writes its first migration with `prisma migrate diff` and runs `auth:check` (plan step 6).
- After adding a plugin to `createAuth`, run `auth:generate`, write a migration, and run `auth:check` in CI.
- The backend does not start without `BETTER_AUTH_SECRET` and `BETTER_AUTH_URL`. The Dokploy environment must supply them (part B).
- In development, CORS accepts any origin, but better-auth trusts only `ALLOWED_ORIGINS` and `BETTER_AUTH_URL`. `--web` adds the Vite and the default portless origins. A developer whose portless proxy uses another TLD or a prefix adds that origin to `ALLOWED_ORIGINS` in `.env`.
- Smoke test of `--web` on 2026-11-19 (Nx 24.0.6, an `npm pack` tarball of 0.8.34): preset, `node-app apps/backend`, `react-app apps/web`, `pair`, `prisma packages/db --backend apps/backend`, `auth --backend apps/backend --db packages/db --web apps/web`. `run-many -t typecheck lint build test` passed, and a second run changed no file. On a `postgres:18-alpine` with the schema from `prisma migrate diff`, with `serve` and the web's `dev`: `POST http://localhost:5173/api/auth/sign-up/email` with `Origin: http://localhost:5173` answered 200 and a session cookie; with `Origin: http://localhost:5174` it answered 403 `INVALID_ORIGIN`; with `ALLOWED_ORIGINS` emptied (the part A values) the same request from `http://localhost:5173` answered 403 `INVALID_ORIGIN`. Under the `portless` target, `POST https://web.acme.localhost/api/auth/sign-up/email` with that origin answered 200, and the same request on a second TLD of the same proxy (`--tld`) answered 403. In Chromium on `http://localhost:5173`, `authClient.signUp.email` and `authClient.getSession` of the generated `src/auth-client.ts` called `/api/auth/sign-up/email` and `/api/auth/get-session` on the page origin, both 200.
- Smoke test of 2026-11-19 (Nx 24.0.6, an `npm pack` tarball): preset, `node-app apps/backend`, `prisma packages/db --backend apps/backend`, `auth --backend apps/backend --db packages/db`. The task wrote 4 models (User, Session, Account, Verification). `auth:check` exited 0. With `session.token` removed it exited 1 ("Missing columns session.token"), and after `auth:generate` it exited 0 again. `nx run-many -t typecheck lint build test` passed for the 3 projects; `app.test.ts` ran with no database. A second run of the generator changed no file. The production bundle, on a `postgres:18-alpine` with the schema from `prisma migrate diff`, answered `POST /api/auth/sign-up/email` and `GET /api/auth/get-session` with 200.
