# A file store holder is judged by its presence

The file lock stores keep a record for each caller: a lock file, or a ticket. A waiter must know if the caller of a record still runs. Before, the waiter read the process ID and the host name in the record. Tests in real containers showed that this check was wrong in five cases. First, two containers on one machine can share a lock directory and a host name, but each has its own process IDs. A waiter did not find the process ID of a live holder in its own container, and it removed that holder: two holders ran at the same time. Second, a stopped holder in a container with a different host name was never removed, because a different host name meant a different machine. Third, a stopped holder with the process ID 1 was never removed when the waiter itself was the process 1 of its container. Fourth, a worker thread that stopped kept its key, because its process continued. Fifth, a zombie process still answers `kill(pid, 0)`, so it looked alive. Thus each caller now keeps a **presence**: an exclusive SQLite transaction on `<key>.lock.<id>.presence`, from before its record appears until after its record is gone. The kernel ends the transaction when the process or the thread of the caller stops. A waiter reads the presence file read-only. If the read succeeds, the caller stopped. A read-only open never makes a file. If the presence file does not exist but the record still names the caller, the acquire fails with an error that gives the names of both files: nobody can tell if that caller runs. Only one caller deletes each presence file: the caller after it removed its own record, or the waiter that removed that record.

## Considered Options

- **The process ID and the host name.** This was the check before. It is wrong for containers, worker threads, and zombie processes, as the five cases show.
- **A listening socket for each caller.** The kernel closes the socket when the caller stops. Tests gave the correct answer for a killed holder, a zombie process, a worker thread, a frozen holder, and containers that share a volume. But a waiter gets an answer only while the caller accepts connections. A frozen or busy caller does not accept them, so the kernel queue fills. On macOS, after 128 waiting connections, the kernel answers `ECONNREFUSED`. That is the same answer as for a stopped caller, so a waiter removes a live holder. On Linux the answer is `EAGAIN`, which is different, but Linux also refuses a socket path of more than approximately 107 bytes.
- **A heartbeat.** The caller writes the time again and again, and a waiter removes a record with an old time. A frozen caller would then lose its key while it can still continue and write. That gives two holders by design.
- **A file lock without SQLite.** Node.js has no `flock`. The Node.js project closed the requests for it as not planned ([nodejs/node#49256](https://github.com/nodejs/node/issues/49256), [nodejs/node#54446](https://github.com/nodejs/node/issues/54446)), and libuv refused file locks for all platforms. A native addon, for example `fs-ext`, is a compiled dependency for each platform.
- **A FIFO.** The kernel knows if a reader has a FIFO open. But Node.js cannot make a FIFO, and Windows has none.
- **One presence for each process or each thread.** A presence for each process is wrong for worker threads. A presence for each thread is shared by many records, so no record can delete it, and a caller that gives up keeps it.

## Consequences

- A waiter removes a stopped holder in containers on one machine, for a zombie process, and for a worker thread that stopped. A waiter never removes a live holder or a frozen holder.
- A waiter of `TicketQueueFileStore` keeps one open file while it waits. A waiter of `LockFileStore` keeps a presence only while it tries to create the lock file.
- Each check opens a file. In a test of 500 acquires and releases, `LockFileStore` took approximately 3% more time, and `TicketQueueFileStore` took the same time. The fencing token write takes most of the time.
- A waiter of `TicketQueueFileStore` reads the presence of the first ticket before it reads the queue. A stopped caller never writes again, so the queue that the waiter writes back is current.
- A caller that gives up ends its presence and leaves its ticket in the queue. The next waiter that finds the ticket at the front removes it. No background loop removes it.
- A record of an older version has no presence file. The acquire fails with an error that gives the names of both files. Stop the processes of the older version, then delete the record.
- A caller that stops between two steps can leave an empty presence file. It has no lock, so it blocks no key.
- On Windows, the delete of a presence file that another program holds open fails after 1 second. The release then rejects with an error that gives the name of the file, but the key is free.
- `LockFileStore` needs SQLite, as all host lock stores do. A SQLite-free check is not possible with Node.js 26 alone.
