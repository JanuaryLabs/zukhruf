# A process says its protocol version before its first request

The processes of a socket lock store send lines of JSON to the leader. Before package version 0.3.1, these messages had no protocol version. A process closed a connection when it got a line that it did not know. Thus, if a new package version changed a message, a process and a leader of two package versions would close their connection, or read a message incorrectly. Now each process sends `{"op":"hello","version":1}` before its first request. The number is `PROTOCOL_VERSION`. It changes only when a message changes, so processes of two package versions can share a directory when their messages are the same. If the leader speaks the same protocol version, it answers `{"op":"welcome"}` and then serves the process. If the `hello` gives another protocol version, the leader answers `{"op":"refused","version":<its protocol version>}` and closes the connection. A process that gets `refused` fails its acquire with `ProtocolVersionError`. The error gives both protocol versions. If the first line is not a `hello`, the leader does not answer, and it does not close the connection. It reads and ignores the next lines. The connection closes when the other process closes it, or when the term of the leader ends.

A process of 0.3.0 or earlier does not send `hello`, and it cannot read `refused`. It closes a connection when it gets a line that it does not know, and then it connects again at once. Each answer that it can read gives the state of a key, and a closed connection tells it that the leader is lost. No answer can tell it that the leader does not serve it. Thus the leader gives no answer. For the same reason, the `hello` and the `refused` answer must keep their shape in each new protocol version: they are how two package versions find out that they differ.

A leader of package version 0.3.0 or earlier does not know `hello`. It closes the connection without an answer, and it keeps its term. But a leader that stops also closes connections without an answer: on Windows, a named pipe accepts a connection while its leader stops. (A Unix socket of a stopped leader refuses the connection.) Thus a closed connection does not prove that the leader speaks another protocol version. The term shows the difference. A leader that stops ends its term within moments. A leader of 0.3.0 or earlier keeps its term. After a closed connection, the process does one campaign that does not wait for the term. If it does not win, it connects again and sends `hello` again. Between two tries, it waits one poll interval. If a new leader answers, the process follows it. The acquire fails with `ProtocolVersionError` only when the leader keeps its term and closes each connection for 1 second in total (`HANDSHAKE_PATIENCE`).

## Considered Options

- **No protocol version.** This was the behavior before 0.3.1. When a message changes, a process and a leader of two package versions close their connection, or read a message incorrectly. Neither process shows an error.
- **The leader refuses and closes each connection that does not start with `hello`.** This was the behavior from 0.3.1 to 0.3.6. A process of 0.3.0 cannot read `refused`, so it closed the connection and connected again at once. In a test with real processes on macOS, a process of 0.3.0 connected again 98,985 times in 5 seconds to a leader of 0.3.6. The leader used 2,300 ms of CPU time, and the process used 3,125 ms. The acquire of the process did not end. With the leader of 0.3.7, the same test showed 1 connection and 0 ms of CPU time in each process.
- **Answers with the messages of 0.3.0.** The leader could answer `busy` to each request and `rejected` to each reassert. Each of these answers gives an incorrect state of a key. For example, a process that skips if busy would skip work that no process does. Also, the leader would need the messages of 0.3.0 in each later protocol version.
- **A refusal after a delay.** The process still connects again in a loop, only more slowly. It still gets no information.
- **The package version in the `hello`.** Each new package version would then refuse all earlier package versions, also when their messages are the same. A rolling upgrade would always fail.
- **A leader that speaks more than one protocol version.** Only one protocol version exists now. A leader that speaks two protocol versions needs code for each message of each protocol version. This option is possible when a second protocol version exists.
- **A closed connection proves an older leader.** A normal failover would then fail. A holder whose `hello` gets to a leader that stops would get `ProtocolVersionError`.
- **One long campaign after a closed connection.** This was the first behavior. The process did one campaign that waited up to 1 second for the term. If another process had the new term already, the process waited the full second. The default grace window is 500 ms. Thus the holder connected to the new leader after the grace window, and the new leader refused its reassert. The new leader granted the key to a waiter while the task of the holder still ran. On Windows CI, the test "a holder keeps its key when the leader dies, and a waiter enters only after it releases" failed three times this way. Its journal showed `holder:enter` and then `waiter:enter`.

## Consequences

- Package versions 0.3.1 and later speak protocol version 1, so they can share a directory. In a test, a leader of 0.3.1 and a process of 0.3.5 shared one. `src/lock-stores/mixed-version.release.test.ts` checks each change against the latest release, with a leader of each version.
- A process of 0.3.1 or later fails its acquire with `ProtocolVersionError` in two cases:
  - The leader speaks another protocol version. The acquire fails at once. `theirs` gives the protocol version of the leader.
  - The leader is of 0.3.0 or earlier. The acquire fails after approximately 1 second (1,007 ms in a test). `theirs` is `undefined`.
- A process of 0.3.0 or earlier gets no error from a leader of 0.3.1 or later, and its requests get no answer. With a leader from 0.3.1 to 0.3.6, it connects again without a pause, and the leader must accept and refuse each connection. With a leader of 0.3.7 or later, it stays connected and uses no CPU time. A rolling upgrade from 0.3.0 or earlier is not safe.
- When a leader that stops closes a connection, the holder follows the new leader in approximately one poll interval (10 ms by default). This is less than the grace window (500 ms by default). The test "a holder hung up on by its stopping leader keeps its key from a successor that already leads" shows this.
- A leader refuses each connection whose first line is a `hello` with another protocol version or with no protocol version. It closes the connection after it writes `refused`, also when the other process keeps its side open.
- A leader does not answer a connection whose first line is not a `hello`. It reads and ignores the next lines, so it sees when the other process closes the connection. Each such connection uses one file descriptor of the leader until it closes.
- The `hello` and the `refused` answer must keep their shape. If a leader does not see a `hello` as a `hello`, a process of a later protocol version gets no answer and waits.
- `HANDSHAKE_PATIENCE` must be longer than the time that a leader needs to end its term when it stops. If it is shorter, a holder in a normal failover gets `ProtocolVersionError`.
- When you change a message, change `PROTOCOL_VERSION`. Then processes of the old and the new package version refuse each other with an error, and they do not read a message incorrectly.
- When you add a request, do not change `PROTOCOL_VERSION`. Add the request to `ADDED_OPS`, so that the `welcome` lists it. See [ADR 0016](0016-a-leader-lists-the-requests-that-it-added.md).
