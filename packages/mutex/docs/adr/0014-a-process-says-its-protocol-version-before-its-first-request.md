# A process says its protocol version before its first request

Rewritten on 2026-10-26. This version supersedes the handling of processes of package version 0.3.0 and earlier in the earlier text of this ADR (the leader gave them no answer, and a process waited up to 1 second, `HANDSHAKE_PATIENCE`, for a leader of 0.3.0 to end its term). It also supersedes [ADR 0016](./0016-a-leader-lists-the-requests-that-it-added.md). This package is not designed for processes of earlier package versions.

The processes of a socket lock store send lines of JSON to the leader. Processes of two package versions can share a directory. If a message changed between the two versions, the leader or the process can read a message incorrectly. An incorrect read can give the key to two holders, and no process shows an error. Thus each process sends `{"op":"hello","version":2}` before its first request. The number is `PROTOCOL_VERSION`. It changes when a message changes. Version 2 started on 2026-10-26, when the `welcome` stopped listing the requests added after version 1. Thus a leader of this version refuses each process of package versions 0.3.1 to 0.3.44, and each of their leaders refuses a process of this version. If the leader speaks the same protocol version, it answers `{"op":"welcome"}` and then serves the process. If the first line is not a `hello` of the same protocol version, the leader answers `{"op":"refused","version":<its protocol version>}` and closes the connection. A process that gets `refused` fails its acquire with `ProtocolVersionError`. The error gives both protocol versions. The `hello` and the `refused` answer must keep their shape in each new protocol version: they are how a leader and a process find out that they cannot read each other.

A leader that stops closes connections without an answer: on Windows, a named pipe accepts a connection while its leader stops. (A Unix socket of a stopped leader refuses the connection.) Thus a closed connection is a failover, not a refusal. After a closed connection, the process does one campaign that does not wait for the term. If it does not win, it connects again and sends `hello` again. Between two tries, it waits one poll interval. If a new leader answers, the process follows it.

## Considered Options

- **No protocol version.** This was the behavior before 0.3.1. When a message changes, a process and a leader of two package versions read a message incorrectly. Neither process shows an error.
- **The package version in the `hello`.** Each new package version would then refuse all earlier package versions, also when their messages are the same.
- **A leader that speaks more than one protocol version.** A leader that speaks two protocol versions needs code for each message of each protocol version. This package is not designed for earlier versions.
- **A list of added requests in the `welcome`.** This was [ADR 0016](./0016-a-leader-lists-the-requests-that-it-added.md). It let a process of a later package version use a leader of an earlier one with the same protocol version. This package is not designed for earlier versions, so a new request changes `PROTOCOL_VERSION`.
- **A closed connection proves a leader of another protocol version.** A normal failover would then fail. A holder whose `hello` gets to a leader that stops would get `ProtocolVersionError`.
- **One long campaign after a closed connection.** The process did one campaign that waited up to 1 second for the term. If another process had the new term already, the process waited the full second. The default grace window is 500 ms. Thus the holder connected to the new leader after the grace window, and the new leader refused its reassert. The new leader granted the key to a waiter while the task of the holder still ran. On Windows CI, the test "a holder keeps its key when the leader dies, and a waiter enters only after it releases" failed three times this way. Its journal showed `holder:enter` and then `waiter:enter`.

## Consequences

- A process fails its acquire at once with `ProtocolVersionError` when the leader speaks another protocol version. `theirs` gives the protocol version of the leader.
- A leader refuses each connection whose first line is not a `hello` of its protocol version: a `hello` of another protocol version, a `hello` with no protocol version, a line that is not JSON, a request, or a line longer than 1024 bytes. It closes the connection after it writes `refused`, also when the other process keeps its side open.
- When a leader that stops closes a connection, the holder follows the new leader in approximately one poll interval (10 ms by default). This is less than the grace window (500 ms by default). The test "a holder hung up on by its stopping leader keeps its key from a successor that already leads" shows this.
- The `hello` and the `refused` answer must keep their shape. If a leader does not see a `hello` as a `hello`, a process of a later protocol version cannot find out that it differs.
- When you change a message or add a request, change `PROTOCOL_VERSION`. Then processes of the old and the new package version refuse each other with an error, and they do not read a message incorrectly.
