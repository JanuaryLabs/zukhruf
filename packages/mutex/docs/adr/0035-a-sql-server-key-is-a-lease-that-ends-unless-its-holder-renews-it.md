# A SQL Server key is a lease that ends unless its holder renews it

Status: Accepted 2026-11-25 by Ezz (datahub #5617), for option (a) with the clock of the server: "just go, man, do it". His defaults answer the open questions of the draft: see [Answers to the open questions](#answers-to-the-open-questions). The reproduction is `src/lock-stores/sqlserver/sqlserver-store.vanished-holder.test.ts`. It failed with the session lock, and it passes with the lease.

Changed in part on 2026-11-28 (#5973) for the count of a renewal. The holder's two intervals count from the moment its statement goes to the server, after its session is there, for the grant and for each renewal; before, they counted from the start of the grant or of the renewal, which includes the connect. Over a link of about 80 ms a new session took 0.6 to 1.3 s, so the first renewal began more than two intervals after the count started and the lease was lost at once. The rule stays safe: the server writes `renewed` when it runs the statement, which is later than the send.

Before this decision, `SqlServerStore` held a key with a session-owned application lock: `sp_getapplock` with `@LockOwner = 'Session'` and no time limit. The README said: "The server releases the lock when the session ends, so a holder that stops never leaves a key locked". This is true only when the server learns that the session ended. A holder that vanishes tells the server nothing. The store page already said it: "A holder machine stops with no reset: the server sees the end of the session only through its own TCP keep-alive. Until then, the key stays held, and waiters wait."

## The problem

**What occurred in production.** datahub's backend runs its ELT writer with `LeaderSelector` over the key `datahub/warehouse-writer` of `SqlServerStore` (`apps/backend/src/server.ts`, `heartbeatInterval: 10_000`). On 2026-11-24, the release swapped the slots of the App Service DAHubWebApp at 18:49 to 18:52 UTC. The container logs of App Service show that each old container stopped 0.3 to 0.6 s after its stop began, although the grace period is 5 s. Thus the shutdown of the old writer did not run, and it did not release the key. The new build started at 18:50:30, and its `sp_getapplock` waited 3,071,181 ms. At 19:42:11, the lock came free with no container stop and no log line from any process, and the new build held it in the same second. No process logged "holds the warehouse" between 18:52 and 19:42. Thus for 51 minutes no live process held the key, and production had no ELT writer. The most probable holder is the session of the old container that the swap stopped. The session list of that time is gone, so this is not proven. The evidence is in the CORRECTION and REPRODUCED sections of datahub #5617.

**A reproduction in Docker.** A `sqlcmd` container took the lock on SQL Server 2022 in another container. Then the test cut it from the network with `docker network disconnect`, so no FIN and no reset went out, and stopped it. The dead session still held the lock at 0, 15 and 31 s. SQL Server ended it at 38 s, with its own TCP keep-alive, and a waiting `sp_getapplock` got the lock then (datahub scratchpad `repro-5617/repro.sh`).

**A reproduction in this package.** The test puts a TCP hop between the holder and the server. `vanish()` stops the hop forwarding in both directions, and from then on it forwards no close and no reset either. It keeps its connection to the server open, as a gateway does for a client machine that is gone. The holder's own lease aborts after two heartbeats ([ADR 0013](./0013-a-lost-lease-aborts-the-signal-of-the-lease.md)), and the store closes its session. The close does not reach the server, so the server keeps the lock, and the waiter waits until the test's limit. The test asserts no upper limit on real time, because load breaks a claim about speed (`zukhruf/no-wall-clock-bound`); only a lease that expires can give the waiter the key while the hop keeps the old session open. `proxyTo` of `src/testing/tcp-proxy.ts` is not enough for this test: it stops the bytes, but it still forwards a close, so the end of the session reaches the server.

**Why the server does not see the end.** A session lock lasts as long as the session. The server ends a session when the connection closes or resets, on `KILL`, or when its TCP keep-alive finds no peer. Azure SQL Database has two connection policies ([Choosing the best connection policy](https://learn.microsoft.com/azure/azure-sql/database/connectivity-connection-policy), ms.date 2026-10-23). With Proxy, "All traffic continues through the gateway for the lifetime of the connection". The TCP peer of the server is then the gateway, not the client, and a live gateway answers the keep-alive of the server. With Redirect, "The gateway redirects the connection to the database host and is then removed from the data path". The policy of the logical server centraldblin is not known: the service principal of DA sees no SQL server. With Default, a connection from Azure uses Redirect if the driver supports TDS 7.4, and "Existing private endpoints using Default use Proxy on port 1433".

**What the heartbeat did.** The heartbeat was on one side only. The holder asked `APPLOCK_MODE` each `heartbeatInterval`. If no answer arrived, its signal aborted with `LeaseLostError`, and it stopped. But nothing told the waiter. The key belonged to the session on the server, not to the heartbeat, so the waiter waited for the server.

## Considered Options

### (a) A lease that ends unless its holder renews it

A row in a table of the caller holds each key: the key's name, the holder, the fencing token, the time of the last renewal, and the lease duration. The holder renews the row each `heartbeatInterval`. Another store takes the key when the lease expired. The row keeps the fencing token of [ADR 0003](./0003-a-fencing-token-on-every-lease.md), so a fenced resource refuses the writes of a late holder.

Precedents, read in their source:

- **Kubernetes `coordination.k8s.io/v1` `Lease`** (`kubernetes/api`, `coordination/v1/types.go`): `holderIdentity`, `leaseDurationSeconds` ("a duration that candidates for a lease need to wait to force acquire it. This is measured against the time of last observed renewTime"), `acquireTime`, `renewTime` and `leaseTransitions`.
- **client-go `leaderelection`** (`tools/leaderelection/leaderelection.go`, commit 4563439f of 2026-10-16): the holder renews each `RetryPeriod` (default 2 s) and stops leading when a renewal does not succeed within `RenewDeadline` (default 10 s). A candidate takes over only when `observedTime + LeaseDuration` is past (`isLeaseValid`, default 15 s). The config rejects `LeaseDuration <= RenewDeadline` and `RenewDeadline <= JitterFactor × RetryPeriod`, so the holder stops before any candidate can take over. The takeover writes the record with a compare: an update of the object that the candidate read. `observedTime` is the local time at which the candidate saw the record change, so the election "is tolerant to arbitrary clock skew, but is not tolerant to arbitrary clock skew rate". With `ReleaseOnCancel`, the holder writes a record with no `HolderIdentity` and `LeaseDurationSeconds: 1` when it stops (`tryRelease`).
- **etcd leases** (`server/lease/lessor.go` and `lease.go`, commit 9d572027 of 2026-07-30): the server grants a lease with a TTL, `refresh` sets `expiry` to the server's `time.Now()` plus the TTL, `Renew` (the KeepAlive of the client) refreshes it, and `revokeExpiredLeases` deletes each lease past its expiry, with the keys that it holds. The server's own clock decides.
- **This package.** The socket lock store already does this between its sessions: a new leader waits for each recorded session until it reasserts, stops, or misses its `leaseDuration` ([ADR 0033](./0033-a-new-leader-grants-nothing-until-each-recorded-session-reasserted-its-keys-stopped-or-missed-its-lease.md), from Chubby §2.9, etcd, Consul and ZooKeeper). The election ends a leader that is silent past the lease duration ([election ADR 0006](../../../election/docs/adr/0006-a-candidate-ends-a-leader-that-is-silent-past-the-lease-duration.md)).

### (b) Keep the session lock, and let the server find a dead client

- **The Redirect connection policy.** Microsoft recommends it: "For production workloads, use explicit Redirect". With Redirect, the keep-alive of the server reaches the client machine, so the server ends the session of a vanished holder. The Docker reproduction shows 38 s. But this is a setting of the server and of the network of each user, not of this package. A private endpoint with Default uses Proxy. Thus the README of the package cannot promise it.
- **TCP keep-alive.** The keep-alive of the server works only against the real peer. Behind a proxy, the gateway is the peer. The [TCP/IP Properties page](https://learn.microsoft.com/sql/tools/configuration-manager/tcp-ip-properties-protocols-tab) (ms.date 2025-12-15) shows the setting for SQL Server on Windows only, and it gives no default. Azure SQL Database has no such setting. The keep-alive that tedious turns on (30 s) protects the client, not the server.

### (c) The holder releases before it stops

`LeaderSelector` and `Mutex` already release the key when their dispose runs, and a test of datahub's writer released the key within 1 s of `SIGTERM`. But on 24 November, App Service stopped each old container in 0.3 to 0.6 s, and the shutdown did not run. A `SIGKILL`, an out-of-memory stop, the loss of a host, or a network partition runs no code at all. In client-go, `ReleaseOnCancel` is an addition to the lease, not a replacement: a lease that the holder does not release still expires.

### (d) A waiter ends the session of a holder that stopped renewing

The holder keeps the session lock, writes its session ID and a renewal time to a row, and a waiter that sees an old renewal runs `KILL` on that session. The [KILL page](https://learn.microsoft.com/sql/t-sql/language-elements/kill-transact-sql) (ms.date 2025-07-09) says that SQL Database "Requires the `KILL DATABASE CONNECTION` permission. The server-level principal login has the `KILL DATABASE CONNECTION` permission", and SQL Server requires `ALTER ANY CONNECTION`. An app role does not have these. The page also says that a session ID "can be reassigned to a new connection", so a late `KILL` can end another process.

### (e) The server writes a keep-alive to the holder

The Docker engine store does this: a holder over SSH gets one byte each 15 s, so the kernel of the engine host ends the connection of a holder that went away ([root ADR 0012](../../../../docs/adr/0012-a-holder-on-a-docker-engine-writes-a-keep-alive-byte-each-15-seconds-so-the-engine-host-ends-the-connection-of-a-holder-that-went-away.md)). In SQL Server, the holder's session would run a batch that sends a message each N seconds (`RAISERROR ... WITH NOWAIT` and `WAITFOR DELAY`). The bound is then the retransmission limit of the far end: `tcp_retries2`, about 924.6 s on Linux ([the Docker engine store page](../stores/docker-engine-store.md)). With Proxy, the far end of the server is the gateway, and its behavior is not documented. The session would also run that batch all the time, and tedious has no MARS, so the heartbeat could not run on it.

### Which clock decides that a lease expired

- **The clock of each waiter** (client-go). A waiter takes over when it saw the same renewal for `leaseDuration` on its own clock. The store already counts its heartbeat on the `clock` that the caller gives, and a test can drive it with a fake clock. But a waiter must watch the row for a full `leaseDuration` before it can take over. `tryAcquire` reads the row once, so it cannot take over a lease that expired, unless the store keeps what it saw at an earlier call. `SqlServerCheckpointStore` of elt uses only `Modes.skipIfBusy()`, which is one `tryAcquire`, so a copy whose run vanished would stay busy for each later run.
- **The clock of the server** (etcd). The statement that takes over compares the last renewal with `SYSUTCDATETIME()` in the same statement. All stores then use one clock, and `tryAcquire` can take over an expired lease in one call. The holder still stops on its own clock, when no renewal succeeded within its deadline. Thus the safety depends only on the rate of the two clocks, as in client-go. A test cannot drive the server's clock, so a test of the takeover waits in real time.

## Decision

Option (a), with the clock of the server. `SqlServerStore` keeps each key as a lease row and no longer uses `sp_getapplock`.

- **The table.** The caller creates it, as it creates the sequence: the store runs no DDL. One row for each key: `name binary(16) NOT NULL PRIMARY KEY` (the first 16 bytes of the key digest, as before), `holder uniqueidentifier NULL` (a random UUID for each grant), `token bigint NOT NULL`, `renewed datetime2 NOT NULL`, and `duration int NOT NULL` (milliseconds, written by the holder, as `leaseDurationSeconds` is in the Kubernetes `Lease`). The option `table` names it, as `sequence` names the sequence. The role of the app needs `SELECT`, `INSERT` and `UPDATE` on it.
- **A grant.** One batch: a compare and set, `UPDATE ... SET holder = @holder, token = NEXT VALUE FOR <sequence>, renewed = SYSUTCDATETIME(), duration = @duration OUTPUT inserted.token INTO @granted WHERE name = @name AND (holder IS NULL OR DATEADD(millisecond, duration, renewed) <= SYSUTCDATETIME())`. When it changes no row and the key has no row, an `INSERT` of the same values, in a `TRY` block that catches only a duplicate key (2627 for the primary key, 2601 for a unique index): the second of two first holders gets no grant. A token in `@granted` is a grant. The token comes from the sequence in the same statement, so a later grant always has a larger token. The name of the table and of the sequence cannot be a parameter, so the batch finds each object with `OBJECT_ID`, quotes it with `QUOTENAME`, and runs the statement with `sp_executesql`.
- **A renewal.** Each `heartbeatInterval`: `UPDATE ... SET renewed = SYSUTCDATETIME() WHERE name = @name AND holder = @holder`. No changed row means that another store took the key: the signal of the lease aborts with `LeaseLostError` ([ADR 0013](./0013-a-lost-lease-aborts-the-signal-of-the-lease.md)). The holder also aborts its signal when no renewal succeeded within two heartbeat intervals, counted on its `clock` from the start of the last renewal that succeeded (the start of the grant at first), because the server writes `renewed` after that start. A holder that lost its lease does not clear its row: the lease ends by itself.
- **The lease duration.** A new option `leaseDuration`, the name that `SocketStore` uses, with a default of 30,000 ms. The constructor throws a `RangeError` when `leaseDuration` is not larger than two heartbeat intervals, as client-go rejects `LeaseDuration <= RenewDeadline`. Thus the holder stops before another store can take its key.
- **A wait.** The store tries the grant each `heartbeatInterval` on its `clock`, as client-go tries each `RetryPeriod`. The in-process queue stays, so one process tries with one caller for each key. The server's lock queue and its push of a grant go: a waiter gets the key at most one interval after a release, and the order between processes is not first come, first served. A cancel rejects at once, and a grant that a running try gets after the cancel is released when its answer arrives.
- **A release.** `UPDATE ... SET holder = NULL WHERE name = @name AND holder = @holder`. The next try of a waiter gets the key, as in client-go's release. No changed row means that another store took the key, and the signal of the lease aborts.
- **A holder check.** It reads the row: held when `holder` is not `NULL` and the lease did not end on the server's clock. It takes nothing ([ADR 0015](./0015-a-holder-check-never-acquires-the-key.md)).
- **Sessions.** The store takes its sessions from the caller's `connect` ([ADR 0022](./0022-a-database-lock-store-takes-its-session-from-the-caller.md)). A lease does not live on a session, so the store runs each statement on a session of its own and closes it at once: a wait and a held key keep no session open, a `close()` can give a connection back to its pool, and a session can connect again by itself. The type of a session loses `on('end')`: the end of a session is no longer a loss. It keeps `on('error')`, because a driver can emit `error` after the close, and an `error` with no listener stops the process.

### Probes

Each statement form was probed before the build on SQL Server 2022 (16.0.4325.4, the amd64 image under emulation on an arm64 Docker engine), with tedious 20 and the statements of the store as they are built (datahub scratchpad `probe-5617/probe.mjs`):

- **`NEXT VALUE FOR` in `UPDATE ... SET` and in `INSERT ... VALUES`, with `OUTPUT ... INTO` a table variable, inside `sp_executesql`.** The first grant of a key took the `INSERT` path and gave token 1. A try of the held key gave no row, and the sequence stayed at 1: an `UPDATE` that changes no row takes no number. The grant after the release took the `UPDATE` path and gave token 2.
- **The end on the server's clock.** With a duration of 1,000 ms, a try 500 ms after the grant and a try 700 ms after a renewal got no row. 1,100 ms after the renewal, the holder check answered 0 and a try got the key.
- **A renewal and a release after a takeover.** Each changed 0 rows, and the key stayed held. The release of the new holder changed 1 row, and the key was free.
- **Concurrent compare and set, under locking read committed and under read committed snapshot (the default of Azure SQL Database).** 16 sessions raced 200 times for a key with no row, 200 times for a released row, and 20 times for a row whose lease had ended. Each race had exactly one grant, no session got an error, and the 220 rows had 220 different tokens.
- **The permissions.** A user with no grant got `The table dbo.mutex_leases does not exist, or the role has no permission on it.` With `SELECT`, `INSERT` and `UPDATE` on the table only, it got the same message for the sequence. With `UPDATE` on the sequence too, the grant, the renewal, the holder check and the release worked.

## How it fits the other decisions

- **ADR 0003 (fencing tokens).** The token is in the row, and each grant takes a new one from the sequence. After a takeover, a late holder has the smaller token, and a fenced resource refuses its writes. A frozen holder can still write until it runs again and its renewal fails. That is the case for which ADR 0003 exists.
- **ADR 0013 (a lost lease aborts the signal).** It stays. The signal aborts when a renewal finds another holder or no renewal succeeds within the deadline. The end of the session is no longer a loss: the lease does not live on it.
- **ADR 0022 (the store takes its session from the caller).** It stays. The rule that a session must never connect again by itself goes for `SqlServerStore`, and so does the rule of one session for each held key.
- **ADR 0024 (the holder check reads the lock view).** Superseded. The holder check reads the lease row, and `VIEW SERVER STATE` and `VIEW SERVER PERFORMANCE STATE` are no longer necessary.
- **ADR 0033 (a new leader waits for each recorded session).** The same idea between two kinds of store: a holder that is silent past its lease duration loses its keys, and `leaseDuration` has the same name and the same meaning. ADR 0033 counts the duration on the clock of the new leader. This decision counts it on the server's clock, because the server is the only clock that every store shares.

## Consequences

- The key of a vanished holder is free at most `leaseDuration` after its last renewal, plus one interval of the waiter, whatever the connection policy.
- Each try of a waiter and each renewal is one statement on a new session, once each `heartbeatInterval`. With a `connect` that opens a connection, that is one login each interval. A wait no longer keeps a session open on the server.
- This is a breaking change of `SqlServerStore`: the caller creates a table and gives its name in `table`. The DDL is in [the store page](../stores/sqlserver-store.md#how-it-works), next to the sequence. The package has no helper for the DDL of the sequence, so it has none for the table either.
- Postgres, MySQL and MariaDB stores also hold session locks, behind the same `SessionLockStore`, and a pooler or a proxy between them and their server has the same gap. This decision changes only `SqlServerStore`. The lease row is strike 1: a second store copies it, and the third extracts it.
- A step of the server's wall clock forward makes leases expire early. The fencing token is the protection for that case.

### For each consumer

The consumers found with `grep` across `~/Desktop/experiments/elt`, `~/Desktop/mo/datahub` and `~/Desktop/experiments/context-compiler`:

- **datahub, `apps/backend/src/server.ts`:** `LeaderSelector.start(writerKey, …)` over `new Mutex(new SqlServerStore({ connect, sequence: 'dbo.warehouse_writer_tokens', heartbeatInterval: 10_000, clock: globalThis })).key('datahub/warehouse-writer')`. Its `connect` creates the sequence and catches error 2714. It must create the lease table the same way, and give `table`. The default `leaseDuration` of 30 s is larger than its two intervals of 20 s. Its `connect` now runs for each statement, so a `CREATE` in it runs each interval too; a creation once at the start costs less. After a swap, the new build gets the writer within `leaseDuration` and one interval, not when Azure SQL ends the old session. Its `takeLeadership` ignores the lease (`_lease`), so its warehouse writes are not fenced. A frozen old writer can write until its renewal fails.
- **elt, `packages/destinations/sqlserver/src/sql-server-checkpoint-store.ts`:** `SqlServerCheckpointStore` holds a key for each copy `id` with `Modes.skipIfBusy()` (`heartbeatInterval: 10_000`). Its `create` makes the sequence with `IF OBJECT_ID(..., 'SO') IS NULL`; it must make the lease table the same way, and give `table`. datahub's pipeline uses it inside the writer (datahub `packages/semantic-layer/elt/src/pipeline.ts`), so a writer that vanished leaves these keys too. Today, a run whose process vanished leaves each of its copies busy: the next run fails with "Checkpoint <id> is in use by another run" until the server ends the old sessions. With the lease, one `tryAcquire` takes the key once the lease expired. Its connections can come from a pool.
- **elt tests:** the tests of `packages/destinations/sqlserver` and `packages/vectorizer/src/sqlserver.test.ts` use `SqlServerCheckpointStore`. Their fixtures create the table.
- **context-compiler:** no use of `SqlServerStore`.

## Answers to the open questions

Ezz answered with defaults on 2026-11-25:

- **Is `leaseDuration` required, or does it have a default?** It has a default: 30,000 ms. datahub and elt use a `heartbeatInterval` of 10,000 ms, so the default fits them.
- **Does the store keep its name and its import path?** Yes: `SqlServerStore` of `@zukhruf/mutex/sqlserver`, with a breaking change of its options.
- **Does the test of a vanished holder need a time limit?** No. It waits for the grant with no limit on real time, and its header says the expected time in words: about `leaseDuration` (1 s in the test) after the last renewal, plus one interval of the waiter.
- **Which policy does centraldblin use?** Not known. The lease does not depend on it.

## Confirmation
