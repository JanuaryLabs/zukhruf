## How the packages fit together

The packages import each other in layers: base, coordination, domain, UI, UI extension, tool and host. Each layer imports only the layers that the ADR lists for it, and `nx lint` refuses each other import. [ADR 0001](./docs/adr/0001-zukhruf-is-a-layered-standard-library.md) gives the layers and the rules that put code into a package.

## Development

```sh
npm install
npx nx run-many -t test        # builds, then runs every test
npx nx run-many -t typecheck   # formats, lints, then type checks
npx nx run <project>:test      # one project, e.g. mutex
npx nx run copy-check:check    # each copy in the test files has a line in a copy ledger
```

## Change a package and a repo that uses it

To change a package and a repo that uses it together, push the package: a push to `main` releases it (see [Release](#release)). Then install the published version in the other repo:

```sh
npm view @zukhruf/<package> version         # the newest version on npm
npm install @zukhruf/<package>@<version>    # in the other repo
```

Do not link the package into the other repo. A link runs code that no release holds, and the other repo can get a second copy of a dependency that both repos use. The `NoOutsideLinks` step of [`@zukhruf/git-hooks`](packages/git-hooks/README.md) stops a commit while a package is linked from another checkout.

## The source condition

Each export of a package has a `@zukhruf/source` condition first. This condition points at the source in `src/`. The other conditions point at the build in `dist/`. A repo that sets no condition gets `dist/`. In this repo, the git hooks (`node --conditions=@zukhruf/source`) and `apps/diagram-playground` set the condition, so they run the source of a workspace package with no build. The published package has no `src/`.

The name follows the `@<scope>/source` convention of Nx and of the "live types" setup in TypeScript monorepos. The scope keeps the name unique. A repo that asks for `@zukhruf/source` gets the source of zukhruf packages only, and not of other packages that define a plain `source` condition. The name is not `development`, because bundlers such as Vite set `development` for every consumer.

## Release

Releases need no command. The packages that Nx tags `npm:public`, because their package.json is not private, are released together, as their conventional commits on `main` ask: a `feat`, `fix` or `refactor` bumps the patch version while the major version is 0, and `chore`, `docs`, `test` and `ci` release nothing.

Each push to `main` starts `.github/workflows/release.yml`, and the release does not wait for CI ([ADR 0007](docs/adr/0007-release-does-not-wait-for-ci.md)). The pushes that arrive during a release wait as one run of the newest push. `nx release version` writes the versions into the checkout of the runner only, and builds the packages ([`nx-release-version`](.github/actions/nx-release-version/README.md)). The release job then makes the tag `release/<version>` on the pushed commit through the GitHub API ([`release-tag`](.github/actions/release-tag/README.md)), and `nx release publish` publishes what was built. The release commits and pushes nothing, so the versions in the `package.json` files on `main` stay old: npm and the release tags hold the versions ([ADR 0008](docs/adr/0008-the-release-writes-no-commit-and-tags-the-pushed-commit.md)). Nothing reaches npm without its tag, and a version already on npm is skipped. When GitHub refuses the tag, the run fails without a publish, and the Release run of the next push releases the same commits. A push with nothing to release changes nothing.

CI runs beside the release and only reports. A red run changes nothing on npm, and the next push fixes forward. CI never cancels a run on `main`: the pushes that arrive during a run wait as one run of the newest commit, and that run checks every commit since the last green run.

To see what the next release would be:

```sh
npx nx release version --dry-run
```
